# Architecture

[Español](es/ARQUITECTURA.md)

## In brief: how it works

MuDeskClient has two halves: the page in the browser and a gateway in PHP on the web server. Nothing is installed on the remote computers.

1. **Signing in.** `api.php` checks the user (a password with lock-outs, TOTP or a passkey, or OpenID Connect or a Windows account) and keeps a PHP session. Users, connections, settings and the audit log are JSON files in `data/`: there is no database. The RDP passwords a user saves are encrypted with a key derived from that user's own password.
2. **Connecting.** The page asks `rdp.php?a=stream` for a session. That request does not end while the session lasts: its PHP process becomes the RDP client. It checks that the computer is an allowed target, connects to it over TCP (directly, or through a Remote Desktop Gateway or a connection broker), negotiates TLS and NLA (CredSSP with Kerberos or NTLMv2) or, for Windows XP and Server 2003, Standard RDP Security, and checks the computer's certificate (the one an administrator fixed for it, or the one the user trusted: the first time, shown for the user to confirm).
3. **The picture.** What the remote computer draws comes in RDP updates (bitmaps, drawing orders, or the graphics pipeline with H.264 and RemoteFX), still compressed. The gateway passes them on as binary frames in that same response, and a worker of the page decodes them (WebCodecs for H.264, JavaScript for the rest) onto a canvas: the gateway speaks RDP but decodes almost no image.
4. **Input.** Keys, mouse, touch, the clipboard and the rest go from the page as short POSTs (`rdp.php?a=send`, allowed by the session's token), each handed to the session's process through a local socket (or a queue file); that process puts them in order and sends them to the remote computer. The camera's pictures and the answers of the user's own folder take a lane that is not ordered, so no key waits behind them.
5. **Channels.** The clipboard (text, formatted text, images, files), sound and the microphone, the camera, the shared folder on the server and a folder of the user's own computer (as drives), the MuDeskPDF printer, display changes, several monitors, RemoteApp windows and multitouch: each one is an RDP virtual channel the gateway speaks (`src/Rdp/`), and the browser does what only it can (playing sound, recording, the camera, the local files, printing).
6. **Ending.** The request ends when the user disconnects or closes the page, or when the remote computer ends the session. A dropped connection is tried again by the page while Windows keeps the session. Every step is in the audit log.

All of it is plain PHP (with only the OpenSSL and session extensions PHP comes with), plain JavaScript and HTML, so it runs on ordinary shared hosting: no daemons, no ports open to the network, no WebSocket needed (on a server of your own, an optional WebSocket service can carry the stream and the input: see below). The sections below go into each part.

## Goals and constraints

- Remote desktop (RDP) in the browser with **nothing installed on the remote computers**.
- Browser side: HTML, CSS and JavaScript only (ES modules, no libraries).
- Server side: **plain PHP 8.1 – 8.5**, only the bundled `openssl` and `session` extensions, no Composer dependencies, no database (JSON files).
- Must run on **shared hosting**: no daemons, no ports open to the network, no WebSocket (an optional service of its own for the servers that allow one, below).

`index.php` asks for `app.js` and `app.css` with `?v=<version>-<fingerprint>`: `Http::build` hashes the names, sizes and dates of the scripts and styles in `public/assets`, so an update changes the address even when the version number does not. The same fingerprint goes in `data-build` of `<html>` and in the `state` answer (`build`): a page older than the gateway says so and offers to reload when it asks for the state (at start and on signing in; not on every request, since the fingerprint costs about 0.8 ms).

### Why one long HTTP request per session

A normal PHP request ends after the response and the RDP connection must stay open for the whole session. Shared hosting does not allow background processes or WebSockets, so each session is **one HTTP request that does not end**: `rdp.php?a=stream` opens the RDP connection and streams binary frames to the browser (`fetch` + `ReadableStream`). If the hosting cuts the request, the browser reconnects automatically and the Windows session is still there.

Frame format (server → browser): `[u8 type][u32 length][payload]`

| Type | Content |
|---|---|
| 0 | padding (makes some proxies start forwarding) |
| 1 | RDP update: `u8 fast-path code` + data (bitmaps, palette, pointers, drawing orders) |
| 2 | desktop size: `u16 width, u16 height, u8 bpp` |
| 3 | status JSON (`token`, `connected`, `end`, `errorInfo`…) |
| 4 | clipboard sub-protocol (`Cliprdr`) |
| 5 | display control available (dynamic resolution) |
| 6 | keep-alive |
| 7 | audio sub-protocol (`Rdpsnd`) |
| 8 | print job JSON (`Rdpdr`, MuDeskPDF) |
| 9 | graphics pipeline message (RDPGFX, decoded in the browser) |
| 10 | bulk compression on: fast-path update as received: `u8 code, u8 fragmentation, u8 compression flags` + data |
| 11 | bulk compression on: slow-path data PDU as received: `u8 compression flags, u8 pduType2` + data |
| 12 | RemoteApp: JSON about the program's windows that does not come with the drawing orders (a window cloaked or shown again) |
| 13 | microphone: `u8 1, u32 rate, u8 channels` (a program of the remote computer records: send 16-bit PCM like this) or `u8 0` (stop and let go of the microphone) |
| 14 | the connection made again (a guest joined a shared session): every decoder and cache starts anew |
| 15 | to guests only: `u16 x, u16 y`, where the owner's mouse is |
| 16 | camera: `u8 1, u16 width, u16 height, u8 pictures a second, u8 the start's number` (a program of the remote computer uses it: send JPEG pictures so, each with that number) or `u8 0` (stop and let go of the camera) |
| 17 | this computer's folder: `u32 the request's number` + a Device I/O Request for it (MS-RDPEFS, from its DeviceId on), answered by `localdrive.js` (messages 20 and 21, with that number) |

Messages from the browser (`rdp.php?a=send`, after a `u32` sequence number: `u8 type` + data):

| Type | Content |
|---|---|
| 1 | input events (keyboard, mouse, Unicode) |
| 2 | resize: `u16 width, u16 height` |
| 3 | page visible or hidden |
| 4 | clipboard sub-protocol (`Cliprdr`) |
| 5 | quit |
| 6 | refresh: the server draws everything again |
| 7 | typed text: characters with their pauses |
| 8 | several characters at once (UTF-8): pasted with "Phone keyboard through the clipboard", else typed |
| 9 | reserved (ending a session from the gateway): refused from the browser, as every type from 32 up (the gateway's own: a guest joined, a link revoked, a guest's input) |
| 10 | graphics pipeline frame acknowledgement |
| 11 | diagnostic note of the browser (diagnostic mode) |
| 12 | a text of the clipboard history (UTF-8), always pasted (with the clipboard on) |
| 13 | several monitors, each the size of its window (JSON) |
| 14 | RemoteApp command (JSON, see below) |
| 15 | microphone audio: 16-bit PCM in the format of frame 13 (about 100 ms each; while one waits to be sent the next is joined to it, at most a second, the oldest dropped) |
| 16 | multitouch frame (with the connection option, once the gateway sent `touch: true`): u8 count, then per finger u8 id (0–9), u8 state (0 down, 1 moved or still, 2 lifted, 3 canceled), i16 x, i16 y; every finger on the screen in each frame |
| 17 | answer to a Remote Desktop Gateway's consent message: `u8 1` accepted, `u8 0` declined |
| 18 | camera: `u8` the start's number (frame 16) + a JPEG picture at its size (only the number: the camera could not be opened); out of order |
| 19 | this computer's folder: `u8 1, u8 read only` + its name (shared, up to 64 characters), or `u8 0` (no longer shared) |
| 20 | this computer's folder: `u32` the request's number (frame 17) + its answer (from the DeviceId on); out of order |
| 21 | this computer's folder: `u32` the request's number, a listing's first answer (`u32` length + answer) with its other names (`u32 FileId, u32 class, u32 count`, then each `u32` length + entry); out of order |
| 22 | a recording made in the page: `u16` its number (status `record_video`), `u32` the piece's, `u8` flags (1 the first: then `u16` length + JSON `{mime, w, h, sound}`; 2 the last, after it was stopped; 4 the page cannot record), then the next bytes of its video; out of order, one at a time |

Besides the stream and these messages, `rdp.php?a=watch` gives a guest the stream of a shared session, `rdp.php?a=replay` a recording (see below), `rdp.php?a=clipfile` takes clipboard files and images in chunks (into `tmp/<sid>/`, counted in the quota) and `rdp.php?a=print` hands out a print job.

### Session admission and time limits

- Each session holds a PHP process while it lasts, so the number of sessions is limited per user and for all users together (`max_sessions_total`, 20 by default). Before any output, `rdp.php` counts the running sessions and registers the new one under one lock (`data/run/register.lock`), so two requests at the same time cannot both take the last place. A full gateway answers 503 `busy` at once, before opening a socket.
- Each handshake step (TCP, TLS, X.224, NLA, MCS) waits at most 8 s; the activation, 30 s. If the browser closes while connecting, the PHP process is freed within 1–2 s.
- The target name is resolved after the admission, so the global limit also bounds the processes waiting for a slow DNS server (see [HOSTING](HOSTING.md#host-names-dns)).

### Input path (browser → server)

Keyboard, mouse, clipboard and resize messages go through **short POST requests** to `rdp.php?a=send`:

- No PHP session is opened (no session-file lock, no user file read): they are authorised by a random **per-session token** delivered in the first status frame and sent in the `X-MuDesk-Token` header (not in the URL, so it stays out of the web server logs). The session's file in `data/run/` keeps only its SHA-256: a copy of the data folder gives nobody the keyboard of a running session. The body is read only once the token (or a guest's link) is checked, and never past 4 MB (4 KB for a guest): PHP's `post_max_size` does not limit it, and a large body sent without a token was read whole first. It is read as long as its `Content-Length` says: with a limit, PHP 8.1 and 8.2 take that much memory first (4 MB for each key).
- Every message carries a `u32` sequence number. The browser keeps **up to 4 requests in flight**; the stream process re-orders them (gaps older than 0.5 s are skipped, and a copy of one already taken is left out). A request the hosting refuses without running it (429, 503, 508: its limit of PHP processes at once, say) goes again after 50, 100, 200, 400 and 800 ms at most, and meanwhile, until 5 s after the last refusal, one request at a time; one lost on the way (no answer, a proxy's 502 or 504) goes again too, but not a guest's (taken as it comes: a copy would type twice).
- The camera's pictures (message 18) and the answers of this computer's folder (20, and 21: a listing's first answer with its other names) go **out of order** instead (`Sessions::OUT_OF_BAND` as the sequence number, two requests in flight, the folder's answers first and only the newest picture waiting): taken as they arrive, so no key waits behind a picture of some 40 KB or a piece of a file of up to 1 MB. `rdp.php?a=send` takes nothing else on that lane, nor anything of the page on the guests' lane. A folder's answer lost on the way (a network error, or the gateway busy: 5xx) is sent again up to 3 times, 0.5, 1 and 1.5 s later; the gateway takes only the first of two (each answer carries its request's number).
- Mouse moves are coalesced while requests are in flight (only the last of the browser's coalesced events is placed). Mouse moves and graphics-pipeline frame acknowledgements take 3 of the 4 slots at most and take turns, so an acknowledgement never starves behind a moving mouse (Windows paces its frames by them) and a key or a click always has a slot.
- **Typed text** (on-screen keyboards, IME, autocorrection) keeps its order with the rest of the input in a queue in the gateway (`Client::input`):
  - A single character (message type 7) goes as Unicode and whatever comes behind waits 100 ms; the pause is applied in the gateway because HTTP requests arrive unevenly spaced.
  - Several characters at once (message type 8, UTF-8), with the "Phone keyboard through the clipboard" option, are **pasted** (`Client::pasteText`, `Cliprdr::typeText`; reasons and tests in [MOBILE-KEYBOARD](MOBILE-KEYBOARD.md)). Texts in a row are joined. When the last thing was copied in Windows, it is read first (all its formats, up to 16 MB) to put it back; with files or over 16 MB the text is typed. The gateway announces the text (with the formats that keep it out of the history and the cloud), waits for the answer to *that* announcement (Windows answers each list in order) and for the screen to change after the last input sent, presses Ctrl and V and holds them until the application asks for the text, hands it over, releases them and puts the clipboard back right after each paste (an empty text when nothing was copied). Windows confirms an announcement before applying it and did not apply a list equal to the one it had (two pastes in a row pasted the previous text again), so each announced list carries a format of its own that alternates: two lists in a row never match. Without the option the text is typed as Unicode.
  - A text of the clipboard history (message type 12, UTF-8, up to 1 MB) is always pasted this way, whatever the option (connections with the clipboard on).
  - Input waiting behind a paste goes out once the screen changes (the application has drawn the paste).
  - Limits only for when Windows does not answer: 2 s for the answer to the announcement and for the screen change, 10 s for the application to ask for the text; then it is typed as Unicode.
- RemoteApp (message type 14, JSON): the desktop synced (`ready`: the server's windows all sent, with how many are open; the program may be asked for), a window brought to the front (`activate`), minimized, maximized, restored or closed (`sys` with one of those four commands only).
- The short request hands the message to the long one through a **Unix socket** in `data/run/` (or in the system temp folder when that path reaches 100 characters); on Windows, which has no Unix sockets for PHP, through a **TCP port of this computer only** (127.0.0.1), each message starting with a secret of the session kept in its mode file (any local process can connect to such a port); without `stream_socket_server` or with `'ipc' => 'file'`, through a queue file polled every 20 ms (Windows used it before: each key, mouse move and frame acknowledgement waited up to 20 ms). Each request is one connection to the socket with one message, kept apart until all of it has arrived: added to one buffer as it came, a large message (a paste) arriving in pieces had the other requests' messages in between, and the session's input stopped for good. New connections are looked for when the listening socket is readable (trying on every turn cost the session's loop 8–11 µs on Windows) or 20 ms after the last look: with TLS data already decrypted, PHP's `stream_select` gives that stream alone without asking the system, and the listening socket was left out while the server drew.

### The optional WebSocket service

On a server of your own (Linux: a VPS, the Docker image, `deploy/lxc/install.sh`) the stream and the input can go through one WebSocket instead (`tools/ws-server.php`; how to set it up in [HOSTING](HOSTING.md#websocket-optional)). Nothing else changes: each session is still `rdp.php` itself, with the same checks, frames and messages, so a session is the same with the WebSocket or without it.

- The service listens on 127.0.0.1 only (`websocket_listen`, port 8091 by default), behind the web server, which passes `<public>/ws` to it with the site's `Host`, `X-Forwarded-For` and `X-Forwarded-Proto`. A connection whose `Origin` is not the site's own (that scheme and `Host`) is refused (403) before anything else is read, so another site's page cannot use the user's cookie through it.
- The page tries it once when it opens (`state` gives its path, `ws`, unless `config.php` has `'websocket' => false`) and uses it when it opens within 2 s; otherwise, also for a session whose WebSocket does not open, HTTP as always. Guests, recordings, replays, the shared folder's files and the rest of the page stay on HTTP.
- A connection is one session. Its first message (text) is `{"csrf", "body"}`, what `rdp.php?a=stream` takes; the service makes a process for it, a copy of itself (`pcntl_fork`: the code it compiled once is shared, some 5 to 8 MB less a session) or, without `pcntl`, a PHP started for it (`tools/ws-session.php`), which gives `rdp.php` the request's details (the cookie, the client's address as the proxy saw it, the scheme) and its body, and writes the frames to its standard output, sent on as binary messages as they come (a session refused before its first frame: its answer as one text message, then the close). Output waiting for the browser past 8 MB is not read until it goes, so a slow browser holds back only its own session.
- Then `{"token"}` (from the first status frame) and binary messages, each what `rdp.php?a=send` takes: the token checked once with `Sessions::tokenOk`, each message handed to the session with `Sessions::fromBrowser` as the short requests are, in the order they came on the socket.
- The browser leaving (the socket closed) closes the session's standard input: `Http::aborted()` is then true, as when an HTTP client goes, and the session ends as over HTTP (`browser_closed`, audited, its files removed); one that does not end within 15 s is stopped.
- Linux only: the service waits on its sessions' pipes with `stream_select`, which PHP cannot do with pipes on Windows.

### Sharing a session

- A link is `#/watch/<sid>.<secret>`: 24 random bytes (base64url), made by `api.php` `session.share` for the session's owner; the session's file in `data/run/` keeps the secret's SHA-256 and the mode (`view` or `control`), never the secret. Up to 10 links per session; none for RemoteApp or with the queue file.
- The guest's page posts the link to `rdp.php?a=watch` (no account, no PHP session). The request connects to the session's socket and says `\0WATCH` + the link's id (after the session's secret over TCP); the stream process keeps that connection open as a guest (at most 5) instead of reading one message from it, and its loop learns of the arrival (an event of its own, type 0x21).
- On an arrival the stream process sends what the old connection had, admits the guest, disconnects from the RDP server and connects again with the same credentials, the same desktop size and the same certificate (any other one ends the session: `cert_changed`), after frame 14. Windows keeps the session meanwhile. The graphics pipeline's surfaces, caches and H.264 streams, the drawing orders' caches and the bulk compressors' histories cannot be joined halfway: from frame 14 every page (the owner's and the guests') decodes from scratch.
- What the browser is sent goes to the guests too, filtered (`Sessions::GUEST_FRAMES`: the picture, its size, the pointer, status and keep-alives; never the clipboard, sound, microphone, camera, this computer's folder (frames 16 and 17) or print jobs), copied only while a guest watches. The guest's request relays it unchanged. A guest that cannot keep up (8 MB waiting) is let go; one that leaves is noticed on the next keep-alive (every 10 s). The owner's page is told how many watch (`viewers` in a status frame). While anyone watches, the owner's page hidden does not stop the server drawing.
- The owner's mouse position (the last mouse event of each batch of input) goes to the guests only, as frame 15.
- A guest with control sends `rdp.php?a=send` with the link's secret in `X-MuDesk-Share`: only keyboard and mouse (1), typed text (7, 8) and touch (16), at most 4 KB, written to the session with sequence number `0xFFFFFFFE` (its own lane, in arrival order: the page keeps one request in flight). The session reads it as an event (0x22 + the message) and handles it as the owner's input. The page never sends acknowledgements, sizes or visibility.
- `session.unshare` removes the link from the file and tells the session (an out-of-band message, 0x20 + the link's id), which lets its guests go at once. The links go with the session's file when it ends.
- A link for a while (`minutes`: 15, 60 or 240) keeps its `expires`: `findShare` refuses it past then, and the session's heartbeat (every 15 s) revokes it as `session.unshare` does (`share_expire`). A guest's input carries its link's id (`Sessions::GUEST_INPUT` + id + message); the session notes when each link with control was last used (or a guest came), and past *Minutes unused after which a guest loses control* (`share_control_idle_minutes`, 15) `Sessions::endIdleControls` turns its mode to `view` and sends its guests only (`toViewersOf`) a status with `control_ended` (`share_control_end`).

### Session recording

- With `record` on a connection (set only by the administrator: a user's own save keeps it), `rdp.php` starts a `Recording` right after the token, before anything of the session is shown, and sends `recording: true, record_by: "policy"` in a status frame; a recording that cannot start ends the session (`record_failed`). `rdp_connect` and `rdp_start` say `recording`. Its id is the session's.
- Started in a running session: `api.php` (`session.record` for the session's user when `Auth::recordsOwn` allows it, `admin.sessions.record` for an administrator) checks who may and tells the session with an out-of-band message `0x23` and JSON `{on, by, as}` (`Sessions::record`; the browser's own input can never send one). The session's loop starts it at once (not for RemoteApp), as a recording made in the page (`kind: "video"`): the stream's frames cannot start halfway (they build on surfaces, caches and video of before, which only a new connection sends again: a first version made the connection again, and Windows showed its welcome for some 10 s), so the page records what it shows. A status frame tells it `record_video`, its number (`$recGen`); `pagerec.js` draws the desktop (all its screens, `surface`) and the pointer where the user's mouse is into a canvas of its own, at the desktop's size at the start (scaled into 3840 × 2160; a desktop that grew drawn smaller, one that shrank in the middle), up to 15 times a second when something changed and once a second (each picture asked of the captured track, or of the stream in Firefox, which has `requestFrame` there); it mixes the remote computer's sound and the microphone the remote computer hears on a line of its own (an `AudioPlayer` playing into a `MediaStreamAudioDestinationNode`, also while the page is muted; the sound's formats it was told at the start kept for it); and records both with MediaRecorder (WebM VP9 or VP8 with Opus, MP4 in Safari; 0.5–6 Mbit/s by the desktop's size; a piece each second). Each piece goes as message 22 on the out-of-order lane, one at a time and in order: one that did not get there (the network, the gateway busy: 5xx, 410, 429) waits ahead of the next ones and goes again with the next piece the recorder makes, 10 times at most; then, or refused, or with more than 32 MB waiting (`REC_BACKLOG`), the page gives the recording up (`PageRecorder.abandon`: REC_FAILED as the next piece). The gateway keeps a piece as a frame `Recording::VIDEO` (33) if it is the next of the current recording (one sent twice, or of a recording before, left out); one missing (a number skipped) ends it there, whole up to it, as does one growing faster than a video can (`Recording::overRate`: `PAGE_RATE`, 1 MB a second since it started, and 10 s more); the first says what the page records (`Recording::describe`: its type, `width`, `height`, `sound`). Stopped, the page is told (`recording: false`), sends the rest with the last flag (or flag 4, failed), and then it is closed (`$recEnd`, `$closeRec`; also when the session ends, or a new one starts); one the page cannot make (flag 4), with a piece missing, too fast, or that stops on its own ends with `record_error: "record_page"`. The page lets its recorder go when it leaves the session (`stop`, `dispose`). The sound is mixed in the session's own AudioContext, or the microphone's, when one runs (a silent `ConstantSourceNode` keeps it going: Chrome writes nothing while an audio track gives no data); with none running, the picture alone. Such a recording takes nothing of the stream's frames (`Recording::frame` keeps only `VIDEO` for it, and no `VIDEO` for the others). A page that connects again (a dropped connection, or a server without Display Control changing its screens) is a new stream: the recording ended with the one before. Such a recording has an id of its own (`Recording::newId`), its session in `sid`, `by`, `started_as` and `stopped_by`; the session's file says `record` and `record_by` (`Sessions::recording`), read by the active sessions, the page (a status frame `recording`, `record_by`, and `record_error` when it could not be written: then it stops and the session goes on) and the guests. Audited as `recording_start` and `recording_stop` with `rec`, the recording's id.
- Every frame the browser is sent goes through `Recording::frame`, which keeps the picture's and the sound's types only (`Recording::TYPES`: updates, size, status, display control, sound (frame 7), graphics pipeline, compressed updates, the microphone's format (frame 13), frame 14 and the owner's mouse, frame 15, and what the remote computer was sent of the user's microphone, the whole packets of 16-bit PCM `Audin::fromBrowser` sent (nothing while it is not open), as type 32 (`Recording::MIC`, a recording's own: no frame of the stream has it); its details say `sound` once there is some, and the largest desktop, `width` and `height`), each as `[u32 ms][u8 type][u32 length][payload]`. A piece is written once it reaches 1 MB (a larger frame goes on in the next pieces: the plain bytes are one stream) or each second: AES-256-GCM with a key derived from the server key (HMAC-SHA256), a random nonce, and the recording's id and the piece's number as additional data, as `[u32 length][nonce][tag][ciphertext]` after `MDREC1\n`. Its details (who, connection, start, end, seconds, bytes, `truncated`) go in `data/recordings/<sid>.json`.
- `rdp.php?a=replay` (administrators and auditors, and a user their own, audited as `recording_view`) decrypts it piece by piece and sends the plain frames, then a padding frame `end` when all of it was read (without it the page says the recording is damaged from there); the page's worker gives them at their pace (`timed`), decoding what comes before the point asked for at once, and pauses, plays and changes the speed when the page says so. The microphone's frames (13, its format, and 32) are played with the sound, on a line of their own (`AudioPlayer.micFormat`, `micData`); in a live session frame 13 only goes to the capture. A recording made in the page (`kind: "video"`) is read whole by `loadPageVideo` (its `VIDEO` frames, in order), made seekable by `WebmRemux` (`webm.js`: MediaRecorder leaves the segment's and clusters' lengths unknown, and no duration nor cues; they are written, the tracks and blocks as they were, cues at the clusters with a key frame of the video; what it cannot read ends the file at its last whole element, an element over 64 MB is taken for garbage, and pieces are joined only once an element is whole; MP4 as it is) and played by the browser's own `<video>` from a `blob:` URL (the policy allows `blob:` media); its download is that same file.
- `Recording::cleanup` (on each recorded session, each listing and the hourly housekeeping) removes those older than `record_days`; with 0, the default, none: kept until deleted by hand.
- **Every one**: `admin.recordings` (administrators and auditors) lists them all, the newest first (`Recording::all`; one made before who started it was kept is the connection's); `admin.recordings.delete` deletes one for an administrator (not while it is being recorded; audited as `recording_delete` with its owner and `as: "admin"`).
- **A user's own**: `api.php`'s `recordings.mine` lists the recordings a user started in their own sessions (`Recording::ownedBy`: their `uid` and `started_as: "owner"`), `recordings.delete` deletes one (not while it is being recorded: `Recording::running`, no `ended` yet and its session alive, `Sessions::alive`; one a process killed left behind can be deleted; audited as `recording_delete`), and `recording.info` and `rdp.php?a=replay` give a user only those (administrators and auditors any): any other is "not found". **Recordings** is in the page's menu of every user, administrators too (for them `ownedBy` also takes one they started in their own session as administrators: `by` theirs); `record_own` (`Auth::recordsOwn`) says whether they may record now.
- **Its video** is made in the browser (`recvideo.js`): a session object plays the recording off the page with `video: true`, and its worker reads it as fast as it goes. Before a frame that comes at least 1/15 s after the last picture, if something was drawn since, the worker waits until the graphics pipeline's H.264 frames went out (`GfxPipeline.idle`; decoded in software there, so each one comes out at once) and asks the page for a picture (`cap`, with its time), going on when the page answers (`ack`). The page draws the desktop, scaled into the recording's largest size, and the pointer where the user's mouse was, and encodes it with WebCodecs' `VideoEncoder` (VP9, else VP8; a key frame every 5 s; at most 8 pictures waiting). The sound's frames come with their time: each piece is decoded, taken to 48 kHz with a windowed-sinc resampler and placed on a line of time as the page plays it (right after the one before of its own source, the remote computer's or the microphone's, while it comes in time, at its own time after a pause or when it comes over 0.5 s ahead), added to what is there; what lies before the last picture is final and goes to `AudioEncoder` (Opus), silence where there was none. `webm.js` puts both into a WebM file: an EBML header, a segment of known length with a seek head, the info (milliseconds, duration), the tracks (OpusHead and codec delay for the sound), clusters of SimpleBlocks in time order (a new one at each key frame, or after 30 s) and the cues of the key frames; the clusters go into blobs as they close.

### Remote Desktop Gateway and connection broker

Checked against the specifications and against an open-source client that works with Windows' gateways and brokers. Tested through an open-source implementation of RD Gateway in front of Windows 11 (a whole session: NTLM, the device policy, keep-alives, the channel's close; both transports, and Kerberos with a test realm's KDC), and the routing tokens against Windows 11 itself; not yet against Windows Server's own gateway or a real broker. The RPC transport (Windows Server 2008 and 2008 R2) was tested against a gateway written from the specifications, `tests/fixtures/rpc_gateway.php`, which an independent client also went through. In the tests, against their own: `tests/fixtures/rdg_server.php` (with `tests/fixtures/nla_server.php` behind it), `tests/fixtures/rpc_gateway.php` and `tests/fixtures/broker_server.php` (a broker and the computer it sends the client to, written from MS-RDPBCGR).

- **Connection broker** (MS-RDPBCGR): the connection's `lb` (238 bytes at most: the X.224 request's length is one byte) goes in the X.224 Connection Request as the routing token (with CR LF) instead of the `mstshash` cookie; the client cluster data block (`TS_UD_CS_CLUSTER`, 0xC004) says redirection is supported (version 5) and, on a redirected connection given a session, the session to join. A Server Redirection PDU (share control PDU type 0xA, `SEC_REDIRECTION_PKT`) is read field by field in the order of the specification (`Client::redirection`) and thrown as `Redirection`. `rdp.php` disconnects and connects again (`Client::redirected`): with a routing token and no target address, back to the computer that sent it, with that token (1.3.8); otherwise to a computer it names, without a token: by address first (its address, then its list of addresses), then its FQDN and NetBIOS name, each allowed target in turn while one cannot be reached (`unreachable`; through a gateway, `gateway_denied`), audited with the one it replaces; through a gateway by name first, its policies deciding. Its session (when not 0), its user and domain (when not empty; an empty domain too with a user of the form user@domain) and its cookie in place of the password go along; that password, when it is text and not an opaque cookie and the user's own is not known (signed in on the broker's logon screen), signs in with NLA there. The target's certificate the broker gives (`LB_TARGET_CERTIFICATE`, a container in base64) is the one to find there: taken without asking (`vouched_by_broker` in `cert_trusted`), another refused as a changed certificate, even on a first use; one the broker does not vouch for is shown to the user to confirm the first time (`cert_new` with its name), and one an administrator fixed for that computer (by its name or address) is the only one taken there, whatever the broker says (`cert_unexpected` for another). At most 3 in a row; each audited (`rdp_redirect`, with whether the user name changed), each computer's certificate pinned under its name (the connection's `certs`, read again each time). One that only informs (`LB_NOREDIRECT`) is not followed. A password encrypted for the target's key (`LB_PASSWORD_IS_PK_ENCRYPTED`) is given there as it came, with the redirection's GUID, through RDSTLS (MS-RDPBCGR 2.2.17: RDSTLS and TLS asked for in the X.224 request, also with the security *NLA only*); a refusal is said as the sign-in's (a wrong password, an account locked…). One that comes once the session is up (signed in on the broker's own logon screen, without NLA) is followed the same way, and every page decodes anew (frame 14); `rdp_redirect` says the address reached (`target_ip`) and `late`. Without a gateway the next computer is reached by its address first; when the broker also gives its name (`TargetFQDN`), that name is the one Kerberos, TLS and the certificate's pin use, and the address checked against the allowed targets the one connected to (with an address alone, NLA there uses NTLM, not Kerberos: no realm for an address). A guest joining a shared session that a broker sent elsewhere connects again to that computer with what the broker gave (its session, user and password or cookie); whether a real broker's computer takes that a second time is not known yet.
- **Remote Desktop Gateway** (MS-TSGU, `Gateway.php`): TLS to the gateway (SNI with its name; its certificate, confirmed by the user the first time (`cert_new` with its name, unless `confirm_new_certificates` is off) and pinned in `certs`, under `gw:` and its name, apart from a farm's computers and never dropped, before anything of the user is sent), then `RDG_OUT_DATA /remoteDesktopGateway/` with `Upgrade: websocket`, signed in with Kerberos when a ticket for `HTTP/<gateway>` can be had (one round: SPNEGO with the AP-REQ, its GSS checksum carrying the channel bindings and its authenticator the hint `AD-AUTH-DATA-AP-OPTIONS`; a ticket the gateway refuses: NTLM on the same connection), else NTLM over HTTP (two rounds, under the NTLM scheme, or under Negotiate when that is the only one offered, also when several come in one header; a chunked body read too; the cookies it sets sent back, for balancers in front of several gateways), the NTLMv2 proof carrying the channel binding of the gateway's certificate (RFC 5929 `tls-server-end-point`: the hash of its signature, SHA-256 for MD5 and SHA-1, the one an RSASSA-PSS signature names in its parameters; for gateways with Extended Protection), and `101 Switching Protocols` with its `Sec-WebSocket-Accept` checked, or `200`: the older transport (Windows Server 2012 and 2012 R2), where that connection then streams the gateway's packets after a few random bytes (up to the handshake response, within 128 bytes; de-chunked when a proxy chunks it) and a second TLS connection to the same address (the same certificate, the same `RDG-Connection-Id`, its cookies, signed in too) takes the client's: after its `200`, one `RDG_IN_DATA` with `Transfer-Encoding: chunked`, written on its own and never answered, then each packet as one HTTP chunk. A `404`, `405` or `501` instead is a gateway without the HTTP transport (Windows Server 2008, 2008 R2): RPC over HTTP, below. Over the WebSocket (the client's frames masked; pings, closes and fragments handled), or the two connections: handshake, tunnel (capabilities: consent and service messages; its consent message, after the optional fields before it, shown on the page, the tunnel going on only once the user accepts it: `rdp.php` waits for the page's answer, message 17, up to ten minutes, the browser checked meanwhile and the session's other messages kept for after; declined, `gateway_consent`, with `why`; the same terms accepted again at once when the session connects again, `again`) and tunnel authorization (each waited for up to 90 s: the gateway may ask for a second factor approved on a phone; the client's name; a quarantined client is given its tunnel all the same; its redirection flags are its device policy: a clipboard, drive or printer it forbids is not offered, `cliprdr` left out, `rdpdr` too when both are forbidden, `Rdpdr` announcing only the one allowed, the paste through the clipboard typed instead; `gateway_denied` in `rdp_start`), channel to the computer (its name and port, waited for up to 30 s), then the RDP bytes in DATA packets of at most 16 KB, the gateway's keep-alives answered and one of its own after 60 s without sending (the proxies in front of gateways cut quiet connections), its service messages (packet 0x0B) kept and shown on the page during the session, a reauthentication message let be, and the channel's close (at the end, the gateway's answer waited for before the connections are closed, within a second: else a gateway of two connections could take one's end before the close the other carried). Errors: `gateway_unreachable`, `gateway_not_allowed` (not an allowed target), `gateway_auth` (user name or password refused: the page asks again), `gateway_denied` (the user refused by its policies, that computer not allowed to that user, or not reached), `gateway_unsupported` (neither the HTTP transport nor RPC over HTTP; no sign-in this client makes; `E_PROXY_CAPABILITYMISMATCH`), `gateway_consent`, the KDC's answers about the user (Kerberos), `gateway`. `rdp_start` says its transport (`websocket`, `http` or `rpc`) and how the user signed in to it.
- **RPC over HTTP** (`GatewayRpc.php`, MS-TSGU over MS-RPCH's RPC over HTTP v2 and MS-RPCE), for a gateway without the HTTP transport (Windows Server 2008 and 2008 R2; later ones have it too): two more TLS connections to the same address, each with the gateway's pinned certificate and signed in with NTLM and the channel binding (under the NTLM or the Negotiate scheme; no Kerberos on this transport), to `/rpc/rpcproxy.dll?localhost:3388`. The IN channel is an `RPC_IN_DATA` request whose body (`Content-Length` 1 GiB, as Windows' own client) carries everything the client sends and is never answered while it goes well; the OUT channel, the body of the `RPC_OUT_DATA` answer, everything the gateway sends. RTS PDUs make the virtual connection (CONN/B1 on IN, A1 on OUT; A3 and C2 awaited, 8 s) and keep its flow (a receive window of 64 KB, FlowControlAck once half of it is used; pings let be). DCE/RPC binds to TsProxyRpcInterface 1.3 with NTLM at packet integrity: each request signed, its header too (header signing); the signatures of the gateway's answers are not checked (the TLS connection, pinned, carries them). Then the calls by opnum: TsProxyCreateTunnel (version, the capabilities, its consent message), TsProxyAuthorizeTunnel (the client's name; the device policy, `gateway_denied`), TsProxyMakeTunnelCall left waiting for the next service message (only when the gateway takes them: Windows Server 2008 has none), TsProxyCreateChannel (the computer and port), TsProxySetupReceivePipe (each response PDU of that call is the computer's bytes; a 4-byte last one, its end) and TsProxySendToServer for the client's bytes; DATA, KEEPALIVE and CLOSE_CHANNEL of `Gateway` become SendToServer, an RTS ping and TsProxyCloseChannel, so `pump` is the same. Answers are kept only for the calls waited for, up to 1 MB each. Each channel is made again before its length is used up: the OUT channel when the gateway asks (OUT_R1/OUT_R2: a new connection signed in, the old one's last PDUs read, what waits for the IN channel set aside meanwhile), the IN channel by the client once half of its 1 GiB is sent (IN_R1/IN_R2: a new connection, written to only once the gateway's A4 comes; the old one's last PDUs and IN_R1/A5 first; nothing lost, doubled or out of order, the signatures' sequence going on across both). An HTTP error the gateway answers on the IN channel is not read: it shows as no answer (`gateway`, after 8 s); on the OUT channel, 401 is `gateway_auth` and 404 `gateway_unsupported`.
- **Kerberos** (`Kerberos.php`, `KerberosCrypto.php`; RFC 4120, RFC 4121, RFC 4178, MS-KILE), tried before NTLM by `CredSsp` (`TERMSRV/<computer>`) and `Gateway` (`HTTP/<gateway>`), and so by the sign-in with a Windows account. AES (types 17 and 18, RFC 3961/3962 in plain PHP: n-fold, the derived keys, PBKDF2 string-to-key, AES-CBC with ciphertext stealing over OpenSSL's AES, HMAC-SHA1-96), checked against the RFCs' vectors and MIT's known answers; and RC4 (type 23, RFC 4757: the NT hash as the key, HMAC-MD5, and its own GSS tokens for MIC, Wrap and Unwrap) for a Windows Server 2003 domain, an account whose password is older than its domain's AES keys or a service without AES keys, offered last (a KDC that has AES gives it), and only if the setting `kerberos_rc4` allows it (*Administration → Settings*, off by default: `Kerberos::types()`; RC4 is then neither offered nor taken, in PA-ETYPE-INFO2, a session key or a subkey: someone in the middle saying the account has only RC4 gets no timestamp encrypted with its key). The realms to try: a user@domain's suffix, the domain by its DNS name, or the computer's DNS suffix when it names the domain (never for an address, `localhost` or a local account: the domain `.` or the computer's own name; then NTLM); an alternate UPN suffix is asked of the KDC of the domain or of the computer, which answers KDC_ERR_WRONG_REALM with the domain that has it, followed; its KDCs from `config.php` (`kerberos_kdc`) or the DNS (`_kerberos._tcp` and `_kerberos._tcp.dc._msdcs` SRV records; only port 88, and never this computer, link-local or a cloud's metadata addresses), over TCP port 88, 8 s for the whole sign-in to the KDC (a silent KDC: NTLM). A service ticket that is a referral to another domain of the forest is left to NTLM. The AS exchange with PA-PAC-REQUEST, pre-authentication by an encrypted timestamp with the salt and type of PA-ETYPE-INFO2 (an account without it taken too), a clock more than 5 minutes off corrected once (`KRB_AP_ERR_SKEW`, the KDC's time), user@domain as an enterprise name (NT-ENTERPRISE; an unknown one asked again with the name alone), the name and realm the KDC gives back used from then on; the TGS exchange (the authenticator with the checksum of the request's body). The KDC's answers about the user (a wrong password, 24; an account locked, disabled or expired, 18 with the NTSTATUS of its KERB-EXT-ERROR; a password expired, 23) are said as such and never tried again with NTLM, which would count another failure; anything else (no realm, no KDC, an unknown user or service) goes on with NTLM. The AP-REQ goes in SPNEGO (Microsoft's Kerberos OID first, the GSS flags 0x32, the GSS checksum 0x8003 with the channel bindings or zeros); the AP-REP gives the context's key (the service's subkey); its mechListMIC is checked, and ours sent only when it asks for more (accept-incomplete). GSS Wrap and Unwrap (RFC 4121: sealed, EC 0, RRC 28 as Windows sends it in CredSSP; the other side's rotated back) carry CredSSP's public-key binding and credentials. Signed in with Kerberos, the Windows version is not known (no NTLM challenge): the automatic graphics mode takes the pipeline.
- PHP cannot put TLS on a stream it makes itself, and the RDP connection has its own TLS and NLA inside the tunnel: the RDP client gets one end of a pair of TCP sockets connected over 127.0.0.1 (one listener per process; only the connection from its own end is taken), on which PHP's TLS works (`stream_socket_pair` makes sockets that take no TLS), and `Gateway::pump` moves bytes between the other end and the tunnel, reading the frames and packets in one pass. With 1 MB waiting for the gateway, the client's bytes stay in the pair (its writes wait); with 8 MB waiting for the client, the gateway's stay in its socket. When the tunnel ends, what came before the end is given to the client, then the end itself, which it sees as a remote computer closing (so the server's last error information is read). `Transport` pumps while it waits (its TLS handshake made non-blocking for that), and the session's loop selects the gateway's socket with the others (for writing too while frames wait) and pumps on each turn; while the tunnel opens, the browser is checked every second. Wake-on-LAN is not used through a gateway (the computer is not on this network).

### Screen path

- The stream is read and decoded in a **Web Worker** (`stream-worker.js`), so input never waits for drawing.
- Decoders (`gfx.js`): interleaved RLE (8/15/16/24 bpp), planar (32 bpp), uncompressed, palettes, pointers (colour, new, large). 15/16-bit pixels use lookup tables.
- Decoded rectangles are transferred to the main thread (`postMessage` with transferable buffers) and drawn with `putImageData`: the bitmaps of an update together, in messages of 64 bitmaps and about 4 million pixels at most (64 bitmaps of a whole 1080p desktop, made from a few hundred bytes, held 506 MB), since each message costs the page's thread time of its own (a 16-bit console listing: 24,388 messages took it 371 ms, 385 messages 210 ms).
- Drawing orders (`orders.js`: DstBlt, PatBlt, OpaqueRect, ScrBlt, MemBlt, Mem3Blt: a cached bitmap with a brush, through any ROP3) and the **bitmap cache** (revision 2, three cells of 600/600/1024 entries: secondary orders *cache bitmap v2* store decoded bitmaps, MemBlt draws them) are parsed in the worker and executed on the canvas; the cached bitmaps live on the main thread as small canvases. On by default (`drawing_orders`): validated pixel-identical against xrdp and Windows 11. MemBlt and PatBlt take any ROP: the plain copies (SRCCOPY, PATCOPY) are drawn by the canvas, the others pixel by pixel on the main thread (`drawRop` reads the rectangle, `rop3` computes each bit from brush, source and destination; PATINVERT XORs the brush colour or pattern). Mem3Blt is not negotiated (Windows sends bitmaps instead), so a MemBlt whose ROP uses a brush takes GDI's default white brush. **Text** (same setting): GlyphIndex, FastIndex and FastGlyph with the glyph cache (Cache Glyph revision 2, which servers send as order type 3 for glyph support level "encode"; ten caches) and the 256-entry fragment cache. The worker keeps glyph sizes and resolves positions (deltas, fixed pitch, fragments); the main thread turns each 1 bpp glyph into a `Path2D` of its pixel runs once and fills it in the text colour, clipped to the background rectangle (the opaque rectangle is filled first with the order's *foreground* field and the text uses the *background* field, as RDP defines them). Checked against hand-built orders (`tests/orders_unit.mjs`), pixel-exact in Chrome and Firefox (`tests/e2e_glyphs.mjs`), and with the real text orders of xrdp's own login window: the text is identical to the bitmap version at 16 and 32 bpp. PatBlt draws 8x8 pattern and hatched brushes (PATCOPY; a set bit takes the background colour, as in GDI). Order colours at 24/32 bpp are red, green, blue bytes. Brush and colour table caches are not negotiated and are skipped by length.
- **Bulk compression** (`bulk_compression`, on by default, `'rdp61'`): the client offers up to RDP 6.1 and the server picks a type no higher than that for each block: MPPC with a 64 KB history ("RDP 5", `Mppc.php`, used by xrdp), NCRUSH ("RDP 6.0", `Ncrush.php`: Huffman-coded literals, copy offsets with a 4-entry cache, 64 KB history; decoding tables built from the codes of MS-RDPEGDI) or XCRUSH ("RDP 6.1", `Xcrush.php`: an inner MPPC over a level that copies matches from a 2,000,000-byte history; Windows Vista SP1/Server 2008 and later). `Bulk.php` dispatches by the type of each block and creates each history when first used. Measured on the same 11.1 MB of xrdp screen updates compressed by FreeRDP's compressors: MPPC 3.05 MB and 0.53 s of gateway CPU, NCRUSH 4.85 MB and 0.93 s, XCRUSH 2.08 MB and 0.32 s; browser 0.09/0.18/0.06 s. XCRUSH needs about 4 MB more memory in the gateway and 2 MB in the browser. The gateway decompresses everything to keep the shared history and to read slow-path PDUs, but forwards updates **as received** (frames 10 and 11); the worker (`bulk.js`) keeps an identical history, decompresses, reassembles fast-path fragments and turns slow-path updates into the fast-path form. Both links carry compressed data. Virtual channels are opened without `CHANNEL_OPTION_COMPRESS_RDP`, so channel data is never compressed.
- **Graphics pipeline** ("Graphics" option, MS-RDPEGFX; never with RemoteApp, where each window would come on a surface of its own; AVC444 and AVC444v2 in full colour: each of their two streams on a decoder of its own, the pictures' planes read with `copyTo` and put back together as MS-RDPEGFX 3.3.8.3.2 lays them out, with its filter, in BT.709 full range, in the worker; the luma stream alone keeps the last chroma picture and the chroma one alone the last luma picture; a browser that gives no planes shows the luma picture as 4:2:0): in automatic mode `Client` turns it on (at 32 bpp) when the Windows version in the NTLM challenge is 6.3 or later. `Drdynvc` opens the `Microsoft::Windows::RDS::Graphics` channel, advertises capability sets 10.7 (no scaled mapping) and 8.1 with AVC420 only when the browser decodes H.264 (checked with `VideoDecoder.isConfigSupported`), and 8.0, and forwards every message untouched (frame type 9). The worker (`rdpgfx.js`) decompresses ZGFX, parses the PDUs and decodes: AVC420 with WebCodecs (the SPS is rewritten to declare BT.709 full range and no frame reordering, otherwise browsers assume limited range and may buffer frames), RemoteFX and RemoteFX progressive (`rfx.js`: RLGR1/3, dequantization, plain and reduce-extrapolate inverse DWT, upgrade passes; the tiles of a message go into one box around its rectangles, or, when the rectangles are sparse (the box would be over twice their area), into a box per rectangle (`#region`): two corners of the screen give 33 KB instead of 8.3 MB), ClearCodec (residual, bands with vBar caches, NSCodec/RLEX subcodecs; glyph cache kept with the surfaces), planar, uncompressed and alpha. Operations keep their order: those after an H.264 frame wait for the decoder. The main thread (`gfxsurfaces.js`) keeps one canvas per surface plus the surface cache, and copies mapped surfaces to the desktop canvas; an operation of several areas (a fill, copies, an H.264 frame) draws them all on the surface, an H.264 frame once through all its areas (each drawing of a frame converts the whole of it: 7 ms at 1920 × 1080 without a graphics card), then copies them to the desktop; a frame that cannot be drawn leaves its surface unclipped and is closed. Each end of frame is acknowledged (message type 10; only the latest pending one is sent), which gives the server its flow control. Requires 32 bpp (forced). Early capability flag (`earlyCapabilityFlags`) `RNS_UD_CS_SUPPORT_DYNVC_GFX_PROTOCOL` is set in the core data.
- Several screens: the remote desktop is drawn on an offscreen surface; each window (one per screen) copies its monitor region on the next animation frame, of this window or, while it is hidden (minimized, covered, another tab: a hidden page gets no frames), of a window of the session in view. A screen is a remote monitor only while its window is open (`RdpSession.setMonitors`, `#wanted`, `#checkMonitors`): the new layout goes as browser message type 13 (JSON `[[x,y,w,h,primary],…]`, checked by `Drdynvc::monitors`) in one Display Control layout, as a plain resize when one is left, or by reconnecting without Display Control; until the server takes it, that window is black and sends no input. Full screen asks `requestFullscreen({ screen })` and opens the other windows in the same click (`fullAndOthers`).
- Screenshot: `RdpSession.areaOf` maps the frame drawn over the canvas to desktop pixels; `capture` makes the PNG at full size, without toolbar or pointer.
- **Limits against corrupt or hostile data** (found with `tests/fuzz.mjs`), so that sizes taken from the data cannot make the browser allocate without bound:
  - Bitmaps (updates and cached ones) no larger than the desktop rounded up to whole 64x64 tiles, and of a valid depth: the gateway sends the desktop size (frame 2) before any update, so the limit is known in time.
  - Surfaces and the graphics output up to 32766 px a side, the RDP maximum: the desktop size is not a limit there, because a single surface may span all the monitors.
  - Each rectangle within its surface and each ClearCodec subcodec within its rectangle (as FreeRDP does); quantizer indexes checked in RemoteFX and progressive; the end of each NSCodec plane and an SPS in the last bytes of an H.264 unit are handled.
  - Still possible: a hostile server can make the browser hold surfaces of up to 4 times the output (at most the pixels of 8192 × 8192, 32766 a side), about 1 GB at worst; beyond that the browser fails with a logged error.

## Security model

- **Sign-in**:
  - First run: the administrator account can only be created with the one-time code of `data/setup-code.php` (behind `<?php exit; ?>`), so nobody can claim a freshly uploaded copy.
  - Passwords: bcrypt cost 12 (≈0.27 s), at least 12 characters, not one of the ≈30 000 common passwords of that length (`src/common-passwords.txt`), not containing the user name.
  - Brute force: failures counted per IP, per user name, per known browser and globally (all IPs). A locked IP is refused. A locked user name, or more global failures than `login_global_max` (a distributed attack), only lets in browsers where that user already signed in (signed *device cookie*, revoked when the password changes), so an attacker cannot lock the owner out. Each known browser has its own attempt count and lock; once it is locked the usual locks apply, so a stolen device cookie gives no more attempts than the per-user lock. The 20 browsers used most recently are kept (in the user's record); each new one is audited (`device_add`) and the user can forget them from the profile.
  - Every sign-in answer (password, TOTP, passkey) takes 1 s (waited until the second is over by `hrtime`: `usleep()` may wake early; one that works, more if checking the password and opening the data key take longer, as on a slow server: 0.9 to 1.2 s with PHP 8.1 and 8.2 on the test computer), except a locked IP's, answered at once (it says nothing about users), and wrong user, wrong password, disabled account and lock give the same message: no user enumeration by timing or text. Within that second the failures since the last sign-in are read from the audit log for the sign-in notice (at most 90 days back; worst case 73 ms, usually 5 ms).
  - Second factor (optional, or required by the administrator, who must have it first): TOTP (RFC 6238; each code is accepted once, also the one that turned it on) or a passkey. A user without one, once it is required, only reaches the profile until they add it.
  - **Passkeys** (WebAuthn, `WebAuthn.php` + `Cbor.php`, plain PHP + OpenSSL): ES256/RS256, user verification required, one-time challenges, origin and RP id checked, signature counter checked. With the PRF extension the passkey's secret (HKDF) wraps the data key, so it can replace the password; without PRF it is only a second step. Phishing-resistant: a passkey only works on its own site.
  - **Company accounts**. *OpenID Connect* (`Oidc.php`, `public/oidc.php`): authorization code flow with PKCE (S256), client_secret_post; the state, nonce and verifier kept in a cookie of their own (`MUDESKOIDC`, encrypted with the server key, `SameSite=Lax`, 10 minutes: the provider's redirect does not bring the Strict session cookie), used once; the provider's configuration and keys over HTTPS with certificate checks, kept an hour (`data/oidc.json`, fetched again for a new key id); the ID token's RS256/RS384/RS512 or ES256/ES384 signature, issuer, audience (and `azp` when there), times (`iat` required, all of them numbers; 2 min of skew) and nonce checked. The session has no data key, so saved RDP passwords are not opened, and the second step required by the administrator is the provider's. The account is the one linked to the provider's (`iss` and `sub`, in the user's `oidc`): made by its first sign-in, or linked by a local user from the profile (`oidc.link`: the flow carries who links, sealed in its cookie), never taken by the name alone; an administrator undoes a local user's link (`admin.user.oidc_unlink`: the user's `sv` goes up, so their web sessions end, and their remote ones too). *Windows accounts* (`WindowsLogin.php`): X.224 asking for NLA, TLS (the computer's certificate must be the one pinned when the administrator saved it, `ad_cert`: NTLM proves the password to whoever knows it, so a computer posing as the domain's would accept any), then CredSSP with NTLMv2 against the computer of the settings, stopped once the server has answered the client's key binding (`CredSsp::authenticate(..., delegate: false)`: the TSCredentials with the password are never sent); a dropped connection is a wrong password, as Windows does. A Windows user's data key is wrapped with the Windows password; when that changes, a new key is made and the saved RDP passwords are forgotten.
- Sessions: new id at sign-in, idle and absolute (12 h) limits (the request that closes an expired session answers `{"error":"auth","reason":…}`, also when it would fail the CSRF check, since the token went with the session; `session.left` tells how long is left without counting as activity; `state` returns `session: {idle, max}`, so the page asks `session.left` only when the session should end and then shows *Session expired* with the reason), bound to the browser (user agent: a stolen cookie fails in another browser and closes the session; the languages are not used because Web Workers may send different ones), and every other session of a user closes when the password changes (session version). The remote sessions opened from a web session end with it (signed out, expired or closed by the gateway: `Sessions::killWeb`, each registered with the sign-in's id `wid`); a password change ends those of the user's other sign-ins (`Sessions::killUser` keeping this `wid`), and the page says *signed out*; signing out in one tab tells the others of that browser (`BroadcastChannel`), which end theirs. A remote session checks every 15 s that its account still exists and is enabled. The password asked again inside a session (passkey or authenticator app added, password changed, second factor removed: `Auth::confirmPassword`) closes it after 5 wrong ones (`reason: reauth`); it does not touch the sign-in locks, which an attack on the user name could hold.
- Temporary passwords set by the administrator must be changed at the first sign-in.
- Remote passwords: AES-256-GCM with a per-user data key. The data key is wrapped with a key derived from the user's password (PBKDF2-SHA256 computed by OpenSSL, 400 000 iterations; a key wrapped with fewer, as up to 1.0.0, is wrapped again at the next sign-in with the password). During a session the data key is kept encrypted in the PHP session with a random key stored only in an HttpOnly cookie, so neither the session file nor the cookie alone reveals it. An administrator password reset makes saved remote passwords unreadable (they are removed).
- Web: CSRF token on every state-changing request, `SameSite=Strict` cookies, strict Content-Security-Policy (`'self'`, plus `data:`/`blob:` images, `blob:` frames and `blob:` media: a recording made in the page is played from its video read whole), `Permissions-Policy` denying the browser features the pages never use, `Cross-Origin-Resource-Policy: same-origin`, HSTS, HTTPS enforced, client IP allow-list. The API answers 400 `invalid_input` when a field carries a list or object instead of text or a number (`rdp.php` too), and 404 `not_found` for what does not exist. A JSON body is read up to 4 MB, as long as its `Content-Length` says (as the input's), and decoded once (413 `too_large` past it: PHP's `post_max_size` does not limit it, and an 8 MB list decoded twice before signing in took 150 MB). PHP's messages never reach the browser, even with `display_errors` on: they go to the server error log, and the visitor gets a page of ours (`ErrorPage.php`), without paths or traces; stack traces carry no arguments (`zend.exception_ignore_args`, passwords marked `#[\SensitiveParameter]`). Values of the address are read as text only (a list such as `p[]=x` is ignored). `files.php`, `rdp.php` and `api.php` (except `state`) refuse a request without a session cookie before a session file is made. Requests from 127.0.0.1 skip the HTTPS check unless that address is a trusted proxy, whose `X-Forwarded-Proto` then decides. Signing out sends `Clear-Site-Data: "cache"`. Items dragged between windows of the application carry a key of that browser (`localStorage`): another page cannot make a drop move files.
- **WebSocket service** (optional, `tools/ws-server.php`): it listens on 127.0.0.1 only and takes only connections whose `Origin` is the site's own (the scheme and `Host` the browser asked for); then the checks of HTTP, run by `rdp.php` itself: the session cookie and its CSRF token, the allowed clients and the limits, with the client's address taken from the last `X-Forwarded-For` hop only when the connection comes from this machine (127.0.0.1, ::1); the input with the session's token. A frame a browser never sends (unmasked, a reserved bit, an unknown opcode, a control frame fragmented or over 125 bytes, a message over 4 MB) ends the connection.
- RDP: target allow-list (IPs, CIDR, host names, `*.domain`), DNS resolved once and the checked address is the one used; a name that does not resolve is refused as a target not allowed. Names go through the system resolver (not one of its own, which would break the `hosts` file, search domains and Windows name resolution). With "Allow all", every address of the name is checked and the gateway never connects to itself (127.0.0.0/8, ::1), to link-local addresses (169.254.0.0/16, with the cloud metadata, and fe80::/10) or to 0.0.0.0/8 and ::, also as IPv4 inside IPv6 (::ffff:…, ::a.b.c.d, NAT64 64:ff9b::/96), nor to the other cloud metadata addresses (100.100.100.200, fd00:ec2::254); they can only be reached by listing them, and Administration warns while "Allow all" is set. In the list, a name rule (the name itself, or `*.domain`, which trusts the DNS of every name under it) reaches what it resolves to, but those addresses only when they are listed themselves too. Server certificate confirmed on first use: a computer or gateway never seen ends the connection with `cert_new` before anything of the user is sent (its SHA-256 and SHA-1 to the page); the user's `trust` on the next connection pins it, and a later change ends it with `cert_changed` (a manual connection's pin, not saved, for the user and that computer: `data/hosts/<uid>.json`). A fingerprint an administrator fixed for a computer (`Connections::fixCert`, `data/certs.json`: from the editor, or `trust_all` with the page's box) holds for every connection to it, by its name or by the address it resolves to (through a gateway by its name only; other fixed names resolved for 5 s at most): nobody is asked, another one ends it with `cert_unexpected` (no user's `trust` accepted; an administrator's `trust_all`, for the very fingerprint shown, puts a renewed one in its place), also on a computer a connection broker sends the session to (there no `trust_all`: renewed from the editor). `confirm_new_certificates: false` (`config.php`) trusts a new one at once; NLA public-key binding verified; a protocol the server picks that was not offered (RDSTLS, NLA extended) ends the connection. Standard RDP Security (Windows XP, Server 2003) only with the security *Automatic*: the server's key pinned as a certificate is (a computer pinned with TLS that now offers only this is a changed certificate), a key RSA cannot be trusted with refused, a server that encrypts nothing refused before the Client Info (`rdp_unencrypted`: the password would go in the clear), PDUs in the clear refused from the *Client Compatible* level up (but licensing), the encryption used in `rdp_start` (`rdp_security`); at the *Low* level what the server sends is not encrypted (see [SECURITY](../SECURITY.md)).
- Shared folder: one quota per user for the drive of all their sessions, the web file manager, clipboard files and print jobs (these two until their session ends). The counter (`files/<uid>.quota`) is changed under its own lock by every way of writing, so together they stay within the quota; it is counted again from the folder when the file manager is opened or refreshed with no session of the user running, walked outside the counter's lock; any other list of a folder shows the counter, without walking the folder (that took 7 to 17 s with 20,000 files) (opening the drive with 3000 files went from 205–238 ms to 0.2–1.4 ms). Names over 255 bytes and Windows device names (CON, NUL, COM1, LPT¹, CONIN$… with any extension) are refused (400 `invalid_path`).
- File manager (`files.php`): every path goes through `Files::clean` (no `..`, no configuration file names) and must stay inside the user's folder once links are followed (`Files::confined`, also for the remote drive): nothing of MuDeskClient makes a link, but one put there by something else (a restored backup, a program on the server; a symbolic link, or a Windows junction, which `is_link()` misses) is never followed, and walks of a folder (deleting it, its ZIP, the quota) never go into one (`Files::isLink`). Moves and renames stay inside the user's folder, never over something and never a folder into itself. The tree reads only the open folders (walking every folder took 2.4 s with 1,000 folders and 20,000 files on Windows; the open ones, 64 ms). Actions: `list` (with the quota), `tree` (up to 200 open folders), `move`, `mkdir`, `mkdirs` (up to 1000), `upload`, `delete`, `download` (`view=1`: thumbnails), `zip` (`check=1` first, with the names in the body, up to 10,000, CSRF checked; the answer's id downloads it, `z=`, kept in the session). `delete` and `move` wait for an upload chunk still being written (with `move`, a file uploaded meanwhile to its destination was replaced), as clipboard files do. Several items or a folder download as a ZIP written while it is sent (`ZipStream`: stored, each file's CRC read just before it, so the length is known first and there are no data descriptors; no temporary copy; up to 4 GB and 65,535 entries and 64 folders deep, else `too_big`, asked first by the page). Thumbnails are served only for bitmap types, inline with `Content-Security-Policy: default-src 'none'; sandbox` (never SVG or HTML), revalidated each time (`Cache-Control: private, no-cache`, `Last-Modified`, 304). Printed documents (MuDeskPDF, made by the remote computer) are sent with the same policy and as a download.
- Data: `data/` outside the web root, or inside it denied by `.htaccess`/`web.config` (rewritten if missing); while it can be read from the web nothing works (`Exposure`, below); server key in an exiting PHP file; files written atomically with locks. A damaged or empty data file, or one that is no JSON object or list (`null`), stops with an error naming it (an empty `users.json` is never taken for a first run); only the failed sign-ins (`ratelimit.json`) start again, the damaged file kept aside. The last enabled administrator and unique user names are checked under the users' lock, and a TOTP step is taken under it (two sign-ins with the same code at once both passed). Settings are saved as what each request changes, written onto those stored under their lock (two administrators saving at once lost one's change).
- Audit: one JSON line per event in a file per day; each line carries the HMAC (server key) of its content and the previous line's, so edits, insertions and removals are detected by *Verify integrity* (purged days are expected at the start). The check ends where the log was when it started (days, size of the newest file and its last line, taken under the writers' lock), so lines written meanwhile are left for the next one. Contents and passwords are never logged. The export (up to 20 000 rows) is streamed row by row, each row as stored (about 20 MB of memory instead of about 71 MB). The JSON export is signed with an RSA 3072 server key (`data/audit-key.php`, made once on the first JSON export or when its panel is opened): the SHA-256 is computed piece by piece while the file goes out, with no copy, and signed at the end with PKCS#1 v1.5, which `openssl dgst -sha256 -verify` checks. RSA allows signing a hash computed that way; measured: 0.21–0.23 s for 20 000 rows (0.32–0.36 s for the unsigned export before), 19–20 MB. Writing costs about 0.13 ms per event (lock + append). Refused requests of someone not signed in are written at most 100 times an hour per address and 5,000 in all (`Audit::anonymous`, then one `audit_limited` line). Days are read a line at a time, backwards in 1 MB blocks (a day of 60 MB: 3.7 MB of memory instead of 128 MB); *Verify integrity* lists the first 1,000 problems and counts them all. Search reads the days in range newest first and decodes only the rows shown (measured with 2 000 events/day: 90 days in about 0.1 s, a year in about 0.4 s, 4 MB of memory; verifying a year, 3.4 s).
- **Connections of the administrator** (`Connections::saveManaged`): given to users who cannot change or delete them. The administrator never sets or reads a user's password (encrypted with the user's key); when the target of a connection changes (host, port, user, domain, security, gateway), the passwords users saved for it and its pinned certificate are dropped, also for a user's own connection changed by the administrator, so that a password typed for one server never reaches another.
- **Limits on what a hostile or broken RDP server can make the gateway or the page hold**:
  - Gateway: a channel message up to 64 MB with the length its first chunk announced; dynamic channel messages up to 64 MB, 8 being joined at a time; XCRUSH history reset only when full; the socket read 4 MB at a time and a write not finished within 30 s (or 15 s without being writable) ending the connection; a desktop up to 32766 a side and 8192 × 8192 pixels; the remote clipboard kept up to 16 MB; print jobs up to 200 MB a session; the drive: 1,024 open handles (64 open files), 20,000 new entries and 2,000 audit lines a session, masks with more than 4 `*` match nothing; drive reads and writes at offsets of 2^63 or more, or ending past it, refused; NCRUSH literals past its 64 KB history refused (as the page refuses them); audio formats only those the page plays (1 or 2 channels, 8–192 kHz, IMA ADPCM blocks of whole groups); messages waiting for a session up to 16 MB; diagnostic traces up to 256 MB in all; the microphone only as 16-bit PCM of 1 or 2 channels at 8–48 kHz, in packets of 10 ms to a second whatever the server asks (one frame a packet made two messages for every 2 bytes), with at most a second of audio waiting, a Format Change before the Open left out (it had no packet size: an endless loop); a Remote Desktop Gateway's HTTP headers within 64 KB and bodies up to 1 MB, 8 of its service messages kept; through the RPC transport, a call's answer up to 1 MB and only for the calls waited for, a new OUT channel's HTTP answer within 64 KB; a broker's redirection fields read up to their first null (a pattern on a long run of zeros gave up); the camera's pictures up to 2 MB each (only the newest kept), 64 Sample Requests waiting at most; this computer's folder: 4,096 requests waiting for the browser (its change notifications apart, as many), each path kept for the audit up to 1,024 characters, its listings within the 200,000 names and 32 MB kept.
  - Page: ZGFX one buffer of the declared size (up to 64 MB); the graphics pipeline's surfaces within 4 times the output, its bitmap cache within 100 MB with each slot inside its surface, ClearCodec glyphs as the codec allows them; drawing-order bitmap caches within the cells offered (600, 600 and 1,024 entries of 256, 1,024 and 4,096 pixels); a desktop over 32766 a side or 8192 × 8192 pixels not taken; clipboard images whose header claims more than they bring (row lengths counted without 32-bit overflow) and remote file chunks past their size refused; a ZIP of remote files up to 65,535 entries and 4 GB (its limits without ZIP64); stream frames up to 128 MB, their length read unsigned (a length of −5 made the worker loop for ever); audio chunks of a format it cannot play and bitmaps or rectangles of no size dropped, never thrown.

### Status, backups and the data folder

- **Status** (`Status::now`, `admin.status`, administrators and auditors): the sessions running and their limit, guests (each session's `viewers`, written when it changes) and recordings, the PHP processes they take, the memory each session's process notes once a minute (`Sessions::report`: `mem`, `mem_peak`; nothing else is taken) against `memory_limit`, the disk of the data folder and what `recordings/` takes, yesterday's and today's failed sign-ins, sessions ended by an error, certificates that did not match and access refused (from the audit), the last housekeeping and the server. **Last 30 days** (`Status::usage`, `admin.usage`): the audit's `rdp_start` (the computer) and `rdp_end` (when and how long) of 30 days and the sessions running, a day's sessions, hours and most at once (its spans swept), and the computers by hours; an attempt that never started (an end without its start) counts for nothing. The page draws them as SVG made of nodes. `health.php`: `Status::problem` only (`ok`, or 503 `data`, `store`); before it, as every entry point, `Http::guard` (503 `data_exposed`, `restoring`).
- **Backup** (`Backup`, `backup.php`, `admin.backup.prepare` / `admin.backup.restore`, administrators): the stores of the data folder that last (users, settings, connections, hosts, certificates, OpenID Connect, the audit, `secret.php` and `audit-key.php`; `files/` (each user's folder whole, whatever its files are called; not the quota counters, counted again) and `recordings/` when asked; never `run/`, `sessions/`, `tmp/`, `trace/`, the gateway's locks and unfinished writes, `ratelimit.json`, `auditlimit.json`, `tls.json`). The file: `MUDESKBK1`, a salt, the PBKDF2 rounds (400,000, SHA-256); chunks of 1 MB of AES-256-GCM, each authenticated with its number and whether it is the last; inside, a manifest and the records (name, size, bytes). Prepared with its password (its key, not the password, kept in the web session for one download, sealed with the browser's key cookie, `Auth::seal`; a file the server cannot read is said then, `backup_unreadable`), written as it is sent, each file from what is read of it (one gone meanwhile left out; one that cannot be read, or grows shorter while it is read, ends the backup without its last chunk: refused whole when restored). Restored: sent in pieces (`backup.php?a=upload`, into `tmp/restore-<id>.mudeskbackup`; 8 MB each at most, `backup_piece`, and none that would leave less than 512 MB free, `backup_space`), read whole into `tmp/restore-<id>/` (its files only for the server's account; a name out of the data folder, a cut, a change: refused; a backup of a newer major or minor version too; a file it cannot write, the disk full: `backup_restore`), then, with `run/restoring` up (every request 503 `restoring`; `Config::load` does not make again the folders being moved), every session ended and each item renamed into place: the stores as in the backup (one it does not have goes too), `files/` and `recordings/` only when it carries them. The old ones go aside, removed at the end; if a move fails they go back (`backup_restore`), and what cannot go back is never removed: kept in `restore-kept-<when>` in the data folder, named in the server's log (`backup_kept`). Then the web sessions are removed and the server key and settings read again.
- **The data folder readable from the web** (`Exposure`, called by `Http::guard`): the server asks itself (the address and port the request came to, its Host, and its script's folder from `SCRIPT_NAME`, never a path the client adds after it) for `data/web-check.txt` beside the page and one folder above, every 10 minutes while it is not readable, every 30 s while it is (`run/exposure.json`); where it was found readable is kept and asked again with each request's (another site's Host, or another path, never finds it protected alone); each time the file gets a new random code. Where it cannot (PHP's built-in server: one request at a time; a new code every 10 minutes), the page's browser reads it (`datacheck.js`) and sends what it read (`data.exposed`): only the file's code now stops it, for 5 minutes, read again then. While stopped, every request answers 503 `data_exposed`.

## Data layout (`data/`)

```
users.json                 accounts (hashes, wrapped data keys, TOTP seeds encrypted with the server key, passkeys,
                           known browsers)
settings.json              administrator settings
connections/<uid>.json     connections of each user; under an id starting with "m", what the user keeps of a connection of
                           the administrator (their password, certificate and connect options)
managed_connections.json   connections of the administrator, each with its users (ids, or "*": every user)
hosts/<uid>.json           certificates of the computers each user reached with manual connections (those are never saved:
                           kept in the web session, ids starting with "o", only for whoever may make connections)
oidc.json                  the OpenID Connect provider's configuration and keys (kept an hour)
certs.json                 certificates an administrator fixed for every connection to a computer ("rdp:host:port")
secret.php                 server key (TOTP seeds, the audit chain's HMAC, trusted-browser cookies), behind
                           <?php exit; ?>
audit-key.php              RSA key of the signed audit exports, behind <?php exit; ?>
.htaccess, web.config,     deny web access (Apache/LiteSpeed/OpenLiteSpeed and IIS;
index.html                 written again if missing)
setup-code.php             one-time code for the first run (deleted once the administrator exists; another one after a day)
web-check.txt              read by the server itself and by the browsers to find an exposed folder (a random code that changes)
ratelimit.json             failed logins
tls.json                   how TLS went with each computer and gateway ("modern": TLS 1.2 seen, never less for a year;
                           "legacy": TLS 1.0 only, offered at once for a day)
restore-kept-<when>        what a failed restore could not put back (never removed: see the server's log)
run/maintenance            the last hourly housekeeping (Maintenance; run/maintenance.lock while it runs)
auditlimit.json            refused requests of visitors not signed in, counted per hour
*.json.lock                lock of each JSON store
audit/YYYY-MM-DD.jsonl     audit log, one file per day (.last: hash of the last line; .lock)
sessions/                  PHP sessions
run/                       running RDP sessions (registry, sockets, queues, register.lock); exposure.json: whether the data folder
                           can be read from the web; restoring: a backup being put in place
tmp/<sid>/                 clipboard uploads and print jobs of a session (removed at the end)
tmp/restore-<id>*          a backup sent to be restored and read (removed with the restore, or after an hour; restore-old-*, the data a restore set aside, never by itself)
tmp/upload-<uid>.lock      the user's uploads, moves, deletions and clipboard files, one at a time
tmp/upload-<uid>.parts     files an upload is replacing (their part, beside them, removed after a day if left half way)
trace/<sid>.log            diagnostic traces (removed after 7 days)
recordings/<id>.rec        session recordings, encrypted (<id>.json: who, connection, session, who started and stopped it,
                           times, size, sound, largest desktop); the id is the session's for a connection always recorded,
                           its own for one started in the session (its video, as the page made
                           it); kept until deleted by hand, or the days of the settings
files/<uid>/               shared folder of each user
files/<uid>.quota          bytes counted against the user's quota
```
