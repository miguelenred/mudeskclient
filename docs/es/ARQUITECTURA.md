# Arquitectura

[English](../ARCHITECTURE.md)

## Objetivos y restricciones

- Escritorio remoto (RDP) en el navegador **sin instalar nada en los equipos remotos**.
- Navegador: solo HTML, CSS y JavaScript (módulos ES, sin librerías).
- Servidor: **PHP puro 8.1 – 8.5**, solo las extensiones `openssl` y `session` que trae PHP de serie, sin dependencias de Composer ni base de datos (ficheros JSON).
- Debe funcionar en **hosting compartido**: sin demonios, sin puertos propios, sin WebSocket.

## Visión general

```
Navegador                                   Servidor web (PHP)                        Equipo remoto
┌──────────────────────────┐   HTTPS   ┌──────────────────────────────┐   TCP/TLS  ┌───────────────┐
│ app.js (interfaz)        │◀────────▶│ api.php   usuarios, conexiones│            │               │
│ session.js (entrada)     │           │ files.php carpeta compartida │            │  Windows /    │
│ stream-worker.js ────────┼──────────▶│ rdp.php?a=stream  ───────────┼──────────▶│  servidor RDP │
│   gfx.js / orders.js     │◀─ tramas ─┤   (una petición larga = una  │◀──────────┤  3389         │
│ audio.js, mic.js, clip…  │           │    sesión RDP, src/Rdp/*)    │            │               │
│        entrada ──────────┼──────────▶│ rdp.php?a=send (cortas, IPC) │            └───────────────┘
└──────────────────────────┘           └──────────────────────────────┘
```

`index.php` pide `app.js` y `app.css` con `?v=<versión>-<huella>`: `Http::build` calcula un hash de los nombres, tamaños y fechas de los scripts y estilos de `public/assets`, así que una actualización cambia la dirección aunque no cambie el número de versión. La misma huella va en `data-build` de `<html>` y en la respuesta de `state` (`build`): una página más antigua que la pasarela lo dice y ofrece recargar cuando pide el estado (al empezar y al entrar; no en cada petición, porque la huella cuesta unos 0,8 ms).

### Por qué una petición HTTP larga por sesión

Una petición PHP normal termina al responder, y la conexión RDP debe seguir abierta toda la sesión. Un hosting compartido no permite procesos en segundo plano ni WebSocket, así que cada sesión es **una petición HTTP que no termina**: `rdp.php?a=stream` abre la conexión RDP y envía tramas binarias al navegador (`fetch` + `ReadableStream`). Si el hosting corta la petición, el navegador reconecta solo y la sesión de Windows sigue viva.

Formato de trama (servidor → navegador): `[u8 tipo][u32 longitud][datos]`

| Tipo | Contenido |
|---|---|
| 0 | relleno (hace que algunos proxies empiecen a reenviar) |
| 1 | actualización RDP: `u8 código fast-path` + datos (mapas de bits, paleta, punteros, órdenes de dibujo) |
| 2 | tamaño del escritorio: `u16 ancho, u16 alto, u8 bits` |
| 3 | JSON de estado (`token`, `connected`, `end`, `errorInfo`…) |
| 4 | subprotocolo de portapapeles (`Cliprdr`) |
| 5 | Display Control disponible (resolución dinámica) |
| 6 | mantener viva la conexión |
| 7 | subprotocolo de audio (`Rdpsnd`) |
| 8 | JSON de trabajo de impresión (`Rdpdr`, MuDeskPDF) |
| 9 | mensaje del canal gráfico (RDPGFX, se decodifica en el navegador) |
| 10 | con compresión: actualización fast-path tal como llega: `u8 código, u8 fragmentación, u8 indicadores de compresión` + datos |
| 11 | con compresión: PDU de datos lenta tal como llega: `u8 indicadores de compresión, u8 pduType2` + datos |
| 12 | RemoteApp: JSON sobre las ventanas del programa que no viene con las órdenes de dibujo (una ventana ocultada o mostrada de nuevo) |
| 13 | micrófono: `u8 1, u32 frecuencia, u8 canales` (un programa del equipo remoto graba: enviar PCM de 16 bits así) o `u8 0` (parar y soltar el micrófono) |

Mensajes del navegador (`rdp.php?a=send`, tras un número de secuencia `u32`: `u8 tipo` + datos):

| Tipo | Contenido |
|---|---|
| 1 | eventos de entrada (teclado, ratón, Unicode) |
| 2 | cambio de tamaño: `u16 ancho, u16 alto` |
| 3 | página visible u oculta |
| 4 | subprotocolo del portapapeles (`Cliprdr`) |
| 5 | salir |
| 6 | refrescar: el servidor lo dibuja todo de nuevo |
| 7 | texto escrito: caracteres con sus pausas |
| 8 | varios caracteres de golpe (UTF-8): se pegan con «Teclado del móvil por portapapeles», si no se escriben |
| 9 | reservado (terminar una sesión desde la pasarela): rechazado desde el navegador |
| 10 | confirmación de fotograma del canal gráfico |
| 11 | nota de diagnóstico del navegador (modo diagnóstico) |
| 12 | un texto del historial del portapapeles (UTF-8), siempre pegado (con el portapapeles activado) |
| 13 | varios monitores, cada uno del tamaño de su ventana (JSON) |
| 14 | orden de RemoteApp (JSON, ver más abajo) |
| 15 | audio del micrófono: PCM de 16 bits en el formato de la trama 13 (unos 100 ms cada uno; mientras uno espera a enviarse el siguiente se le une, como mucho un segundo, quitando el más antiguo) |

Además del flujo y de estos mensajes, `rdp.php?a=clipfile` recibe por trozos los archivos e imágenes del portapapeles (en `tmp/<sid>/`, contados en la cuota) y `rdp.php?a=print` entrega un trabajo de impresión.

### Admisión de sesiones y tiempos límite

- Cada sesión ocupa un proceso PHP mientras dura, así que el número de sesiones se limita por usuario y entre todos los usuarios (`max_sessions_total`, 20 por defecto). Antes de enviar nada, `rdp.php` cuenta las sesiones en marcha y registra la nueva bajo un mismo bloqueo (`data/run/register.lock`), así dos peticiones a la vez no pueden quedarse las dos con la última plaza. Una pasarela llena responde al momento 503 `busy`, antes de abrir ningún socket.
- Cada paso del saludo (TCP, TLS, X.224, NLA, MCS) espera como mucho 8 s; la activación, 30 s. Si el navegador se cierra mientras se conecta, el proceso PHP se libera en 1–2 s.
- El nombre del destino se resuelve después de la admisión, así que el límite global también acota los procesos que esperan a un servidor DNS lento (ver [HOSTING](HOSTING.md#nombres-de-equipo-dns)).

### Entrada (navegador → servidor)

Teclado, ratón, portapapeles y cambios de tamaño viajan en **peticiones POST cortas** a `rdp.php?a=send`:

- No abren la sesión PHP (ni bloqueo del fichero de sesión ni lectura de usuarios): se autorizan con un **token aleatorio por sesión** que llega en la primera trama de estado y viaja en la cabecera `X-MuDesk-Token` (no en la URL, para que no quede en los registros del servidor web). El fichero de la sesión en `data/run/` guarda solo su SHA-256: una copia de la carpeta de datos no da a nadie el teclado de una sesión abierta.
- Cada mensaje lleva un número de secuencia `u32`. El navegador mantiene **hasta 4 peticiones en paralelo** y el proceso de la sesión las reordena (los huecos de más de 0,5 s se saltan).
- Los movimientos de ratón se agrupan mientras hay peticiones en curso (de los eventos agrupados por el navegador solo se sitúa el último). Los movimientos y las confirmaciones de fotogramas del canal gráfico ocupan como mucho 3 de las 4 plazas y se turnan, así una confirmación nunca se queda atrás por un ratón en movimiento (Windows regula sus fotogramas con ellas) y una tecla o un clic siempre tiene plaza.
- El **texto tecleado** (teclados en pantalla, IME, autocorrección) sigue el orden del resto de la entrada en una cola de la pasarela (`Client::input`):
  - Un carácter suelto (mensaje de tipo 7) va como Unicode y lo que llega detrás espera 100 ms; la pausa se aplica en la pasarela porque las peticiones HTTP llegan con separaciones desiguales.
  - Varios caracteres de golpe (mensaje de tipo 8, UTF-8), con la opción «Teclado del móvil por portapapeles», se **pegan** (`Client::pasteText`, `Cliprdr::typeText`; motivo y pruebas en [TECLADO-MOVIL](TECLADO-MOVIL.md)). Los textos seguidos se unen. Si lo último se copió en Windows, se lee antes (todos sus formatos, hasta 16 MB) para reponerlo; con archivos o más de 16 MB el texto se escribe. La pasarela anuncia el texto (con los formatos que lo excluyen del historial y de la nube), espera la respuesta a *ese* anuncio (Windows responde a cada lista en orden) y a que la pantalla cambie tras la última entrada enviada, pulsa Ctrl y V y las mantiene hasta que la aplicación pide el texto, lo entrega, las suelta y repone el portapapeles justo después de cada pegado (un texto vacío si no había nada copiado). Windows confirma un anuncio antes de aplicarlo y no aplicaba una lista igual a la que tenía (dos pegados seguidos volvían a pegar el texto anterior), así que cada lista anunciada lleva un formato propio que alterna: dos listas seguidas nunca son iguales. Sin la opción, el texto se escribe como Unicode.
  - Un texto del historial del portapapeles (mensaje de tipo 12, UTF-8, hasta 1 MB) se pega siempre así, tenga o no la opción (con el portapapeles activado).
  - La entrada que espera detrás de un pegado sale cuando la pantalla cambia (la aplicación ha dibujado lo pegado).
  - Límites solo para cuando Windows no responde: 2 s para la respuesta al anuncio y para el cambio de pantalla, 10 s para que la aplicación pida el texto; entonces se escribe como Unicode.
- RemoteApp (mensaje de tipo 14, JSON): el escritorio sincronizado (`ready`: el servidor ha mandado todas sus ventanas, con cuántas hay abiertas, y ya se puede pedir el programa), una ventana traída al frente (`activate`), minimizada, maximizada, restaurada o cerrada (`sys`, solo con una de esas cuatro órdenes).
- La petición corta entrega el mensaje a la larga por un **socket Unix** en `data/run/` (o en la carpeta temporal del sistema si esa ruta llega a 100 caracteres); en Windows, que no tiene sockets Unix para PHP, por un **puerto TCP solo de este equipo** (127.0.0.1), con cada mensaje empezando por un secreto de la sesión guardado en su fichero de modo (a un puerto así puede conectarse cualquier proceso local); sin `stream_socket_server` o con `'ipc' => 'file'`, por un fichero de cola que se revisa cada 20 ms (Windows lo usaba antes: cada tecla, movimiento del ratón y confirmación de fotograma esperaba hasta 20 ms). Cada petición es una conexión al socket con un mensaje, que se guarda aparte hasta que ha llegado entero: añadido a un único búfer según llegaba, un mensaje grande (un pegado) que llegaba en trozos quedaba mezclado con los de las otras peticiones, y la entrada de la sesión dejaba de funcionar.

### Pantalla

- El flujo se lee y decodifica en un **Web Worker** (`stream-worker.js`), así la entrada nunca espera al dibujado.
- Decodificadores (`gfx.js`): RLE entrelazado (8/15/16/24 bits), planar (32 bits), sin comprimir, paletas y punteros (color, nuevo, grande). Los píxeles de 15/16 bits usan tablas precalculadas.
- Los rectángulos decodificados se transfieren al hilo principal (`postMessage` con búferes transferibles) y se pintan con `putImageData`.
- Las órdenes de dibujo (`orders.js`: DstBlt, PatBlt, OpaqueRect, ScrBlt, MemBlt) y la **caché de mapas de bits** (revisión 2, tres celdas de 600/600/1024 entradas: las órdenes secundarias *cache bitmap v2* guardan mapas de bits ya decodificados y MemBlt los pinta) se analizan en el worker y se ejecutan en el canvas; los mapas de bits guardados viven en el hilo principal como canvas pequeños. Activadas por defecto (`drawing_orders`): validadas píxel a píxel contra xrdp y Windows 11. MemBlt y PatBlt admiten cualquier ROP: las copias simples (SRCCOPY, PATCOPY) las pinta el canvas, y las demás se hacen píxel a píxel en el hilo principal (`drawRop` lee el rectángulo y `rop3` calcula cada bit a partir del pincel, el origen y el destino; PATINVERT hace XOR con el color o el patrón del pincel). Mem3Blt no se negocia (Windows manda mapas de bits en su lugar), así que un MemBlt cuyo ROP use pincel toma el pincel blanco por defecto de GDI. **Texto** (mismo ajuste): GlyphIndex, FastIndex y FastGlyph con la caché de glifos (Cache Glyph revisión 2, que los servidores envían como orden de tipo 3 con el nivel de soporte «encode»; diez cachés) y la caché de 256 fragmentos. El worker guarda el tamaño de los glifos y calcula las posiciones (desplazamientos, paso fijo, fragmentos); el hilo principal convierte una vez cada glifo de 1 bit en un `Path2D` con sus tramos de píxeles y lo rellena con el color del texto, recortado al rectángulo de fondo (primero se rellena el rectángulo opaco con el campo *foreground* de la orden y el texto usa el campo *background*, como lo define RDP). Comprobado con órdenes construidas a mano (`tests/orders_unit.mjs`), al píxel en Chrome y Firefox (`tests/e2e_glyphs.mjs`) y con las órdenes de texto reales de la ventana de acceso de xrdp: el texto sale idéntico a la versión en mapas de bits a 16 y 32 bits. PatBlt pinta pinceles de patrón 8x8 y tramados (PATCOPY; un bit a 1 toma el color de fondo, como en GDI). Los colores de las órdenes a 24/32 bits son bytes rojo, verde, azul. Las cachés de pinceles y tablas de color no se negocian y se saltan por su longitud.
- **Compresión** (`bulk_compression`, activada por defecto, `'rdp61'`): el cliente ofrece hasta RDP 6.1 y el servidor elige para cada bloque un tipo no superior: MPPC con historial de 64 KB («RDP 5», `Mppc.php`, el que usa xrdp), NCRUSH («RDP 6.0», `Ncrush.php`: literales con códigos Huffman, desplazamientos con caché de 4 entradas, historial de 64 KB; las tablas de decodificación se generan a partir de los códigos de MS-RDPEGDI) o XCRUSH («RDP 6.1», `Xcrush.php`: un MPPC interior sobre un nivel que copia coincidencias de un historial de 2.000.000 de bytes; Windows Vista SP1/Server 2008 y posteriores). `Bulk.php` elige por el tipo de cada bloque y crea cada historial la primera vez que se usa. Medido con los mismos 11,1 MB de actualizaciones de pantalla de xrdp comprimidos con los compresores de FreeRDP: MPPC 3,05 MB y 0,53 s de CPU de la pasarela, NCRUSH 4,85 MB y 0,93 s, XCRUSH 2,08 MB y 0,32 s; navegador 0,09/0,18/0,06 s. XCRUSH necesita unos 4 MB más de memoria en la pasarela y 2 MB en el navegador. La pasarela lo descomprime para mantener el historial común y leer las PDU lentas, pero reenvía las actualizaciones **tal como llegan** (tramas 10 y 11); el worker (`bulk.js`) lleva un historial idéntico, descomprime, une los fragmentos fast-path y pasa las actualizaciones lentas a la forma fast-path. Por los dos tramos viajan datos comprimidos. Los canales virtuales se abren sin `CHANNEL_OPTION_COMPRESS_RDP`, así sus datos nunca llegan comprimidos.
- **Canal gráfico** (opción «Gráficos», MS-RDPEGFX; nunca con RemoteApp, donde cada ventana llegaría en una superficie propia; AVC444 y AVC444v2 se muestran a partir de su flujo 4:2:0): en modo automático `Client` lo activa (a 32 bits) si la versión de Windows del desafío NTLM es 6.3 o posterior. `Drdynvc` abre el canal `Microsoft::Windows::RDS::Graphics`, anuncia las capacidades 10.7 (sin mapeo escalado) y 8.1 con AVC420 solo si el navegador decodifica H.264 (comprobado con `VideoDecoder.isConfigSupported`), y 8.0, y reenvía cada mensaje sin tocarlo (trama de tipo 9). El worker (`rdpgfx.js`) descomprime ZGFX, analiza las PDU y decodifica: AVC420 con WebCodecs (se reescribe el SPS para declarar BT.709 de rango completo y sin reordenación de fotogramas; si no, los navegadores suponen rango limitado y pueden retener fotogramas), RemoteFX y RemoteFX progresivo (`rfx.js`: RLGR1/3, decuantificación, DWT inversa normal y «reduce-extrapolate», pasadas de mejora; las teselas de un mensaje van a una caja que abarca sus rectángulos o, si los rectángulos están dispersos (la caja ocuparía más del doble de su área), a una caja por rectángulo (`#region`): dos esquinas de la pantalla ocupan 33 KB en vez de 8,3 MB), ClearCodec (residual, bandas con cachés de barras, subcódecs NSCodec/RLEX; la caché de glifos vive con las superficies), planar, sin comprimir y alfa. Las operaciones mantienen su orden: las que siguen a un fotograma H.264 esperan al decodificador. El hilo principal (`gfxsurfaces.js`) tiene un canvas por superficie y la caché de superficies, y copia las superficies asignadas al canvas del escritorio. Cada fin de fotograma se confirma (mensaje de tipo 10; solo se envía la última confirmación pendiente), que es el control de flujo del servidor. Requiere 32 bits (se fuerza). En los datos core se activa `RNS_UD_CS_SUPPORT_DYNVC_GFX_PROTOCOL`.
- Varias pantallas: el escritorio remoto se dibuja en una superficie fuera de pantalla y cada ventana (una por pantalla) copia la región de su monitor en el siguiente fotograma. Una pantalla es monitor remoto solo mientras su ventana está abierta (`RdpSession.setMonitors`, `#wanted`, `#checkMonitors`): la nueva disposición va como mensaje del navegador de tipo 13 (JSON `[[x,y,an,al,principal],…]`, comprobado por `Drdynvc::monitors`) en una sola disposición de Display Control, como cambio de tamaño normal si queda una, o reconectando sin Display Control; hasta que el servidor la acepta, esa ventana sale en negro y no envía entrada. Pantalla completa pide `requestFullscreen({ screen })` y abre las demás ventanas en el mismo clic (`fullAndOthers`).
- Captura: `RdpSession.areaOf` pasa el recuadro dibujado sobre el canvas a píxeles del escritorio; `capture` hace el PNG a tamaño real, sin barra ni puntero.
- **Límites ante datos corruptos u hostiles** (encontrados con `tests/fuzz.mjs`), para que un tamaño tomado de los datos no haga reservar memoria sin límite al navegador:
  - Mapas de bits (actualizaciones y los guardados en caché) no mayores que el escritorio redondeado a teselas enteras de 64x64, y con una profundidad válida: la pasarela envía el tamaño del escritorio (trama 2) antes de cualquier actualización, así que el límite se conoce a tiempo.
  - Superficies y salida gráfica de hasta 32766 px por lado, el máximo de RDP: ahí el tamaño del escritorio no sirve de límite, porque una sola superficie puede abarcar todos los monitores.
  - Cada rectángulo dentro de su superficie y cada subcódec de ClearCodec dentro de su rectángulo (como hace FreeRDP); índices de cuantizador comprobados en RemoteFX y progresivo; se controlan el final de cada plano de NSCodec y un SPS en los últimos bytes de un bloque H.264.
  - Aún posible: un servidor hostil puede hacer que el navegador guarde superficies de hasta 4 veces la salida (como mucho 8192 × 8192), en el peor caso 1 GB; por encima, el navegador falla con un error registrado.

## Implementación RDP (`src/Rdp/`)

| Clase | Función |
|---|---|
| `Transport` | TCP + TLS (cualquier versión, admite autofirmados), `TCP_NODELAY`, tramas (TPKT, fast-path, DER) |
| `Client` | negociación X.224, MCS/GCC (bloques core, seguridad, red y monitores), Client Info, licencias, Demand/Confirm Active, finalización, entrada/salida fast-path, canales virtuales estáticos, reactivación; RemoteApp pedido (`INFO_RAIL`, conjuntos de capacidades 23 y 24; un servidor sin ella termina la sesión con `app_unsupported`) |
| `CredSsp` + `Ntlm` + `Rc4` + `Der` | NLA: CredSSP v6 con NTLMv2, MIC, seguridad de sesión y comprobación de la clave pública; con `.\usuario` el nombre NetBIOS del servidor se toma del desafío NTLM; el nombre de usuario en mayúsculas con la tabla del propio Windows (sacada de Windows 11: las 973 letras de todos los alfabetos que cambia, y ninguna de las que deja) |
| `Licensing` | intercambio de licencias RDS (MS-RDPELE): RSA y desafío de plataforma |
| `Drdynvc` | canales dinámicos; Display Control (MS-RDPEDISP) para cambiar la resolución; canal gráfico (se reenvía al navegador y vuelven las confirmaciones de fotograma); el `AUDIO_INPUT` del micrófono (solo con la opción); un mensaje que no cabe en un trozo de canal de 1600 bytes (1598 bytes con un id de canal menor que 256) va como PDU Data First + Data |
| `Cliprdr` | portapapeles (MS-RDPECLIP): texto, texto con formato («HTML Format»: el navegador convierte entre HTML y CF_HTML, la pasarela solo reenvía los bytes), imágenes DIB y archivos (FileGroupDescriptorW / FileContents) |
| `Rdpdr` | redirección de dispositivos (MS-RDPEFS/RDPEPC): la unidad de la carpeta compartida («Carpeta compartida en MuDesk», en el idioma de la página) y la impresora MuDeskPDF |
| `Rdpsnd` | salida de audio (MS-RDPEA): IMA ADPCM, A-law, μ-law, PCM |
| `Audin` | micrófono (MS-RDPEAI, canal dinámico `AUDIO_INPUT`; `INFO_AUDIOCAPTURE` en el Client Info): Windows abre el canal cuando un programa graba allí y lo cierra cuando ninguno lo hace. La pasarela contesta ella misma la negociación, al momento (Windows espera como mucho 5 s cada respuesta, menos de lo que el navegador puede tardar en tener permiso para el micrófono): versión 1 (la 2 solo cambia AAC), los formatos que acepta (PCM de 16 bits, 1 o 2 canales, 8–48 kHz: mono primero, la frecuencia más alta primero), la apertura (el formato inicial confirmado con un Format Change PDU y después el éxito) y los cambios de formato posteriores. Al navegador se le dice el formato (trama 13) y envía PCM (mensaje 15); la pasarela lo envía en paquetes del tamaño que pidió Windows (FramesPerPacket, entre 10 ms y un segundo), cada uno tras un Incoming Data PDU, con como mucho un segundo esperando. Un mensaje mal formado se descarta sin terminar la sesión |
| `Rail` | RemoteApp (MS-RDPERP): el canal `rail` (saludo, estado del cliente, parámetros del sistema con el área de trabajo = la ventana del navegador menos una barra de tareas de 40 px (con varias pantallas, el monitor de la página, que pasa a ser el principal); Client Execute cuando el navegador avisa de que el escritorio está sincronizado (`ready`, con cuántas ventanas hay abiertas) o, sin ese aviso, 5 s después del saludo (no al reconectar tras una conexión caída), y una vez más 2 s después si el servidor aún no vigilaba el escritorio (RAIL_EXEC_E_HOOK_NOT_LOADED); al volver a conectar (`again`: estado del cliente con AUTORECONNECT; `resume`: desde una página donde estaba abierto), solo si no ha vuelto ninguna; los rechazos del servidor, las órdenes de ventana del navegador); las órdenes de ventana se leen en el navegador (`orders.js`), que copia a la página solo la región visible de cada ventana, dice que se está abriendo (a los 15 s, que tarda; a los 90 s, que el programa no se ha abierto), se vuelve a conectar sin avisar si el servidor cierra la sesión antes de que aparezca el programa (error info 0x0B) y termina la sesión cuando la última ventana del programa lleva 3 s cerrada (no cuentan las ventanas sin tamaño, sin nada visible, ocultas, ocultadas ni de herramientas); con varias pantallas, el canvas de cada ventana recibe las ventanas del programa de su monitor, pasadas de las coordenadas del servidor (principal en 0,0) a las del escritorio |
| `Mppc` | descompresión (MPPC, historial de 64 KB) |
| `Bulk`, `Ncrush`, `Xcrush` | nivel de compresión ofrecido (`bulk_compression`) y descompresión NCRUSH / XCRUSH (RDP 6.0 / 6.1) |
| `Trace` | traza de diagnóstico de una sesión en `data/trace/<sid>.log`: nunca contenidos; 8 MB por sesión, 256 MB en total, se borra a los 7 días |

Los mapas de bits **no se decodifican en PHP**: la pasarela solo analiza cabeceras y reenvía, así el consumo de CPU y memoria es bajo (medido: 0,19 s de CPU y 4 MB para pasar 34 MB de pantalla).

## Modelo de seguridad

- **Acceso**:
  - Instalación: la cuenta de administrador solo se crea con el código de un solo uso de `data/setup-code.php` (tras `<?php exit; ?>`), así nadie puede adueñarse de una copia recién subida.
  - Contraseñas: bcrypt coste 12 (≈0,27 s), al menos 12 caracteres, que no esté entre las ≈30 000 contraseñas comunes de esa longitud (`src/common-passwords.txt`) ni contenga el nombre de usuario.
  - Fuerza bruta: los fallos se cuentan por IP, por usuario, por navegador conocido y en total (todas las IP). Una IP bloqueada no entra. Un usuario bloqueado, o más fallos totales que `login_global_max` (un ataque repartido), solo deja entrar desde navegadores donde ese usuario ya entró (*cookie de dispositivo* firmada, que se anula al cambiar la contraseña), así un atacante no puede dejar fuera al dueño. Cada navegador conocido tiene su propio contador y bloqueo de intentos; una vez bloqueado se le aplican los bloqueos normales, así una cookie de dispositivo robada no da más intentos que el bloqueo por usuario. Se guardan los 20 navegadores usados más recientemente (en la ficha del usuario); cada alta queda en la auditoría (`device_add`) y el usuario puede olvidarlos desde su perfil.
  - Toda respuesta de acceso (contraseña, TOTP, passkey) tarda 1 s (se espera hasta que pasa el segundo midiendo con `hrtime`: `usleep()` puede despertar antes), salvo la de una IP bloqueada, al momento (no dice nada de los usuarios), y usuario inexistente, contraseña mala, cuenta desactivada y bloqueo dan el mismo mensaje: no se pueden averiguar usuarios por tiempos ni por textos. Dentro de ese segundo se leen de la auditoría el último acceso y los fallos desde entonces para el aviso al entrar (como mucho 90 días atrás; peor caso 73 ms, lo normal 5 ms).
  - Segundo factor (opcional, u obligatorio si lo decide el administrador, que debe tenerlo antes): TOTP (RFC 6238; cada código se acepta una sola vez, también el que lo activó) o una passkey. Cuando es obligatorio, quien no lo tiene solo llega a su perfil hasta que lo añade.
  - **Passkeys** (WebAuthn, `WebAuthn.php` + `Cbor.php`, PHP puro + OpenSSL): ES256/RS256, verificación de usuario obligatoria, desafíos de un solo uso, origen e id del sitio comprobados y contador de firmas vigilado. Con la extensión PRF el secreto de la passkey (HKDF) envuelve la clave de datos, así puede sustituir a la contraseña; sin PRF solo sirve como segundo paso. Resisten el phishing: una passkey solo funciona en su propio sitio.
- Sesiones: id nuevo al entrar, límites por inactividad y absoluto (12 h; la petición que cierra una sesión caducada responde `{"error":"auth","reason":…}`, también si no pasaría la comprobación CSRF, porque el token se fue con la sesión; `session.left` dice cuánto le queda sin contar como actividad; `state` devuelve `session: {idle, max}`, así la página solo pregunta `session.left` cuando la sesión debería terminar y entonces muestra *Sesión caducada* con el motivo), ligadas al navegador (agente de usuario: una cookie robada falla en otro navegador y cierra la sesión; no se usan los idiomas porque los Web Workers pueden enviar otros), y al cambiar la contraseña se cierran las demás sesiones del usuario (versión de sesión).
- Las contraseñas temporales que pone el administrador se cambian obligatoriamente al entrar.
- Contraseñas remotas: AES-256-GCM con una clave de datos por usuario. Esa clave se envuelve con otra derivada de la contraseña del usuario (PBKDF2-SHA256, 200 000 iteraciones). Durante la sesión la clave de datos se guarda cifrada en la sesión PHP con una clave aleatoria que solo está en una cookie HttpOnly: ni el fichero de sesión ni la cookie por separado la revelan. Si el administrador restablece la contraseña, las contraseñas remotas guardadas se vuelven ilegibles y se borran.
- Web: token CSRF en toda petición que cambia datos, cookies `SameSite=Strict`, Content-Security-Policy estricta (`'self'`, más imágenes `data:`/`blob:` y marcos `blob:`), HSTS, HTTPS obligatorio, lista blanca de IPs cliente. La API responde 400 `invalid_input` si un campo trae una lista u objeto en vez de texto o un número (también `rdp.php`), y 404 `not_found` para lo que no existe. Un cuerpo JSON se lee hasta 4 MB y se decodifica una vez (413 `too_large` si pasa: `post_max_size` de PHP no lo limita, y una lista de 8 MB decodificada dos veces antes de iniciar sesión ocupaba 150 MB). Los mensajes de PHP nunca llegan al navegador, aunque `display_errors` esté activado: van al registro de errores del servidor, y el visitante ve una página propia (`ErrorPage.php`), sin rutas ni trazas.
- RDP: lista blanca de destinos (IPs, CIDR, nombres, `*.dominio`); el DNS se resuelve una vez y se usa la dirección comprobada; un nombre que no resuelve se rechaza como destino no permitido. Los nombres pasan por el resolutor del sistema (no por uno propio, que rompería el fichero `hosts`, los dominios de búsqueda y la resolución de nombres de Windows). Con «Todo permitido» se comprueban todas las direcciones del nombre y la pasarela nunca se conecta a sí misma (127.0.0.0/8, ::1), a direcciones de enlace local (169.254.0.0/16, con los metadatos de nube, y fe80::/10) ni a 0.0.0.0/8 y ::, tampoco en su forma ::ffff:…; solo se llega a ellas poniéndolas en la lista, y Administración avisa mientras esté en «Todo permitido». En la lista, un nombre exacto llega a lo que resuelva; una regla `*.dominio` confía en el DNS de todos los nombres que cuelgan de él, así que por ella también se rechazan esas direcciones. Fijación del certificado del servidor en el primer uso con aviso si cambia; comprobación de la clave pública en NLA.
- Carpeta compartida: una sola cuota por usuario para la unidad de todas sus sesiones, el gestor de archivos web y los ficheros del portapapeles. El contador (`files/<uid>.quota`) lo cambian bajo su propio bloqueo todas las formas de escribir, así que juntas no pasan de la cuota; se vuelve a contar desde la carpeta al abrir o actualizar el gestor de archivos sin ninguna sesión del usuario en marcha, recorriéndola fuera del bloqueo del contador; cualquier otro listado de una carpeta muestra el contador, sin recorrer la carpeta (eso tardaba de 7 a 17 s con 20 000 archivos) (abrir la unidad con 3000 ficheros pasó de 205–238 ms a 0,2–1,4 ms). Los nombres de más de 255 bytes se rechazan (400 `invalid_path`).
- Gestor de archivos (`files.php`): toda ruta pasa por `Files::clean` (sin `..` ni nombres de archivos de configuración) y tiene que quedar dentro de la carpeta del usuario una vez seguidos los enlaces (`Files::confined`, también en la unidad remota): MuDeskClient no crea enlaces, pero uno puesto ahí por otra cosa (una copia de seguridad restaurada, un programa del servidor; un enlace simbólico, o una unión de Windows, que `is_link()` no ve) nunca se sigue, y los recorridos de una carpeta (borrarla, su ZIP, la cuota) nunca entran en uno (`Files::isLink`). Mover y cambiar de nombre no sale de la carpeta del usuario, nunca pisa algo ni mete una carpeta dentro de sí misma. El árbol lee solo las carpetas abiertas (recorrerlas todas tardaba 2,4 s con 1.000 carpetas y 20.000 archivos en Windows; las abiertas, 64 ms). Acciones: `list` (con la cuota), `tree` (hasta 200 carpetas abiertas), `move`, `mkdir`, `mkdirs` (hasta 1000), `upload`, `delete`, `download` (`view=1`: miniaturas), `zip` (antes `check=1`). Varios elementos o una carpeta se descargan en un ZIP escrito mientras se envía (`ZipStream`: sin compresión, el CRC de cada archivo se lee justo antes, así la longitud se conoce de antemano y no hay descriptores de datos; sin copia temporal; hasta 4 GB y 65.535 entradas, si no `too_big`, que la página pregunta antes). Las miniaturas solo se sirven para tipos de mapa de bits, en línea y con `Content-Security-Policy: default-src 'none'; sandbox` (nunca SVG ni HTML).
- Datos: `data/` fuera de la raíz web, o dentro de ella negada por `.htaccess`/`web.config` (se reescriben si faltan) con una comprobación desde el navegador que avisa al administrador si se puede leer; clave del servidor en un fichero PHP que termina al momento; escritura atómica con bloqueos. Un fichero de datos dañado o vacío se para con un error que lo nombra (un `users.json` vacío nunca se toma por un primer arranque); solo los intentos fallidos de inicio de sesión (`ratelimit.json`) empiezan de nuevo, guardando aparte el dañado. El último administrador activo y que los nombres de usuario no se repitan se comprueban bajo el bloqueo de los usuarios, y un paso TOTP se toma bajo él (dos inicios de sesión con el mismo código a la vez pasaban los dos).
- Auditoría: una línea JSON por evento en un fichero por día; cada línea lleva el HMAC (clave del servidor) de su contenido y el de la anterior, así que *Verificar integridad* detecta ediciones, inserciones y borrados (los días purgados se esperan al principio). La comprobación termina donde estaba el registro al empezar (días, tamaño del fichero más nuevo y su última línea, tomados bajo el bloqueo de los escritores), así que lo escrito mientras tanto queda para la siguiente. Nunca se registran contenidos ni contraseñas. La exportación (hasta 20 000 filas) se envía fila a fila, cada fila tal como está guardada (unos 20 MB de memoria en vez de unos 71 MB). La exportación JSON va firmada con una clave RSA 3072 del servidor (`data/audit-key.php`, creada una sola vez en la primera exportación JSON o al abrir su panel): el SHA-256 se calcula por partes mientras sale el fichero, sin copiarlo, y al final se firma con PKCS#1 v1.5, que es lo que comprueba `openssl dgst -sha256 -verify`. RSA permite firmar un hash calculado así; medido: 0,21–0,23 s para 20 000 filas (0,32–0,36 s la exportación sin firmar de antes), 19–20 MB. Escribir cuesta unos 0,13 ms por evento (bloqueo + añadir). La búsqueda lee los días del rango del más nuevo al más antiguo y solo decodifica las filas que se muestran (medido con 2 000 eventos/día: 90 días en unos 0,1 s, un año en unos 0,4 s, 4 MB de memoria; verificar un año, 3,4 s).
- **Sesiones remotas y sesión web**: las sesiones remotas abiertas desde una sesión web terminan con ella (salir, caducar o cerrarla la pasarela: `Sessions::killWeb`, cada una registrada con el id de su acceso, `wid`); un cambio de contraseña termina las de los otros accesos del usuario (`Sessions::killUser` conservando este `wid`) y la página dice *sesión cerrada*; salir en una pestaña avisa a las demás de ese navegador (`BroadcastChannel`), que terminan las suyas. Una sesión remota comprueba cada 15 s que su cuenta sigue existiendo y activa. La contraseña pedida de nuevo dentro de una sesión (añadir una passkey o una app de autenticación, cambiar la contraseña, quitar un segundo factor: `Auth::confirmPassword`) la cierra tras 5 errores (`reason: reauth`); no usa los bloqueos de acceso, que un ataque al nombre de usuario podría mantener.
- **Peticiones**: los valores de la dirección se leen solo como texto (una lista como `p[]=x` se ignora); `files.php`, `rdp.php` y `api.php` (salvo `state`) rechazan una petición sin cookie de sesión antes de crear un fichero de sesión; las peticiones desde 127.0.0.1 no pasan la comprobación de HTTPS salvo que esa dirección sea un proxy de confianza, cuyo `X-Forwarded-Proto` decide entonces; al salir se envía `Clear-Site-Data: "cache"`; las trazas de error no llevan argumentos (`zend.exception_ignore_args`, contraseñas marcadas `#[\SensitiveParameter]`). Los elementos arrastrados entre ventanas de la aplicación llevan una clave de ese navegador (`localStorage`): otra página no puede hacer que soltar algo mueva archivos.
- **Destinos RDP**: con «Todo permitido», el IPv4 dentro de IPv6 se comprueba como IPv4 también en sus formas NAT64 (`64:ff9b::/96`) y `::a.b.c.d`, y se rechazan también las otras direcciones de metadatos de la nube (100.100.100.200, fd00:ec2::254). Un protocolo que el servidor elige sin haberlo ofrecido (RDSTLS, NLA extendido) termina la conexión.
- **Carpeta compartida**: se rechazan los nombres de dispositivo de Windows (CON, NUL, COM1, LPT¹, CONIN$… con cualquier extensión). El ZIP se pide primero con los nombres en el cuerpo (`check=1`, hasta 10 000, con CSRF) y se descarga con el id de la respuesta (`z=`, guardado en la sesión); el recorrido para pasadas 65 535 entradas o 64 carpetas de profundidad. Las miniaturas se revalidan cada vez (`Cache-Control: private, no-cache`, `Last-Modified`, 304). `delete` espera a que termine de escribirse un trozo de subida.
- **Auditoría**: las peticiones rechazadas de alguien sin sesión se escriben como mucho 100 veces por hora y dirección y 5000 en total (`Audit::anonymous`, luego una línea `audit_limited`). Los días se leen línea a línea, hacia atrás en bloques de 1 MB (un día de 60 MB: 3,7 MB de memoria en vez de 128 MB); *Verificar integridad* enumera los 1000 primeros problemas y los cuenta todos.
- **Conexiones del administrador** (`Connections::saveManaged`): asignadas a usuarios que no pueden cambiarlas ni borrarlas. El administrador nunca pone ni lee la contraseña de un usuario (cifrada con la clave de ese usuario); cuando cambia el destino de una conexión (equipo, puerto, usuario, dominio, seguridad), se olvidan las contraseñas que los usuarios guardaron para ella y su certificado de confianza, también en una conexión propia de un usuario cambiada por el administrador, para que una contraseña escrita para un servidor nunca llegue a otro.
- **Límites de lo que un servidor RDP hostil o defectuoso puede hacer guardar a la pasarela o a la página**:
  - Pasarela: un mensaje de canal de hasta 64 MB con la longitud que anunció su primer trozo; mensajes de canales dinámicos de hasta 64 MB, 8 a la vez en reconstrucción; el historial de XCRUSH vuelve al principio solo cuando está lleno; el socket se lee de 4 MB en 4 MB y una escritura que no termina en 30 s (o 15 s sin poder escribir) termina la conexión; un escritorio de hasta 32766 por lado y 8192 × 8192 píxeles; el portapapeles remoto se guarda hasta 16 MB; los trabajos de impresión, hasta 200 MB por sesión; la unidad: 1024 identificadores abiertos (64 archivos abiertos), 20 000 entradas nuevas y 2000 líneas de auditoría por sesión, las máscaras con más de 4 `*` no coinciden con nada; se rechazan las lecturas y escrituras de la unidad en posiciones de 2^63 o más, o que terminan más allá; se rechazan los literales NCRUSH más allá de su histórico de 64 KB (como los rechaza la página); de los formatos de audio, solo los que la página reproduce (1 o 2 canales, 8–192 kHz, bloques IMA ADPCM de grupos enteros); los mensajes en espera de una sesión hasta 16 MB; las trazas de diagnóstico hasta 256 MB en total; el micrófono solo en PCM de 16 bits de 1 o 2 canales a 8–48 kHz, en paquetes de 10 ms a un segundo pida lo que pida el servidor (una muestra por paquete daba dos mensajes por cada 2 bytes), con como mucho un segundo de audio esperando, y un Format Change antes del Open descartado (no tenía tamaño de paquete: un bucle sin fin).
  - Página: ZGFX con un único búfer del tamaño declarado (hasta 64 MB); las superficies del canal gráfico dentro de 4 veces la salida, su caché de mapas de bits dentro de 100 MB y cada hueco dentro de su superficie, los glifos de ClearCodec como los permite el códec; las cachés de mapas de bits de las órdenes de dibujo dentro de las celdas ofrecidas (600, 600 y 1024 entradas de 256, 1024 y 4096 píxeles); no se acepta un escritorio de más de 32766 por lado o 8192 × 8192 píxeles; se rechazan las imágenes del portapapeles cuya cabecera dice más de lo que traen (el largo de fila contado sin desbordar 32 bits) y los trozos de archivos remotos que pasan de su tamaño; un ZIP de archivos remotos hasta 65 535 entradas y 4 GB (sus límites sin ZIP64); las tramas del flujo hasta 128 MB, con su longitud leída sin signo (una longitud de −5 dejaba el worker en un bucle sin fin); los trozos de audio de un formato que no puede reproducir y los mapas de bits o rectángulos sin tamaño se descartan, sin lanzar.

## Estructura de datos (`data/`)

```
users.json                 cuentas (hashes, claves de datos envueltas, semillas TOTP cifradas con la clave del servidor, passkeys,
                           navegadores conocidos)
settings.json              ajustes del administrador
connections/<uid>.json     conexiones de cada usuario; con un id que empieza por "m", lo que el usuario guarda de una
                           conexión del administrador (su contraseña, certificado y opciones al conectar)
managed_connections.json   conexiones del administrador, cada una con sus usuarios (ids, o "*": todos)
secret.php                 clave del servidor (semillas TOTP, el HMAC de la cadena de auditoría, las cookies de los navegadores
                           de confianza), tras <?php exit; ?>
audit-key.php              clave RSA de las exportaciones firmadas de la auditoría, tras <?php exit; ?>
.htaccess, web.config,     niegan el acceso web (Apache/LiteSpeed/OpenLiteSpeed e IIS;
index.html                 se reescriben si faltan)
setup-code.php             código de un solo uso de la instalación (se borra al crear el administrador)
web-check.txt              el navegador intenta leerlo para detectar una carpeta expuesta
ratelimit.json             intentos fallidos
auditlimit.json            peticiones rechazadas de quien no ha entrado, contadas por hora
*.json.lock                bloqueo de cada almacén JSON
audit/AAAA-MM-DD.jsonl     auditoría, un fichero por día (.last: hash de la última línea; .lock)
sessions/                  sesiones PHP
run/                       sesiones RDP en curso (registro, sockets, colas, register.lock)
tmp/<sid>/                 subidas del portapapeles y trabajos de impresión de una sesión (se borran al terminar)
tmp/upload-<uid>.lock      una sola subida a la vez a la carpeta compartida del usuario
trace/<sid>.log            trazas de diagnóstico (se borran a los 7 días)
files/<uid>/               carpeta compartida de cada usuario
files/<uid>.quota          bytes contados en la cuota del usuario
```
