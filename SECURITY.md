# Security policy

## Reporting a vulnerability

Please do not open a public issue. Use GitHub's **private vulnerability reporting** (Security tab → *Report a vulnerability*) with the steps to reproduce, the affected version and the impact. You will receive an answer as soon as possible.

## Supported versions

Only the latest release (1.3.0 now) receives security fixes.

## Disclaimer

MuDeskClient is made as well as we know how and as well as we can: security first, a test for every critical change, and the code checked against the known vulnerabilities of RDP clients and reviewed in code audits. When we find a fault or a bug, we try to fix it and publish an update as soon as we can (report it as said above).

Even so, no software is free of faults. MuDeskClient is provided "as is", without warranties of any kind, and its authors accept no liability for any damage, including when a malicious user or an attacker manages to compromise the application, the server it runs on, the remote computers or the data, as sections 7 and 8 of the [Apache License 2.0](LICENSE) say. Whoever installs it is responsible for keeping it updated, setting it up as the checklist below recommends and backing up its data.

## Hardening checklist

- Serve the application over HTTPS only (`force_https` is on by default).
- Prefer keeping `src/`, `data/` and `config.php` outside the web root; inside it, check that `data/web-check.txt`, `config.php` and `src/bootstrap.php` answer 403 (or 404), never 200 (see [HOSTING](docs/HOSTING.md)).
- Keep the web idle time-out short (30 minutes by default; every session ends after 12 hours, and the page says so).
- Open the RDP port of the remote computers only to the IP of the web server, and keep NLA enabled.
- Keep the remote computers updated: on one that several people use at once, without the updates of January and April 2022 (CVE-2022-21893, CVE-2022-24533), another user signed in there could take what a session redirects (clipboard, drives); turn the redirections off for the computers you do not keep updated or do not trust (in a connection of yours given to users, they can turn one off, never on).
- Keep the security of the connections to computers that have NLA at *NLA only*, as new connections come: *Automatic* also takes TLS alone and, for computers without TLS (Windows XP, Server 2003), *Standard RDP Security*.
- Use the allow-lists (client IPs and RDP targets) when the set of users or computers is known.
- Behind a reverse proxy, list its IP in `trusted_proxies` (only the exact addresses of your own proxies, never a range: whoever sends from there could pass any address and get past the allowed clients and the sign-in locks; anything that is not an IP address stops the site with a page that says so) and have it send `X-Forwarded-Proto: https`; when it does not pass the site's public name on, set `public_url` (see [HOSTING](docs/HOSTING.md)).
- With the optional WebSocket service, keep `websocket_listen` on 127.0.0.1 (its default), reached only through your web server's proxy rule, which must send the site's `Host` and `X-Forwarded-Proto`; set `'websocket' => false` when you do not use it.
- Finish the first run as soon as the files are in place (its setup code works a day, and then another one takes its place in `data/setup-code.php`), and delete `public/check.php` after the hosting check (it refuses to work a day after it was copied, and the administration says in red while it is there).
- With Docker Compose, keep the image of a version (`compose.yaml` names it) and change it when you update, rather than `latest`.
- Turn on two-step verification (authenticator app or passkey) for administrator accounts; *Require 2FA for every user* makes it mandatory for all.
- Turn off saving RDP passwords (*Allow saving the password of RDP connections*) when users can type them each time.
- Leave the options that lower security as they come, unless a computer you cannot update needs one, and only while it does: `confirm_new_certificates` on (off, the first connection to a computer trusts whoever answers), `credssp_unpatched` off (on, NLA with computers without the 2018 CredSSP update) and *Allow Kerberos with RC4* off (on, a domain controller's answer lets a password be guessed offline far faster). Each is explained under *Known limits* below.
- Leave the microphone and camera box unticked (the default) on connections that do not need them.
- Back up `data/`: it contains `secret.php`, the server key (without it TOTP seeds cannot be read, the audit log no longer verifies and trusted browsers are forgotten), and `audit-key.php`, the key of the signed audit exports.

## Known vulnerabilities of RDP clients

Every vulnerability of RDP clients that official sources list (INCIBE-CERT, CISA, CERT-UA, Microsoft, the NVD), the research behind them and each of FreeRDP's security advisories were looked for in MuDeskClient's code in November 2026: what each was and how MuDeskClient stands is in [VULNERABILITIES](docs/VULNERABILITIES.md) ([Spanish](docs/es/VULNERABILIDADES.md)).

## Known limits: what MuDeskClient does not protect against

- **The first connection to a remote computer.** RDP servers use self-signed certificates, so the gateway cannot check by itself who a computer it has never seen is. That first connection stops before anything of the user is sent and shows the certificate's fingerprints (SHA-256, and SHA-1 as Windows shows it) for the user to compare with the computer's; trusted, it is saved, and a later change is warned of. An administrator can fix a computer's fingerprint for every connection to it (in the connection editor, or by confirming with *Valid for every user*): then nobody is asked, and another certificate is refused, also on a computer a connection broker sends the session to (only an administrator can put a renewed one in its place: by connecting to it, or in the connection editor). `confirm_new_certificates` (`config.php`) set to `false` trusts a new one at once, as before 1.2. Someone in the middle of the network between the gateway and that computer, on a first connection trusted without comparing, can pose as it:
  - with the security *Automatic* or *TLS only*, they can answer that the computer only speaks TLS and receive the Windows password;
  - with *NLA only*, they cannot get the password (NLA binds it to the real computer's key and stops before sending it), but they get a challenge answer from which a weak password can be guessed offline.

  Choose *NLA only* where the computers have it (every current Windows), make the first connection from a network you trust, and keep the RDP port reachable only from the gateway's IP. `'confirm_new_certificates' => false` in `config.php` skips the confirmation (as before 1.2): the first connection then trusts whoever answers, without asking; keep it on.
- **The data folder inside the web root** is protected by the `.htaccess` and `web.config` files; a web server that ignores them (Nginx without the rules of [HOSTING](docs/HOSTING.md), Apache with `AllowOverride None`) would serve it. The application checks it (the server asks itself for `data/web-check.txt` every 10 minutes, and each page's browser tries too, proving it with a random code that changes) and, while it can be read, **does not work**: every page, request and session answers a page that says what to do, until it is protected. Prefer keeping `data/` out of the web root.
- **Backups** carry the keys of the data (`secret.php`, `audit-key.php`) with the users, their encrypted passwords and the audit: whoever has a backup and its password has all of it. They are encrypted (AES-256-GCM, PBKDF2 with 400,000 rounds) with a password of their own: choose a long one and keep it apart from the file. The key made from it waits for the download sealed with the key of the administrator's browser (its cookie), not in the clear in the web session.
- **"Allow all" targets** let any signed-in user reach any computer and port the web server reaches, private networks included (never the gateway itself, link-local or cloud metadata addresses). Use the target list when users should only reach some computers. In the list, a name trusts its DNS, but it reaches those addresses only when they are listed too.
- **The input token** of a running session is a secret held by its browser tab: whoever has it (a proxy that logs request headers, a malicious browser extension) can type into that session until it ends. The server keeps only its SHA-256.
- **A stolen session cookie** is taken from a browser with the same User-Agent: that check stops casual reuse, not someone who copies the header too. Short idle time-outs and two-step verification limit the damage.
- **Sign-in time**: every failed sign-in answer takes a fixed second, so that it never tells which user names exist (one that works, at least that second: on a slow server, opening the user's data key can take a little more), and holds a PHP process meanwhile; many attempts at once keep processes busy. A locked IP is answered at once, and nothing more is written for it.
- **Sign-in locks can be used to keep a user out**: five wrong passwords for a user name lock it for 15 minutes from browsers it has not signed in from, and 50 among all addresses lock every such browser; anyone who knows a user name can do it. Browsers a user has signed in from (*Trusted browsers*) and passkeys are not locked, so a user, an administrator above all, keeps a way in: sign in once from the browsers you use and add a passkey.
- **Old TLS towards old computers.** TLS 1.2 or later without triple DES is offered first, to the remote computers, the Remote Desktop Gateways and the computer that checks Windows accounts. To reach Windows 7 and Server 2008 R2 without their TLS 1.2 update (and Server 2003), a computer that refuses it is connected again with TLS 1.0 made by MuDeskClient itself (ECDHE or RSA, AES or triple DES; its padding and MAC checked with the same work whatever the padding says), and a gateway with OpenSSL's TLS 1.0 and 1.1, triple DES last and its security level 0 (old ciphers and short keys); OpenSSL's level is 1 otherwise, and the certificate is checked by its pinned fingerprint: that link is as strong as the computer or the gateway allows. Only a computer never seen with TLS 1.2: one that used it is never offered less for a year after its last use (`data/tls.json`), so someone in the middle who makes the first handshake fail no longer takes it back to TLS 1.0; the first connection to a computer cannot know. Install the TLS 1.2 update on those computers, keep them on networks you trust, and prefer NLA (it binds the password to the computer's key). The browser's link to the gateway is HTTPS, as the web server serves it.
- **CredSSP without the 2018 update (CVE-2018-0886).** Windows 7 and Server 2008 R2 without the updates of May 2018 speak CredSSP 2 to 4, which bind the TLS key itself, without a nonce: someone in the middle taken for that computer could have MuDeskClient seal what it chose with the session's key and use it against the real computer. NLA with them is refused before MuDeskClient's NTLM answer or key binding goes, as Windows' own client does (it was taken whenever the computer said so); `'credssp_unpatched' => true` in `config.php` allows it (Windows' *Vulnerable*), only while such a computer cannot be updated.
- **Standard RDP Security towards Windows XP and Server 2003.** These computers have no TLS (or none OpenSSL 3 shares with Server 2003), only RDP's own encryption: RC4 with keys of up to 128 bits, or triple DES on a "FIPS compliant" server, with no proof of who the server is (the key Microsoft signs its certificates with is public, and a server's own key may be as short as 512 bits). MuDeskClient uses it only when the connection's security is *Automatic*, pins the server's key as it pins a certificate (a computer that answered with TLS before and now offers only this is warned about as a changed certificate), refuses a key RSA cannot be trusted with (an exponent of 1 or an even one, a modulus under 512 bits) and records it in the audit (`rdp_security` in `rdp_start`). A server that encrypts nothing is refused before the password is sent ("The server does not encrypt the connection"); from the *Client Compatible* encryption level up, anything else the server sends in the clear (but for licensing) is refused; at the *Low* level only what the gateway sends is encrypted, and what the server sends (the screen, its clipboard) goes in the clear. Anyone who can read the network between the gateway and such a computer may break RC4 or pose as it on the first connection. Keep those computers on networks you trust, at the *High* level, or choose *TLS only* / *NLA only* for the connections that must never use it.
- **Kerberos domain controllers from the DNS.** When `config.php` names none, they are looked up in the DNS of the user's domain, which a user can type (user@domain): only port 88 is taken, and never this computer, link-local or cloud metadata addresses. The lookups use the system's resolver (`'kerberos_dns' => false` turns them off) and the whole sign-in to the KDC has 8 seconds. A KDC's errors are not authenticated (Kerberos has none that are): someone in the middle can make a sign-in fail, but not learn the password from it; a clock more than a day away or a reply in an encryption type not in use (RC4 while it is off) is refused.
- **Kerberos with RC4.** Off by default. Allowed in *Administration → Settings* (for a Windows Server 2003 domain, or an account whose password is older than its domain's AES keys; without it those accounts sign in with NTLM; Windows XP does not need it: it is reached with Standard RDP Security, without Kerberos), someone in the middle between this server and a domain controller can make it be used, and the pre-authentication then sent lets the password be guessed offline thousands of times faster than with AES: allow it only if you need it, and reach the domain controllers over networks you trust.
- **The RPC transport of Windows Server 2008 and 2008 R2 gateways** signs each request of MuDeskClient with NTLM, but the signatures of the gateway's answers are not checked: what protects them is the TLS connection to the gateway, whose certificate is pinned as on the other transports. Its sign-in is NTLM only (no Kerberos on that transport).
- **A malicious RDP server** is treated as untrusted (every decoder checks sizes and limits), but it draws what it wants, sees what is typed into its session and copied to its clipboard, and can fill the shared folder up to the user's quota (what it prints counts there too while the session lasts).
- **A connection broker** sends the user to its servers with their certificate in its redirection: the certificate it vouches for is taken for a server seen for the first time, never in place of one pinned before for it (a changed certificate: the user decides). A broker taken over can still send a user who has never been to that server to an impostor it vouches for, within the targets allowed, unless an administrator fixed that server's fingerprint.
- **Session recordings** keep what the screen shows, where the mouse is, what the remote computer plays and what the user's microphone sends it (when the connection has the microphone), encrypted on the server until they are deleted by hand (or the days of the settings); administrators and auditors watch them and can download them as a video, which is then a file outside MuDeskClient's protection, and administrators delete them. The recording of a connection always recorded is made by the server from the session's own stream: the user's browser cannot leave anything out. One started in the session is made by the user's browser, of what its page shows: a page changed on purpose could leave out or alter what it sends, so a recording that must hold whatever the user does is the connection's (*Record the sessions of this connection*). Whoever is recorded is told while it lasts (**● Recording**). Users may start and stop recordings of their own sessions only when the administrator allows it, and never stop one an administrator started or that of a connection always recorded. A user watches, downloads and deletes only the recordings they started: those of a connection always recorded, or an administrator's, they can neither watch nor delete.
- **The microphone and the camera** are off by default (one box) and go only to connections where it is ticked. There, the remote computer decides when it records: once the browser has allowed the microphone for the gateway's address (browsers remember it), any program of that computer that records hears it, and any that uses the camera sees it, with no further question. The browser shows its own sign meanwhile. MuDeskClient says it too, at the top of the session, while the remote computer uses the microphone or the camera. Tick it only for computers you trust, and remove the permissions from the browser (the icon next to the address) on shared computers.
- **A folder of this computer**, shared from the session's *Files* panel, can be read (and, in Chrome and Edge, changed, filled and emptied) by any program of the remote computer while it is shared, as a drive of the computer you connect from would be with Remote Desktop Connection; a guest given control of a shared session can use it through that session too. Nothing of it is kept on the web server, and the files read, written, created, emptied, deleted and renamed are audited (also those still open when the session ends). Share only a folder that holds what the remote computer may have, and stop sharing it when done. An administrator who does not want it turns off the connection's shared folder.
