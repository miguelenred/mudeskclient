# Arquitectura

[English](../ARCHITECTURE.md)

## En resumen: cómo funciona

MuDeskClient tiene dos mitades: la página en el navegador y una pasarela en PHP en el servidor web. En los equipos remotos no se instala nada.

1. **Entrar.** `api.php` comprueba al usuario (una contraseña con bloqueos, TOTP o una passkey, u OpenID Connect o una cuenta de Windows) y guarda una sesión de PHP. Los usuarios, las conexiones, los ajustes y la auditoría son ficheros JSON en `data/`: no hay base de datos. Las contraseñas RDP que guarda un usuario se cifran con una clave derivada de su propia contraseña.
2. **Conectar.** La página pide una sesión a `rdp.php?a=stream`. Esa petición no termina mientras dura la sesión: su proceso de PHP se convierte en el cliente RDP. Comprueba que el equipo es un destino permitido, se conecta a él por TCP (directamente, o a través de una puerta de enlace de Escritorio remoto o de un agente de conexión), negocia TLS y NLA (CredSSP con Kerberos o NTLMv2) o, para Windows XP y Server 2003, la seguridad RDP estándar, y fija el certificado del equipo.
3. **La imagen.** Lo que dibuja el equipo remoto llega en actualizaciones RDP (mapas de bits, órdenes de dibujo o el canal gráfico con H.264 y RemoteFX), todavía comprimidas. La pasarela las pasa como tramas binarias en esa misma respuesta, y un worker de la página las decodifica (WebCodecs para H.264, JavaScript para lo demás) sobre un canvas: la pasarela habla RDP pero casi no decodifica imágenes.
4. **La entrada.** El teclado, el ratón, el táctil, el portapapeles y lo demás salen de la página como POST cortos (`rdp.php?a=send`, autorizados por el token de la sesión), y cada uno llega al proceso de la sesión por un socket local (o un fichero de cola); ese proceso los pone en orden y los manda al equipo remoto. Las imágenes de la cámara y las respuestas de la carpeta del propio equipo van por un carril sin orden, para que ninguna tecla espere detrás de ellas.
5. **Los canales.** El portapapeles (texto, texto con formato, imágenes, archivos), el sonido y el micrófono, la cámara, la carpeta compartida del servidor y una carpeta del propio equipo del usuario (como unidades), la impresora MuDeskPDF, los cambios de pantalla, varios monitores, las ventanas de RemoteApp y el multitáctil: cada uno es un canal virtual de RDP que habla la pasarela (`src/Rdp/`), y el navegador hace lo que solo él puede (reproducir el sonido, grabar, la cámara, los archivos locales, imprimir).
6. **Terminar.** La petición termina cuando el usuario desconecta o cierra la página, o cuando el equipo remoto cierra la sesión. Si la conexión se corta, la página vuelve a intentarlo mientras Windows conserva la sesión. Cada paso queda en la auditoría.

Todo es PHP puro (solo con las extensiones OpenSSL y session que trae PHP), JavaScript y HTML, así que funciona en un hosting compartido normal: sin demonios, sin puertos abiertos a la red, sin WebSocket. Las secciones siguientes entran en cada parte.

## Objetivos y restricciones

- Escritorio remoto (RDP) en el navegador **sin instalar nada en los equipos remotos**.
- Navegador: solo HTML, CSS y JavaScript (módulos ES, sin librerías).
- Servidor: **PHP puro 8.1 – 8.5**, solo las extensiones `openssl` y `session` que trae PHP de serie, sin dependencias de Composer ni base de datos (ficheros JSON).
- Debe funcionar en **hosting compartido**: sin demonios, sin puertos abiertos a la red, sin WebSocket.

`index.php` pide `app.js` y `app.css` con `?v=<versión>-<huella>`: `Http::build` calcula un hash de los nombres, tamaños y fechas de los scripts y estilos de `public/assets`, así que una actualización cambia la dirección aunque no cambie el número de versión. La misma huella va en `data-build` de `<html>` y en la respuesta de `state` (`build`): una página más antigua que la pasarela lo dice y ofrece recargar cuando pide el estado (al empezar y al entrar; no en cada petición, porque la huella cuesta unos 0,8 ms).

### Por qué una petición HTTP larga por sesión

Una petición PHP normal termina al responder, y la conexión RDP debe seguir abierta toda la sesión. Un hosting compartido no permite procesos en segundo plano ni WebSocket, así que cada sesión es **una petición HTTP que no termina**: `rdp.php?a=stream` abre la conexión RDP y envía tramas binarias al navegador (`fetch` + `ReadableStream`). Si el hosting corta la petición, el navegador reconecta solo y la sesión de Windows sigue viva.

Formato de trama (servidor → navegador): `[u8 tipo][u32 longitud][datos]`

| Tipo | Contenido |
|---|---|
| 0 | relleno (hace que algunos proxies empiecen a reenviar) |
| 1 | actualización RDP: `u8 código fast-path` + datos (mapas de bits, paleta, punteros, órdenes de dibujo) |
| 2 | tamaño del escritorio: `u16 ancho, u16 alto, u8 bits` |
| 3 | JSON de estado (`token`, `connected`, `end`, `errorInfo`…) |
| 4 | subprotocolo de portapapeles (`Cliprdr`) |
| 5 | Display Control disponible (resolución dinámica) |
| 6 | mantener viva la conexión |
| 7 | subprotocolo de audio (`Rdpsnd`) |
| 8 | JSON de trabajo de impresión (`Rdpdr`, MuDeskPDF) |
| 9 | mensaje del canal gráfico (RDPGFX, se decodifica en el navegador) |
| 10 | con compresión: actualización fast-path tal como llega: `u8 código, u8 fragmentación, u8 indicadores de compresión` + datos |
| 11 | con compresión: PDU de datos lenta tal como llega: `u8 indicadores de compresión, u8 pduType2` + datos |
| 12 | RemoteApp: JSON sobre las ventanas del programa que no viene con las órdenes de dibujo (una ventana ocultada o mostrada de nuevo) |
| 13 | micrófono: `u8 1, u32 frecuencia, u8 canales` (un programa del equipo remoto graba: enviar PCM de 16 bits así) o `u8 0` (parar y soltar el micrófono) |
| 14 | la conexión rehecha (un invitado entró en una sesión compartida): todos los decodificadores y cachés empiezan de nuevo |
| 15 | solo a los invitados: `u16 x, u16 y`, dónde está el ratón del propietario |
| 16 | cámara: `u8 1, u16 ancho, u16 alto, u8 imágenes por segundo, u8 el número del arranque` (un programa del equipo remoto la usa: enviar imágenes JPEG así, cada una con ese número) o `u8 0` (parar y soltar la cámara) |
| 17 | carpeta de este equipo: `u32 el número de la petición` + una Device I/O Request para ella (MS-RDPEFS, desde su DeviceId), que responde `localdrive.js` (mensajes 20 y 21, con ese número) |

| Tipo | Contenido |
|---|---|
| 1 | eventos de entrada (teclado, ratón, Unicode) |
| 2 | cambio de tamaño: `u16 ancho, u16 alto` |

| 5 | salir |
| 6 | refrescar: el servidor lo dibuja todo de nuevo |
| 7 | texto escrito: caracteres con sus pausas |
| 8 | varios caracteres de golpe (UTF-8): se pegan con «Teclado del móvil por portapapeles», si no se escriben |
| 9 | reservado (terminar una sesión desde la pasarela): rechazado desde el navegador, como todo tipo desde 32 (los de la propia pasarela: entró un invitado, se revocó un enlace, la entrada de un invitado) |
| 10 | confirmación de fotograma del canal gráfico |
| 11 | nota de diagnóstico del navegador (modo diagnóstico) |
| 12 | un texto del historial del portapapeles (UTF-8), siempre pegado (con el portapapeles activado) |
| 13 | varios monitores, cada uno del tamaño de su ventana (JSON) |
| 14 | orden de RemoteApp (JSON, ver más abajo) |
| 15 | audio del micrófono: PCM de 16 bits en el formato de la trama 13 (unos 100 ms cada uno; mientras uno espera a enviarse el siguiente se le une, como mucho un segundo, quitando el más antiguo) |
| 16 | trama multitáctil (con la opción de la conexión, después de que la pasarela envíe `touch: true`): u8 número, y por dedo u8 id (0–9), u8 estado (0 apoyado, 1 movido o quieto, 2 levantado, 3 cancelado), i16 x, i16 y; todos los dedos de la pantalla en cada trama |
| 17 | respuesta al mensaje de consentimiento de una puerta de enlace de Escritorio remoto: `u8 1` aceptado, `u8 0` rechazado |
| 18 | cámara: `u8` el número del arranque (trama 16) + una imagen JPEG de su tamaño (solo el número: no se pudo abrir la cámara); sin orden |
| 19 | carpeta de este equipo: `u8 1, u8 solo lectura` + su nombre (compartida, hasta 64 caracteres), o `u8 0` (ya no) |

Además del flujo y de estos mensajes, `rdp.php?a=watch` da a un invitado el flujo de una sesión compartida, `rdp.php?a=replay` una grabación (ver más abajo), `rdp.php?a=clipfile` recibe por trozos los archivos e imágenes del portapapeles (en `tmp/<sid>/`, contados en la cuota) y `rdp.php?a=print` entrega un trabajo de impresión.

### Admisión de sesiones y tiempos límite

- Cada sesión ocupa un proceso PHP mientras dura, así que el número de sesiones se limita por usuario y entre todos los usuarios (`max_sessions_total`, 20 por defecto). Antes de enviar nada, `rdp.php` cuenta las sesiones en marcha y registra la nueva bajo un mismo bloqueo (`data/run/register.lock`), así dos peticiones a la vez no pueden quedarse las dos con la última plaza. Una pasarela llena responde al momento 503 `busy`, antes de abrir ningún socket.
- Cada paso del saludo (TCP, TLS, X.224, NLA, MCS) espera como mucho 8 s; la activación, 30 s. Si el navegador se cierra mientras se conecta, el proceso PHP se libera en 1–2 s.
- El nombre del destino se resuelve después de la admisión, así que el límite global también acota los procesos que esperan a un servidor DNS lento (ver [HOSTING](HOSTING.md#nombres-de-equipo-dns)).

### Entrada (navegador → servidor)

Teclado, ratón, portapapeles y cambios de tamaño viajan en **peticiones POST cortas** a `rdp.php?a=send`:

- No abren la sesión PHP (ni bloqueo del fichero de sesión ni lectura de usuarios): se autorizan con un **token aleatorio por sesión** que llega en la primera trama de estado y viaja en la cabecera `X-MuDesk-Token` (no en la URL, para que no quede en los registros del servidor web). El fichero de la sesión en `data/run/` guarda solo su SHA-256: una copia de la carpeta de datos no da a nadie el teclado de una sesión abierta. El cuerpo se lee solo después de comprobar el token (o el enlace de un invitado), y nunca más de 4 MB (4 KB para un invitado): `post_max_size` de PHP no lo limita, y un cuerpo grande enviado sin token se leía entero antes. Se lee lo que dice su `Content-Length`: con un límite, PHP 8.1 y 8.2 reservan antes toda esa memoria (4 MB por cada tecla).
- Cada mensaje lleva un número de secuencia `u32`. El navegador mantiene **hasta 4 peticiones en paralelo** y el proceso de la sesión las reordena (los huecos de más de 0,5 s se saltan).
- Las imágenes de la cámara (mensaje 18) y las respuestas de la carpeta de este equipo (20, y 21: la primera respuesta de un listado con sus demás nombres) van en cambio **sin orden** (`Sessions::OUT_OF_BAND` como número de secuencia, dos peticiones a la vez, primero las respuestas de la carpeta y solo la imagen más nueva esperando): se toman según llegan, así que ninguna tecla espera detrás de una imagen de unos 40 KB o de un trozo de archivo de hasta 1 MB. `rdp.php?a=send` no admite nada más por ese carril, ni nada de la página por el de los invitados. Una respuesta de la carpeta que se pierde por el camino (un error de red, o la pasarela ocupada: 5xx) se envía otra vez hasta 3 veces, a los 0,5, 1 y 1,5 s; la pasarela solo toma la primera de dos (cada respuesta lleva el número de su petición).
- Los movimientos de ratón se agrupan mientras hay peticiones en curso (de los eventos agrupados por el navegador solo se sitúa el último). Los movimientos y las confirmaciones de fotogramas del canal gráfico ocupan como mucho 3 de las 4 plazas y se turnan, así una confirmación nunca se queda atrás por un ratón en movimiento (Windows regula sus fotogramas con ellas) y una tecla o un clic siempre tiene plaza.
- El **texto tecleado** (teclados en pantalla, IME, autocorrección) sigue el orden del resto de la entrada en una cola de la pasarela (`Client::input`):
  - Un carácter suelto (mensaje de tipo 7) va como Unicode y lo que llega detrás espera 100 ms; la pausa se aplica en la pasarela porque las peticiones HTTP llegan con separaciones desiguales.
  - Varios caracteres de golpe (mensaje de tipo 8, UTF-8), con la opción «Teclado del móvil por portapapeles», se **pegan** (`Client::pasteText`, `Cliprdr::typeText`; motivo y pruebas en [TECLADO-MOVIL](TECLADO-MOVIL.md)). Los textos seguidos se unen. Si lo último se copió en Windows, se lee antes (todos sus formatos, hasta 16 MB) para reponerlo; con archivos o más de 16 MB el texto se escribe. La pasarela anuncia el texto (con los formatos que lo excluyen del historial y de la nube), espera la respuesta a *ese* anuncio (Windows responde a cada lista en orden) y a que la pantalla cambie tras la última entrada enviada, pulsa Ctrl y V y las mantiene hasta que la aplicación pide el texto, lo entrega, las suelta y repone el portapapeles justo después de cada pegado (un texto vacío si no había nada copiado). Windows confirma un anuncio antes de aplicarlo y no aplicaba una lista igual a la que tenía (dos pegados seguidos volvían a pegar el texto anterior), así que cada lista anunciada lleva un formato propio que alterna: dos listas seguidas nunca son iguales. Sin la opción, el texto se escribe como Unicode.
  - Un texto del historial del portapapeles (mensaje de tipo 12, UTF-8, hasta 1 MB) se pega siempre así, tenga o no la opción (con el portapapeles activado).
  - La entrada que espera detrás de un pegado sale cuando la pantalla cambia (la aplicación ha dibujado lo pegado).
  - Límites solo para cuando Windows no responde: 2 s para la respuesta al anuncio y para el cambio de pantalla, 10 s para que la aplicación pida el texto; entonces se escribe como Unicode.
- RemoteApp (mensaje de tipo 14, JSON): el escritorio sincronizado (`ready`: el servidor ha mandado todas sus ventanas, con cuántas hay abiertas, y ya se puede pedir el programa), una ventana traída al frente (`activate`), minimizada, maximizada, restaurada o cerrada (`sys`, solo con una de esas cuatro órdenes).
- La petición corta entrega el mensaje a la larga por un **socket Unix** en `data/run/` (o en la carpeta temporal del sistema si esa ruta llega a 100 caracteres); en Windows, que no tiene sockets Unix para PHP, por un **puerto TCP solo de este equipo** (127.0.0.1), con cada mensaje empezando por un secreto de la sesión guardado en su fichero de modo (a un puerto así puede conectarse cualquier proceso local); sin `stream_socket_server` o con `'ipc' => 'file'`, por un fichero de cola que se revisa cada 20 ms (Windows lo usaba antes: cada tecla, movimiento del ratón y confirmación de fotograma esperaba hasta 20 ms). Cada petición es una conexión al socket con un mensaje, que se guarda aparte hasta que ha llegado entero: añadido a un único búfer según llegaba, un mensaje grande (un pegado) que llegaba en trozos quedaba mezclado con los de las otras peticiones, y la entrada de la sesión dejaba de funcionar. Las conexiones nuevas se buscan cuando el socket de escucha se puede leer (intentarlo en cada vuelta costaba al bucle de la sesión 8–11 µs en Windows) o 20 ms después de la última búsqueda: con datos TLS ya descifrados, `stream_select` de PHP da solo ese flujo sin preguntar al sistema, y el socket de escucha se quedaba fuera mientras el servidor dibujaba.

### Compartir una sesión

- Un enlace es `#/watch/<sid>.<secreto>`: 24 bytes aleatorios (base64url), creado por `api.php` `session.share` para el propietario de la sesión; el fichero de la sesión en `data/run/` guarda el SHA-256 del secreto y el modo (`view` o `control`), nunca el secreto. Hasta 10 enlaces por sesión; ninguno con RemoteApp ni con el fichero de cola.
- La página del invitado envía el enlace a `rdp.php?a=watch` (sin cuenta ni sesión PHP). La petición se conecta al socket de la sesión y dice `\0WATCH` + el id del enlace (tras el secreto de la sesión por TCP); el proceso del flujo mantiene esa conexión abierta como invitado (como mucho 5) en vez de leer de ella un mensaje, y su bucle se entera de la llegada (un evento propio, tipo 0x21).
- Ante una llegada, el proceso del flujo envía lo que tenía la conexión anterior, admite al invitado, se desconecta del servidor RDP y vuelve a conectar con las mismas credenciales, el mismo tamaño de escritorio y el mismo certificado (otro distinto termina la sesión: `cert_changed`), tras la trama 14. Windows mantiene la sesión mientras tanto. Las superficies, cachés y flujos H.264 del canal gráfico, las cachés de las órdenes de dibujo y los históricos de los compresores no se pueden tomar a medias: desde la trama 14 todas las páginas (la del propietario y las de los invitados) decodifican desde cero.
- Lo que se envía al navegador va también a los invitados, filtrado (`Sessions::GUEST_FRAMES`: la imagen, su tamaño, el puntero, el estado y los avisos de vida; nunca el portapapeles, el sonido, el micrófono, la cámara, la carpeta de este equipo (tramas 16 y 17) ni los trabajos de impresión), copiado solo mientras algún invitado mira. La petición del invitado lo reenvía tal cual. Un invitado que no da abasto (8 MB esperando) se suelta; uno que se va se nota en el siguiente aviso de vida (cada 10 s). A la página del propietario se le dice cuántos miran (`viewers` en una trama de estado). Mientras alguien mira, la página del propietario oculta no detiene el dibujo del servidor.
- La posición del ratón del propietario (el último evento de ratón de cada lote de entrada) va solo a los invitados, como trama 15.
- Un invitado con control envía `rdp.php?a=send` con el secreto del enlace en `X-MuDesk-Share`: solo teclado y ratón (1), texto escrito (7, 8) y toques (16), como mucho 4 KB, escritos a la sesión con el número de secuencia `0xFFFFFFFE` (su propio carril, en orden de llegada: la página mantiene una petición en vuelo). La sesión lo lee como un evento (0x22 + el mensaje) y lo trata como la entrada del propietario. La página nunca envía confirmaciones, tamaños ni visibilidad.
- `session.unshare` quita el enlace del fichero y avisa a la sesión (un mensaje fuera de orden, 0x20 + el id del enlace), que suelta a sus invitados al momento. Los enlaces se van con el fichero de la sesión cuando termina.

### Grabación de sesiones

- Con `record` en una conexión (solo lo pone el administrador: un guardado del propio usuario lo conserva), `rdp.php` empieza una `Recording` justo después del token, antes de mostrar nada de la sesión, y envía `recording: true` en una trama de estado; una grabación que no puede empezar termina la sesión (`record_failed`). `rdp_connect` y `rdp_start` lo dicen con `recording`.
- Cada trama que se envía al navegador pasa por `Recording::frame`, que guarda solo los tipos de la imagen (`Recording::TYPES`: actualizaciones, tamaño, estado, control de pantalla, canal gráfico, actualizaciones comprimidas, la trama 14 y el ratón del propietario, la trama 15), cada una como `[u32 ms][u8 tipo][u32 longitud][datos]`. Un trozo se escribe al llegar a 1 MB (un fotograma mayor sigue en los trozos siguientes: los bytes en claro son un solo flujo) o cada segundo: AES-256-GCM con una clave derivada de la del servidor (HMAC-SHA256), un nonce aleatorio y el id de la grabación y el número del trozo como datos adicionales, como `[u32 longitud][nonce][etiqueta][cifrado]` tras `MDREC1\n`. Sus datos (quién, conexión, inicio, fin, segundos, bytes, `truncated`) van en `data/recordings/<sid>.json`.
- `rdp.php?a=replay` (administradores y auditores, en la auditoría como `recording_view`) la descifra trozo a trozo y envía las tramas en claro, y después una trama de relleno `end` si la leyó entera (sin ella la página dice que está dañada a partir de ahí); el worker de la página las da a su ritmo (`timed`), decodificando de golpe lo que va antes del punto pedido, y pausa, sigue y cambia la velocidad cuando la página lo pide.
- `Recording::cleanup` (en cada sesión grabada y en cada consulta) borra las de más de `record_days`.

### Puerta de enlace de Escritorio remoto y agente de conexión

Contrastados con las especificaciones y con un cliente de código abierto que funciona con las puertas de enlace y los agentes de Windows. Probados a través de una implementación de código abierto de RD Gateway delante de Windows 11 (una sesión entera: NTLM, la directiva de dispositivos, los keep-alive, el cierre del canal; los dos transportes, y Kerberos con el KDC de un reino de prueba), y los tokens de enrutamiento contra el propio Windows 11; aún no contra la puerta de enlace de Windows Server ni contra un agente real. El transporte RPC (Windows Server 2008 y 2008 R2) se probó contra una puerta de enlace escrita según las especificaciones, `tests/fixtures/rpc_gateway.php`, por la que pasó también un cliente independiente. En las pruebas, contra los suyos: `tests/fixtures/rdg_server.php` (con `tests/fixtures/nla_server.php` detrás), `tests/fixtures/rpc_gateway.php` y `tests/fixtures/broker_server.php` (un agente y el equipo al que envía al cliente, escritos según MS-RDPBCGR).

- **Agente de conexión** (MS-RDPBCGR): el `lb` de la conexión (238 bytes como mucho: la longitud de la petición X.224 es de un byte) va en la X.224 Connection Request como token de enrutamiento (con CR LF) en vez de la cookie `mstshash`; el bloque de datos de clúster del cliente (`TS_UD_CS_CLUSTER`, 0xC004) dice que se admite la redirección (versión 5) y, en una conexión redirigida a la que se dio una sesión, la sesión a la que unirse. Una Server Redirection PDU (share control PDU de tipo 0xA, `SEC_REDIRECTION_PKT`) se lee campo a campo en el orden de la especificación (`Client::redirection`) y se lanza como `Redirection`. `rdp.php` desconecta y vuelve a conectar (`Client::redirected`): con un token de enrutamiento y sin dirección de destino, al mismo equipo que la envió, con ese token (1.3.8); si no, a un equipo que nombra, sin token: primero por dirección (su dirección y después su lista de direcciones), luego su FQDN y su nombre NetBIOS, cada destino permitido por turno mientras uno no se alcance (`unreachable`; a través de una puerta de enlace, `gateway_denied`), auditado con el que sustituye; a través de una puerta de enlace, primero por nombre, y deciden sus directivas. Van con ella su sesión (si no es 0), su usuario y dominio (si no están vacíos; también un dominio vacío con un usuario de la forma usuario@dominio) y su cookie en lugar de la contraseña; esa contraseña, si es texto y no una cookie opaca y no se conoce la del usuario (entró en la pantalla de inicio de sesión del agente), sirve para entrar con NLA allí. El certificado del destino que da el agente (`LB_TARGET_CERTIFICATE`, un contenedor en base64) es el que tiene que encontrarse allí: se acepta sin preguntar (`vouched_by_broker` en `cert_trusted`) y otro se rechaza como certificado cambiado, aunque sea el primer uso. Como mucho 3 seguidas; cada una se audita (`rdp_redirect`, con si cambió el usuario) y el certificado de cada equipo se fija con su nombre (los `certs` de la conexión, leídos de nuevo cada vez). Una que solo informa (`LB_NOREDIRECT`) no se sigue. Una contraseña cifrada para la clave del destino (`LB_PASSWORD_IS_PK_ENCRYPTED`) se le entrega allí tal como llegó, con el GUID de la redirección, por RDSTLS (MS-RDPBCGR 2.2.17: RDSTLS y TLS pedidos en la petición X.224, también con la seguridad *Solo NLA*); un rechazo se dice como el del inicio de sesión (contraseña incorrecta, cuenta bloqueada…). Una que llega con la sesión ya en marcha (tras entrar en la pantalla de inicio de sesión del propio agente, sin NLA) se sigue igual, y todas las páginas decodifican de nuevo (trama 14); `rdp_redirect` dice la dirección a la que se llegó (`target_ip`) y `late`. Sin puerta de enlace se llega al equipo siguiente primero por su dirección; si el agente da también su nombre (`TargetFQDN`), ese nombre es el que usan Kerberos, TLS y la huella de su certificado, y se conecta a la dirección comprobada contra los destinos permitidos (con solo una dirección, NLA usa allí NTLM, no Kerberos: una dirección no tiene reino). Un invitado que se une a una sesión compartida que un agente envió a otro equipo vuelve a conectar con ese equipo con lo que dio el agente (su sesión, su usuario y su contraseña o cookie); aún no se sabe si el equipo de un agente real lo acepta una segunda vez.
- **Puerta de enlace de Escritorio remoto** (MS-TSGU, `Gateway.php`): TLS hasta la puerta de enlace (SNI con su nombre; su certificado fijado en el primer uso en `certs`, con `gw:` y su nombre, aparte de los equipos de una granja y sin descartarse nunca, antes de enviar nada del usuario), después `RDG_OUT_DATA /remoteDesktopGateway/` con `Upgrade: websocket`, entrando con Kerberos si se puede tener un ticket para `HTTP/<puerta de enlace>` (una vuelta: SPNEGO con el AP-REQ, cuya suma GSS lleva el enlace de canal y cuyo autenticador lleva el aviso `AD-AUTH-DATA-AP-OPTIONS`; si la puerta de enlace rechaza el ticket, NTLM en la misma conexión) y, si no, con NTLM sobre HTTP (dos vueltas, con el esquema NTLM, o con Negotiate si es el único que ofrece, también si vienen varios en una cabecera; también se lee un cuerpo por trozos; las cookies que pone se devuelven, para los balanceadores delante de varias puertas de enlace), con el enlace de canal del certificado de la puerta de enlace en la prueba NTLMv2 (RFC 5929 `tls-server-end-point`: el hash de su firma, SHA-256 para MD5 y SHA-1, el que una firma RSASSA-PSS nombra en sus parámetros; para las que tienen la Protección extendida), y `101 Switching Protocols` con su `Sec-WebSocket-Accept` comprobado, o `200`: el transporte antiguo (Windows Server 2012 y 2012 R2), en el que esa conexión trae después los paquetes de la puerta de enlace tras unos bytes aleatorios (hasta la respuesta al saludo, dentro de 128 bytes; sin trozos si un proxy la trocea) y una segunda conexión TLS a la misma dirección (el mismo certificado, el mismo `RDG-Connection-Id`, sus cookies, también con su entrada) lleva los del cliente: tras su `200`, un `RDG_IN_DATA` con `Transfer-Encoding: chunked`, escrito aparte y sin respuesta, y luego cada paquete como un trozo HTTP. Un `404`, `405` o `501` en su lugar es una puerta de enlace sin el transporte HTTP (Windows Server 2008, 2008 R2): RPC sobre HTTP, más abajo. Sobre el WebSocket (las tramas del cliente enmascaradas; pings, cierres y fragmentos atendidos), o las dos conexiones: saludo, túnel (capacidades: mensajes de consentimiento y de servicio; su mensaje de consentimiento, tras los campos opcionales de antes, se muestra en la página y el túnel sigue solo si el usuario lo acepta: `rdp.php` espera la respuesta de la página, el mensaje 17, hasta diez minutos, comprobando el navegador y guardando para después los demás mensajes de la sesión; rechazado, `gateway_consent`, con `why`; las mismas condiciones, aceptadas otra vez al momento cuando la sesión vuelve a conectar, `again`) y autorización del túnel (cada uno esperado hasta 90 s: la puerta de enlace puede pedir un segundo factor aprobado en un móvil; el nombre del cliente; a un cliente en cuarentena se le da el túnel igualmente; sus indicadores de redirección son su directiva de dispositivos: el portapapeles, las unidades o las impresoras que prohíba no se ofrecen, `cliprdr` fuera, `rdpdr` también si se prohíben ambos, `Rdpdr` anunciando solo el permitido, y el pegado por el portapapeles se teclea; `gateway_denied` en `rdp_start`), canal al equipo (su nombre y puerto, esperado hasta 30 s) y después los bytes RDP en paquetes DATA de 16 KB como mucho, los keep-alive de la puerta de enlace contestados y uno propio tras 60 s sin enviar nada (los proxies delante de las puertas de enlace cortan las conexiones calladas), sus mensajes de servicio (paquete 0x0B) guardados y mostrados en la página durante la sesión, un mensaje de reautenticación sin atender, y el cierre del canal. Errores: `gateway_unreachable`, `gateway_not_allowed` (no es un destino permitido), `gateway_auth` (usuario o contraseña rechazados: la página los vuelve a pedir), `gateway_denied` (el usuario rechazado por sus directivas, ese equipo no permitido a ese usuario, o no alcanzado), `gateway_unsupported` (ni el transporte HTTP ni RPC sobre HTTP; sin una entrada que haga este cliente; `E_PROXY_CAPABILITYMISMATCH`), `gateway_consent`, las respuestas del KDC sobre el usuario (Kerberos), `gateway`. `rdp_start` dice su transporte (`websocket`, `http` o `rpc`) y cómo entró el usuario en ella.
- **RPC sobre HTTP** (`GatewayRpc.php`, MS-TSGU sobre el RPC sobre HTTP v2 de MS-RPCH y MS-RPCE), para una puerta de enlace sin el transporte HTTP (Windows Server 2008 y 2008 R2; las posteriores también lo tienen): dos conexiones TLS más a la misma dirección, cada una con el certificado fijado de la puerta de enlace y con su entrada por NTLM con el enlace de canal (con el esquema NTLM o con Negotiate; sin Kerberos en este transporte), a `/rpc/rpcproxy.dll?localhost:3388`. El canal IN es una petición `RPC_IN_DATA` cuyo cuerpo (`Content-Length` de 1 GiB, como el cliente de Windows) lleva todo lo que envía el cliente y que no se contesta mientras va bien; el canal OUT, el cuerpo de la respuesta a `RPC_OUT_DATA`, todo lo que envía la puerta de enlace. Las PDU RTS hacen la conexión virtual (CONN/B1 por IN, A1 por OUT; A3 y C2 esperadas, 8 s) y llevan su control de flujo (una ventana de recepción de 64 KB, FlowControlAck al usarse la mitad; los pings se dejan estar). DCE/RPC se enlaza (bind) a TsProxyRpcInterface 1.3 con NTLM a nivel de integridad de paquete: cada petición firmada, también su cabecera (header signing); las firmas de las respuestas de la puerta de enlace no se comprueban (las lleva la conexión TLS, fijada). Después, las llamadas por opnum: TsProxyCreateTunnel (versión, capacidades, su mensaje de consentimiento), TsProxyAuthorizeTunnel (el nombre del cliente; la directiva de dispositivos, `gateway_denied`), TsProxyMakeTunnelCall esperando el siguiente mensaje de servicio (solo si la puerta de enlace los admite: Windows Server 2008 no tiene), TsProxyCreateChannel (el equipo y el puerto), TsProxySetupReceivePipe (cada PDU de respuesta de esa llamada son bytes del equipo; una última de 4 bytes, su fin) y TsProxySendToServer para los bytes del cliente; los paquetes DATA, KEEPALIVE y CLOSE_CHANNEL de `Gateway` pasan a ser SendToServer, un ping RTS y TsProxyCloseChannel, así `pump` es el mismo. Las respuestas solo se guardan para las llamadas que se esperan, hasta 1 MB cada una. Cada canal se rehace antes de gastar su longitud: el OUT cuando la puerta de enlace lo pide (OUT_R1/OUT_R2: una conexión nueva con su entrada, leídas las últimas PDU de la vieja, apartado mientras tanto lo que espera al canal IN), el IN por el cliente al enviar la mitad de su GiB (IN_R1/IN_R2: una conexión nueva en la que solo se escribe cuando llega la A4 de la puerta de enlace; antes, las últimas PDU de la vieja y la IN_R1/A5; nada se pierde, se duplica ni se desordena, y la secuencia de las firmas sigue entre las dos). Un error HTTP que la puerta de enlace conteste en el canal IN no se lee: se ve como que no contesta (`gateway`, a los 8 s); en el canal OUT, 401 es `gateway_auth` y 404 `gateway_unsupported`.
- **Kerberos** (`Kerberos.php`, `KerberosCrypto.php`; RFC 4120, RFC 4121, RFC 4178, MS-KILE), que `CredSsp` (`TERMSRV/<equipo>`) y `Gateway` (`HTTP/<puerta de enlace>`) prueban antes que NTLM, y con ellos la entrada con cuenta de Windows. AES (tipos 17 y 18, RFC 3961/3962 en PHP puro: n-fold, las claves derivadas, string-to-key con PBKDF2, AES-CBC con robo de texto cifrado sobre el AES de OpenSSL, HMAC-SHA1-96), comprobado con los vectores de las RFC y las respuestas conocidas de MIT; y RC4 (tipo 23, RFC 4757: el hash NT como clave, HMAC-MD5 y sus propios tokens GSS para MIC, Wrap y Unwrap) para un dominio de Windows Server 2003, una cuenta cuya contraseña es anterior a las claves AES de su dominio o un servicio sin claves AES, ofrecido el último (un KDC que tiene AES lo da), y solo si el ajuste `kerberos_rc4` lo permite (*Administración → Ajustes*, desactivado de serie: `Kerberos::types()`; RC4 no se ofrece ni se acepta entonces, ni en PA-ETYPE-INFO2 ni como clave de sesión o subclave: quien se ponga en medio diciendo que la cuenta solo tiene RC4 no recibe ninguna marca de tiempo cifrada con su clave). Los reinos que probar: el sufijo de un usuario@dominio, el dominio por su nombre DNS o el sufijo DNS del equipo cuando nombra el dominio (nunca para una dirección, `localhost` o una cuenta local: el dominio `.` o el nombre del propio equipo; entonces NTLM); un sufijo UPN alternativo se pregunta al KDC del dominio o del equipo, que contesta KDC_ERR_WRONG_REALM con el dominio que lo tiene, y se sigue; sus KDC, de `config.php` (`kerberos_kdc`) o del DNS (registros SRV `_kerberos._tcp` y `_kerberos._tcp.dc._msdcs`; solo el puerto 88, y nunca este equipo, direcciones de enlace local ni las de metadatos de una nube), por el puerto TCP 88, con 8 s para todo el inicio de sesión con el KDC (un KDC callado: NTLM). Un ticket de servicio que es una referencia a otro dominio del bosque se deja a NTLM. El intercambio AS con PA-PAC-REQUEST, preautenticación con una marca de tiempo cifrada con la sal y el tipo de PA-ETYPE-INFO2 (también una cuenta sin ella), un reloj desfasado más de 5 minutos corregido una vez (`KRB_AP_ERR_SKEW`, la hora del KDC), usuario@dominio como nombre de empresa (NT-ENTERPRISE; uno desconocido se pide otra vez con el nombre solo), y el nombre y el reino que devuelve el KDC usados desde entonces; el intercambio TGS (el autenticador con la suma de comprobación del cuerpo de la petición). Las respuestas del KDC sobre el usuario (contraseña incorrecta, 24; cuenta bloqueada, deshabilitada o caducada, 18 con el NTSTATUS de su KERB-EXT-ERROR; contraseña caducada, 23) se dicen tal cual y nunca se reintentan con NTLM, que contaría otro fallo; lo demás (sin reino, sin KDC, usuario o servicio desconocidos) sigue con NTLM. El AP-REQ va en SPNEGO (primero el OID Kerberos de Microsoft, los indicadores GSS 0x32, la suma GSS 0x8003 con el enlace de canal o ceros); el AP-REP da la clave del contexto (la subclave del servicio); su mechListMIC se comprueba, y el nuestro se envía solo si pide más (accept-incomplete). GSS Wrap y Unwrap (RFC 4121: sellado, EC 0, RRC 28 como lo envía Windows en CredSSP; los del otro lado, rotados de vuelta) llevan el enlace con la clave pública y las credenciales de CredSSP. Con Kerberos no se conoce la versión de Windows (no hay desafío NTLM): el modo de gráficos automático toma el canal gráfico.
- PHP no puede poner TLS sobre un flujo hecho por él mismo, y la conexión RDP lleva su propio TLS y NLA dentro del túnel: el cliente RDP usa un extremo de un par de sockets TCP conectados por 127.0.0.1 (un puerto de escucha por proceso; solo se toma la conexión de su propio extremo), sobre los que el TLS de PHP funciona (`stream_socket_pair` da sockets que no admiten TLS), y `Gateway::pump` pasa los bytes entre el otro extremo y el túnel, leyendo las tramas y los paquetes de una pasada. Con 1 MB esperando a la puerta de enlace, los bytes del cliente se quedan en el par (sus escrituras esperan); con 8 MB esperando al cliente, los de la puerta de enlace se quedan en su socket. Cuando el túnel termina, el cliente recibe lo que llegó antes del final y después el final, que ve como un equipo remoto que cierra (así se lee la última información de error del servidor). `Transport` bombea mientras espera (su saludo TLS, no bloqueante para eso) y el bucle de la sesión vigila el socket de la puerta de enlace con los demás (también para escribir mientras esperan tramas) y bombea en cada vuelta; mientras se abre el túnel, se comprueba el navegador cada segundo. A través de una puerta de enlace no se usa Wake-on-LAN (el equipo no está en esta red).

### Pantalla

- El flujo se lee y decodifica en un **Web Worker** (`stream-worker.js`), así la entrada nunca espera al dibujado.
- Decodificadores (`gfx.js`): RLE entrelazado (8/15/16/24 bits), planar (32 bits), sin comprimir, paletas y punteros (color, nuevo, grande). Los píxeles de 15/16 bits usan tablas precalculadas.
- Los rectángulos decodificados se transfieren al hilo principal (`postMessage` con búferes transferibles) y se pintan con `putImageData`: los mapas de bits de una actualización juntos, en mensajes de 64 mapas de bits y unos 4 millones de píxeles como mucho (64 mapas de bits de un escritorio 1080p entero, hechos con unos cientos de bytes, ocupaban 506 MB), porque cada mensaje le cuesta su propio tiempo al hilo de la página (un listado de consola a 16 bits: 24 388 mensajes le llevaron 371 ms, 385 mensajes 210 ms).
- Las órdenes de dibujo (`orders.js`: DstBlt, PatBlt, OpaqueRect, ScrBlt, MemBlt) y la **caché de mapas de bits** (revisión 2, tres celdas de 600/600/1024 entradas: las órdenes secundarias *cache bitmap v2* guardan mapas de bits ya decodificados y MemBlt los pinta) se analizan en el worker y se ejecutan en el canvas; los mapas de bits guardados viven en el hilo principal como canvas pequeños. Activadas por defecto (`drawing_orders`): validadas píxel a píxel contra xrdp y Windows 11. MemBlt y PatBlt admiten cualquier ROP: las copias simples (SRCCOPY, PATCOPY) las pinta el canvas, y las demás se hacen píxel a píxel en el hilo principal (`drawRop` lee el rectángulo y `rop3` calcula cada bit a partir del pincel, el origen y el destino; PATINVERT hace XOR con el color o el patrón del pincel). Mem3Blt no se negocia (Windows manda mapas de bits en su lugar), así que un MemBlt cuyo ROP use pincel toma el pincel blanco por defecto de GDI. **Texto** (mismo ajuste): GlyphIndex, FastIndex y FastGlyph con la caché de glifos (Cache Glyph revisión 2, que los servidores envían como orden de tipo 3 con el nivel de soporte «encode»; diez cachés) y la caché de 256 fragmentos. El worker guarda el tamaño de los glifos y calcula las posiciones (desplazamientos, paso fijo, fragmentos); el hilo principal convierte una vez cada glifo de 1 bit en un `Path2D` con sus tramos de píxeles y lo rellena con el color del texto, recortado al rectángulo de fondo (primero se rellena el rectángulo opaco con el campo *foreground* de la orden y el texto usa el campo *background*, como lo define RDP). Comprobado con órdenes construidas a mano (`tests/orders_unit.mjs`), al píxel en Chrome y Firefox (`tests/e2e_glyphs.mjs`) y con las órdenes de texto reales de la ventana de acceso de xrdp: el texto sale idéntico a la versión en mapas de bits a 16 y 32 bits. PatBlt pinta pinceles de patrón 8x8 y tramados (PATCOPY; un bit a 1 toma el color de fondo, como en GDI). Los colores de las órdenes a 24/32 bits son bytes rojo, verde, azul. Las cachés de pinceles y tablas de color no se negocian y se saltan por su longitud.
- **Compresión** (`bulk_compression`, activada por defecto, `'rdp61'`): el cliente ofrece hasta RDP 6.1 y el servidor elige para cada bloque un tipo no superior: MPPC con historial de 64 KB («RDP 5», `Mppc.php`, el que usa xrdp), NCRUSH («RDP 6.0», `Ncrush.php`: literales con códigos Huffman, desplazamientos con caché de 4 entradas, historial de 64 KB; las tablas de decodificación se generan a partir de los códigos de MS-RDPEGDI) o XCRUSH («RDP 6.1», `Xcrush.php`: un MPPC interior sobre un nivel que copia coincidencias de un historial de 2.000.000 de bytes; Windows Vista SP1/Server 2008 y posteriores). `Bulk.php` elige por el tipo de cada bloque y crea cada historial la primera vez que se usa. Medido con los mismos 11,1 MB de actualizaciones de pantalla de xrdp comprimidos con los compresores de FreeRDP: MPPC 3,05 MB y 0,53 s de CPU de la pasarela, NCRUSH 4,85 MB y 0,93 s, XCRUSH 2,08 MB y 0,32 s; navegador 0,09/0,18/0,06 s. XCRUSH necesita unos 4 MB más de memoria en la pasarela y 2 MB en el navegador. La pasarela lo descomprime para mantener el historial común y leer las PDU lentas, pero reenvía las actualizaciones **tal como llegan** (tramas 10 y 11); el worker (`bulk.js`) lleva un historial idéntico, descomprime, une los fragmentos fast-path y pasa las actualizaciones lentas a la forma fast-path. Por los dos tramos viajan datos comprimidos. Los canales virtuales se abren sin `CHANNEL_OPTION_COMPRESS_RDP`, así sus datos nunca llegan comprimidos.
- **Canal gráfico** (opción «Gráficos», MS-RDPEGFX; nunca con RemoteApp, donde cada ventana llegaría en una superficie propia; AVC444 y AVC444v2 se muestran a partir de su flujo 4:2:0): en modo automático `Client` lo activa (a 32 bits) si la versión de Windows del desafío NTLM es 6.3 o posterior. `Drdynvc` abre el canal `Microsoft::Windows::RDS::Graphics`, anuncia las capacidades 10.7 (sin mapeo escalado) y 8.1 con AVC420 solo si el navegador decodifica H.264 (comprobado con `VideoDecoder.isConfigSupported`), y 8.0, y reenvía cada mensaje sin tocarlo (trama de tipo 9). El worker (`rdpgfx.js`) descomprime ZGFX, analiza las PDU y decodifica: AVC420 con WebCodecs (se reescribe el SPS para declarar BT.709 de rango completo y sin reordenación de fotogramas; si no, los navegadores suponen rango limitado y pueden retener fotogramas), RemoteFX y RemoteFX progresivo (`rfx.js`: RLGR1/3, decuantificación, DWT inversa normal y «reduce-extrapolate», pasadas de mejora; las teselas de un mensaje van a una caja que abarca sus rectángulos o, si los rectángulos están dispersos (la caja ocuparía más del doble de su área), a una caja por rectángulo (`#region`): dos esquinas de la pantalla ocupan 33 KB en vez de 8,3 MB), ClearCodec (residual, bandas con cachés de barras, subcódecs NSCodec/RLEX; la caché de glifos vive con las superficies), planar, sin comprimir y alfa. Las operaciones mantienen su orden: las que siguen a un fotograma H.264 esperan al decodificador. El hilo principal (`gfxsurfaces.js`) tiene un canvas por superficie y la caché de superficies, y copia las superficies asignadas al canvas del escritorio; una operación de varias zonas (un relleno, copias, un fotograma H.264) las pinta todas en la superficie, un fotograma H.264 una sola vez a través de todas sus zonas (cada vez que se pinta un fotograma se convierte entero: 7 ms a 1920 × 1080 sin tarjeta gráfica), y después las copia al escritorio; un fotograma que no se puede pintar deja su superficie sin recorte y se cierra. Cada fin de fotograma se confirma (mensaje de tipo 10; solo se envía la última confirmación pendiente), que es el control de flujo del servidor. Requiere 32 bits (se fuerza). En los datos core se activa `RNS_UD_CS_SUPPORT_DYNVC_GFX_PROTOCOL`.
- Varias pantallas: el escritorio remoto se dibuja en una superficie fuera de pantalla y cada ventana (una por pantalla) copia la región de su monitor en el siguiente fotograma de esta ventana o, mientras está oculta (minimizada, tapada, otra pestaña: una página oculta no recibe fotogramas), de una ventana de la sesión que se vea. Una pantalla es monitor remoto solo mientras su ventana está abierta (`RdpSession.setMonitors`, `#wanted`, `#checkMonitors`): la nueva disposición va como mensaje del navegador de tipo 13 (JSON `[[x,y,an,al,principal],…]`, comprobado por `Drdynvc::monitors`) en una sola disposición de Display Control, como cambio de tamaño normal si queda una, o reconectando sin Display Control; hasta que el servidor la acepta, esa ventana sale en negro y no envía entrada. Pantalla completa pide `requestFullscreen({ screen })` y abre las demás ventanas en el mismo clic (`fullAndOthers`).
- Captura: `RdpSession.areaOf` pasa el recuadro dibujado sobre el canvas a píxeles del escritorio; `capture` hace el PNG a tamaño real, sin barra ni puntero.
- **Límites ante datos corruptos u hostiles** (encontrados con `tests/fuzz.mjs`), para que un tamaño tomado de los datos no haga reservar memoria sin límite al navegador:
  - Mapas de bits (actualizaciones y los guardados en caché) no mayores que el escritorio redondeado a teselas enteras de 64x64, y con una profundidad válida: la pasarela envía el tamaño del escritorio (trama 2) antes de cualquier actualización, así que el límite se conoce a tiempo.
  - Superficies y salida gráfica de hasta 32766 px por lado, el máximo de RDP: ahí el tamaño del escritorio no sirve de límite, porque una sola superficie puede abarcar todos los monitores.
  - Cada rectángulo dentro de su superficie y cada subcódec de ClearCodec dentro de su rectángulo (como hace FreeRDP); índices de cuantizador comprobados en RemoteFX y progresivo; se controlan el final de cada plano de NSCodec y un SPS en los últimos bytes de un bloque H.264.
  - Aún posible: un servidor hostil puede hacer que el navegador guarde superficies de hasta 4 veces la salida (como mucho 8192 × 8192), en el peor caso 1 GB; por encima, el navegador falla con un error registrado.

## Modelo de seguridad

- **Acceso**:
  - Instalación: la cuenta de administrador solo se crea con el código de un solo uso de `data/setup-code.php` (tras `<?php exit; ?>`), así nadie puede adueñarse de una copia recién subida.
  - Contraseñas: bcrypt coste 12 (≈0,27 s), al menos 12 caracteres, que no esté entre las ≈30 000 contraseñas comunes de esa longitud (`src/common-passwords.txt`) ni contenga el nombre de usuario.
  - Fuerza bruta: los fallos se cuentan por IP, por usuario, por navegador conocido y en total (todas las IP). Una IP bloqueada no entra. Un usuario bloqueado, o más fallos totales que `login_global_max` (un ataque repartido), solo deja entrar desde navegadores donde ese usuario ya entró (*cookie de dispositivo* firmada, que se anula al cambiar la contraseña), así un atacante no puede dejar fuera al dueño. Cada navegador conocido tiene su propio contador y bloqueo de intentos; una vez bloqueado se le aplican los bloqueos normales, así una cookie de dispositivo robada no da más intentos que el bloqueo por usuario. Se guardan los 20 navegadores usados más recientemente (en la ficha del usuario); cada alta queda en la auditoría (`device_add`) y el usuario puede olvidarlos desde su perfil.
  - Toda respuesta de acceso (contraseña, TOTP, passkey) tarda 1 s (se espera hasta que pasa el segundo midiendo con `hrtime`: `usleep()` puede despertar antes), salvo la de una IP bloqueada, al momento (no dice nada de los usuarios), y usuario inexistente, contraseña mala, cuenta desactivada y bloqueo dan el mismo mensaje: no se pueden averiguar usuarios por tiempos ni por textos. Dentro de ese segundo se leen de la auditoría el último acceso y los fallos desde entonces para el aviso al entrar (como mucho 90 días atrás; peor caso 73 ms, lo normal 5 ms).
  - Segundo factor (opcional, u obligatorio si lo decide el administrador, que debe tenerlo antes): TOTP (RFC 6238; cada código se acepta una sola vez, también el que lo activó) o una passkey. Cuando es obligatorio, quien no lo tiene solo llega a su perfil hasta que lo añade.
  - **Passkeys** (WebAuthn, `WebAuthn.php` + `Cbor.php`, PHP puro + OpenSSL): ES256/RS256, verificación de usuario obligatoria, desafíos de un solo uso, origen e id del sitio comprobados y contador de firmas vigilado. Con la extensión PRF el secreto de la passkey (HKDF) envuelve la clave de datos, así puede sustituir a la contraseña; sin PRF solo sirve como segundo paso. Resisten el phishing: una passkey solo funciona en su propio sitio.
  - **Cuentas de empresa**. *OpenID Connect* (`Oidc.php`, `public/oidc.php`): flujo de código de autorización con PKCE (S256), client_secret_post; el state, el nonce y el verificador en una cookie propia (`MUDESKOIDC`, cifrada con la clave del servidor, `SameSite=Lax`, 10 minutos: la redirección del proveedor no trae la cookie de sesión Strict), de un solo uso; la configuración y las claves del proveedor por HTTPS con comprobación de certificado, guardadas una hora (`data/oidc.json`, pedidas otra vez ante un id. de clave nuevo); del token de identidad se comprueban la firma RS256/RS384/RS512 o ES256/ES384, el emisor, la audiencia (y `azp` si viene), las horas (`iat` obligatorio, y todas números; 2 min de margen) y el nonce. La sesión no tiene clave de datos, así que no se abren las contraseñas RDP guardadas, y el segundo paso que exige el administrador es el del proveedor. *Cuentas de Windows* (`WindowsLogin.php`): X.224 pidiendo NLA, TLS (el certificado del equipo debe ser el fijado cuando el administrador lo guardó, `ad_cert`: NTLM demuestra la contraseña a quien la conozca, así que un equipo que se hiciera pasar por el del dominio daría cualquiera por buena) y CredSSP con NTLMv2 contra el equipo de los ajustes, que se detiene cuando el servidor ha contestado el enlace de la clave del cliente (`CredSsp::authenticate(..., delegate: false)`: nunca se envían las TSCredentials con la contraseña); una conexión cortada es una contraseña errónea, como hace Windows. La clave de datos de un usuario de Windows se envuelve con su contraseña de Windows; si cambia, se crea una clave nueva y se olvidan las contraseñas RDP guardadas.
- Sesiones: id nuevo al entrar, límites por inactividad y absoluto (12 h; la petición que cierra una sesión caducada responde `{"error":"auth","reason":…}`, también si no pasaría la comprobación CSRF, porque el token se fue con la sesión; `session.left` dice cuánto le queda sin contar como actividad; `state` devuelve `session: {idle, max}`, así la página solo pregunta `session.left` cuando la sesión debería terminar y entonces muestra *Sesión caducada* con el motivo), ligadas al navegador (agente de usuario: una cookie robada falla en otro navegador y cierra la sesión; no se usan los idiomas porque los Web Workers pueden enviar otros), y al cambiar la contraseña se cierran las demás sesiones del usuario (versión de sesión). Las sesiones remotas abiertas desde una sesión web terminan con ella (salir, caducar o cerrarla la pasarela: `Sessions::killWeb`, cada una registrada con el id de su acceso, `wid`); un cambio de contraseña termina las de los otros accesos del usuario (`Sessions::killUser` conservando este `wid`) y la página dice *sesión cerrada*; salir en una pestaña avisa a las demás de ese navegador (`BroadcastChannel`), que terminan las suyas. Una sesión remota comprueba cada 15 s que su cuenta sigue existiendo y activa. La contraseña pedida de nuevo dentro de una sesión (añadir una passkey o una app de autenticación, cambiar la contraseña, quitar un segundo factor: `Auth::confirmPassword`) la cierra tras 5 errores (`reason: reauth`); no usa los bloqueos de acceso, que un ataque al nombre de usuario podría mantener.
- Las contraseñas temporales que pone el administrador se cambian obligatoriamente al entrar.
- Contraseñas remotas: AES-256-GCM con una clave de datos por usuario. Esa clave se envuelve con otra derivada de la contraseña del usuario (PBKDF2-SHA256 calculado por OpenSSL, 400 000 iteraciones; una clave envuelta con menos, como hasta la 1.0.0, se vuelve a envolver en el siguiente inicio de sesión con contraseña). Durante la sesión la clave de datos se guarda cifrada en la sesión PHP con una clave aleatoria que solo está en una cookie HttpOnly: ni el fichero de sesión ni la cookie por separado la revelan. Si el administrador restablece la contraseña, las contraseñas remotas guardadas se vuelven ilegibles y se borran.
- Web: token CSRF en toda petición que cambia datos, cookies `SameSite=Strict`, Content-Security-Policy estricta (`'self'`, más imágenes `data:`/`blob:` y marcos `blob:`), HSTS, HTTPS obligatorio, lista blanca de IPs cliente. La API responde 400 `invalid_input` si un campo trae una lista u objeto en vez de texto o un número (también `rdp.php`), y 404 `not_found` para lo que no existe. Un cuerpo JSON se lee hasta 4 MB, lo que dice su `Content-Length` (como la entrada), y se decodifica una vez (413 `too_large` si pasa: `post_max_size` de PHP no lo limita, y una lista de 8 MB decodificada dos veces antes de iniciar sesión ocupaba 150 MB). Los mensajes de PHP nunca llegan al navegador, aunque `display_errors` esté activado: van al registro de errores del servidor, y el visitante ve una página propia (`ErrorPage.php`), sin rutas ni trazas; las trazas de error no llevan argumentos (`zend.exception_ignore_args`, contraseñas marcadas `#[\SensitiveParameter]`). Los valores de la dirección se leen solo como texto (una lista como `p[]=x` se ignora). `files.php`, `rdp.php` y `api.php` (salvo `state`) rechazan una petición sin cookie de sesión antes de crear un fichero de sesión. Las peticiones desde 127.0.0.1 se saltan la comprobación de HTTPS salvo que esa dirección sea un proxy de confianza, cuyo `X-Forwarded-Proto` decide entonces. Al salir se envía `Clear-Site-Data: "cache"`. Los elementos arrastrados entre ventanas de la aplicación llevan una clave de ese navegador (`localStorage`): otra página no puede hacer que soltar algo mueva archivos.
- RDP: lista blanca de destinos (IPs, CIDR, nombres, `*.dominio`); el DNS se resuelve una vez y se usa la dirección comprobada; un nombre que no resuelve se rechaza como destino no permitido. Los nombres pasan por el resolutor del sistema (no por uno propio, que rompería el fichero `hosts`, los dominios de búsqueda y la resolución de nombres de Windows). Con «Todo permitido» se comprueban todas las direcciones del nombre y la pasarela nunca se conecta a sí misma (127.0.0.0/8, ::1), a direcciones de enlace local (169.254.0.0/16, con los metadatos de nube, y fe80::/10) ni a 0.0.0.0/8 y ::, tampoco como IPv4 dentro de IPv6 (::ffff:…, ::a.b.c.d, NAT64 64:ff9b::/96), ni a las otras direcciones de metadatos de la nube (100.100.100.200, fd00:ec2::254); solo se llega a ellas poniéndolas en la lista, y Administración avisa mientras esté en «Todo permitido». En la lista, un nombre exacto llega a lo que resuelva; una regla `*.dominio` confía en el DNS de todos los nombres que cuelgan de él, así que por ella también se rechazan esas direcciones. Fijación del certificado del servidor en el primer uso con aviso si cambia (el de una conexión manual, que no se guarda, para el usuario y ese equipo: `data/hosts/<uid>.json`); comprobación de la clave pública en NLA; un protocolo que el servidor elige sin haberlo ofrecido (RDSTLS, NLA extendido) termina la conexión. La seguridad RDP estándar (Windows XP, Server 2003), solo con la seguridad *Automática*: la clave del servidor se fija como un certificado (un equipo fijado con TLS que ahora solo ofrece esto es un certificado cambiado), se rechaza una clave con la que RSA no es de fiar, un servidor que no cifra nada se rechaza antes del Client Info (`rdp_unencrypted`: la contraseña iría sin cifrar), las PDU sin cifrar se rechazan desde el nivel *Compatible con el cliente* (salvo las de licencias), y el cifrado usado queda en `rdp_start` (`rdp_security`); en el nivel *Bajo* lo que envía el servidor no va cifrado (ver [SECURITY](../../SECURITY.md)).
- Carpeta compartida: una sola cuota por usuario para la unidad de todas sus sesiones, el gestor de archivos web y los ficheros del portapapeles. El contador (`files/<uid>.quota`) lo cambian bajo su propio bloqueo todas las formas de escribir, así que juntas no pasan de la cuota; se vuelve a contar desde la carpeta al abrir o actualizar el gestor de archivos sin ninguna sesión del usuario en marcha, recorriéndola fuera del bloqueo del contador; cualquier otro listado de una carpeta muestra el contador, sin recorrer la carpeta (eso tardaba de 7 a 17 s con 20 000 archivos) (abrir la unidad con 3000 ficheros pasó de 205–238 ms a 0,2–1,4 ms). Los nombres de más de 255 bytes y los nombres de dispositivo de Windows (CON, NUL, COM1, LPT¹, CONIN$… con cualquier extensión) se rechazan (400 `invalid_path`).
- Gestor de archivos (`files.php`): toda ruta pasa por `Files::clean` (sin `..` ni nombres de archivos de configuración) y tiene que quedar dentro de la carpeta del usuario una vez seguidos los enlaces (`Files::confined`, también en la unidad remota): MuDeskClient no crea enlaces, pero uno puesto ahí por otra cosa (una copia de seguridad restaurada, un programa del servidor; un enlace simbólico, o una unión de Windows, que `is_link()` no ve) nunca se sigue, y los recorridos de una carpeta (borrarla, su ZIP, la cuota) nunca entran en uno (`Files::isLink`). Mover y cambiar de nombre no sale de la carpeta del usuario, nunca pisa algo ni mete una carpeta dentro de sí misma. El árbol lee solo las carpetas abiertas (recorrerlas todas tardaba 2,4 s con 1.000 carpetas y 20.000 archivos en Windows; las abiertas, 64 ms). Acciones: `list` (con la cuota), `tree` (hasta 200 carpetas abiertas), `move`, `mkdir`, `mkdirs` (hasta 1000), `upload`, `delete`, `download` (`view=1`: miniaturas), `zip` (antes `check=1`, con los nombres en el cuerpo, hasta 10 000, con CSRF; el id de la respuesta lo descarga, `z=`, guardado en la sesión). `delete` y `move` esperan a que termine de escribirse un trozo de subida (con `move`, un archivo subido mientras tanto a su destino quedaba sustituido), como los archivos del portapapeles. Varios elementos o una carpeta se descargan en un ZIP escrito mientras se envía (`ZipStream`: sin compresión, el CRC de cada archivo se lee justo antes, así la longitud se conoce de antemano y no hay descriptores de datos; sin copia temporal; hasta 4 GB, 65.535 entradas y 64 carpetas de profundidad, si no `too_big`, que la página pregunta antes). Las miniaturas solo se sirven para tipos de mapa de bits, en línea y con `Content-Security-Policy: default-src 'none'; sandbox` (nunca SVG ni HTML), revalidadas cada vez (`Cache-Control: private, no-cache`, `Last-Modified`, 304). Los documentos impresos (MuDeskPDF, hechos por el equipo remoto) se envían con la misma política y como descarga.
- Datos: `data/` fuera de la raíz web, o dentro de ella negada por `.htaccess`/`web.config` (se reescriben si faltan) con una comprobación desde el navegador que avisa al administrador si se puede leer; clave del servidor en un fichero PHP que termina al momento; escritura atómica con bloqueos. Un fichero de datos dañado o vacío, o que no es un objeto ni una lista JSON (`null`), se para con un error que lo nombra (un `users.json` vacío nunca se toma por un primer arranque); solo los intentos fallidos de inicio de sesión (`ratelimit.json`) empiezan de nuevo, guardando aparte el dañado. El último administrador activo y que los nombres de usuario no se repitan se comprueban bajo el bloqueo de los usuarios, y un paso TOTP se toma bajo él (dos inicios de sesión con el mismo código a la vez pasaban los dos). Los ajustes se guardan como lo que cambia cada petición, escrito sobre los guardados bajo su bloqueo (dos administradores que guardaban a la vez perdían el cambio de uno).
- Auditoría: una línea JSON por evento en un fichero por día; cada línea lleva el HMAC (clave del servidor) de su contenido y el de la anterior, así que *Verificar integridad* detecta ediciones, inserciones y borrados (los días purgados se esperan al principio). La comprobación termina donde estaba el registro al empezar (días, tamaño del fichero más nuevo y su última línea, tomados bajo el bloqueo de los escritores), así que lo escrito mientras tanto queda para la siguiente. Nunca se registran contenidos ni contraseñas. La exportación (hasta 20 000 filas) se envía fila a fila, cada fila tal como está guardada (unos 20 MB de memoria en vez de unos 71 MB). La exportación JSON va firmada con una clave RSA 3072 del servidor (`data/audit-key.php`, creada una sola vez en la primera exportación JSON o al abrir su panel): el SHA-256 se calcula por partes mientras sale el fichero, sin copiarlo, y al final se firma con PKCS#1 v1.5, que es lo que comprueba `openssl dgst -sha256 -verify`. RSA permite firmar un hash calculado así; medido: 0,21–0,23 s para 20 000 filas (0,32–0,36 s la exportación sin firmar de antes), 19–20 MB. Escribir cuesta unos 0,13 ms por evento (bloqueo + añadir). Las peticiones rechazadas de alguien sin sesión se escriben como mucho 100 veces por hora y dirección y 5000 en total (`Audit::anonymous`, luego una línea `audit_limited`). Los días se leen línea a línea, hacia atrás en bloques de 1 MB (un día de 60 MB: 3,7 MB de memoria en vez de 128 MB); *Verificar integridad* enumera los 1000 primeros problemas y los cuenta todos. La búsqueda lee los días del rango del más nuevo al más antiguo y solo decodifica las filas que se muestran (medido con 2 000 eventos/día: 90 días en unos 0,1 s, un año en unos 0,4 s, 4 MB de memoria; verificar un año, 3,4 s).
- **Conexiones del administrador** (`Connections::saveManaged`): asignadas a usuarios que no pueden cambiarlas ni borrarlas. El administrador nunca pone ni lee la contraseña de un usuario (cifrada con la clave de ese usuario); cuando cambia el destino de una conexión (equipo, puerto, usuario, dominio, seguridad), se olvidan las contraseñas que los usuarios guardaron para ella y su certificado de confianza, también en una conexión propia de un usuario cambiada por el administrador, para que una contraseña escrita para un servidor nunca llegue a otro.
- **Límites de lo que un servidor RDP hostil o defectuoso puede hacer guardar a la pasarela o a la página**:
  - Pasarela: un mensaje de canal de hasta 64 MB con la longitud que anunció su primer trozo; mensajes de canales dinámicos de hasta 64 MB, 8 a la vez en reconstrucción; el historial de XCRUSH vuelve al principio solo cuando está lleno; el socket se lee de 4 MB en 4 MB y una escritura que no termina en 30 s (o 15 s sin poder escribir) termina la conexión; un escritorio de hasta 32766 por lado y 8192 × 8192 píxeles; el portapapeles remoto se guarda hasta 16 MB; los trabajos de impresión, hasta 200 MB por sesión; la unidad: 1024 identificadores abiertos (64 archivos abiertos), 20 000 entradas nuevas y 2000 líneas de auditoría por sesión, las máscaras con más de 4 `*` no coinciden con nada; se rechazan las lecturas y escrituras de la unidad en posiciones de 2^63 o más, o que terminan más allá; se rechazan los literales NCRUSH más allá de su histórico de 64 KB (como los rechaza la página); de los formatos de audio, solo los que la página reproduce (1 o 2 canales, 8–192 kHz, bloques IMA ADPCM de grupos enteros); los mensajes en espera de una sesión hasta 16 MB; las trazas de diagnóstico hasta 256 MB en total; el micrófono solo en PCM de 16 bits de 1 o 2 canales a 8–48 kHz, en paquetes de 10 ms a un segundo pida lo que pida el servidor (una muestra por paquete daba dos mensajes por cada 2 bytes), con como mucho un segundo de audio esperando, y un Format Change antes del Open descartado (no tenía tamaño de paquete: un bucle sin fin); de una puerta de enlace de Escritorio remoto, las cabeceras HTTP dentro de 64 KB y los cuerpos hasta 1 MB, y 8 de sus mensajes de servicio guardados; por el transporte RPC, la respuesta de una llamada hasta 1 MB y solo de las llamadas que se esperan, y la respuesta HTTP de un canal OUT nuevo dentro de 64 KB; los campos de la redirección de un agente se leen hasta su primer nulo (un patrón sobre una larga serie de ceros se rendía); las imágenes de la cámara hasta 2 MB cada una (solo se guarda la más nueva), como mucho 64 Sample Request esperando; la carpeta de este equipo: 4096 peticiones esperando al navegador (sus avisos de cambios aparte, otros tantos), cada ruta guardada para la auditoría hasta 1024 caracteres, sus listados dentro de los 200 000 nombres y 32 MB guardados.
  - Página: ZGFX con un único búfer del tamaño declarado (hasta 64 MB); las superficies del canal gráfico dentro de 4 veces la salida, su caché de mapas de bits dentro de 100 MB y cada hueco dentro de su superficie, los glifos de ClearCodec como los permite el códec; las cachés de mapas de bits de las órdenes de dibujo dentro de las celdas ofrecidas (600, 600 y 1024 entradas de 256, 1024 y 4096 píxeles); no se acepta un escritorio de más de 32766 por lado o 8192 × 8192 píxeles; se rechazan las imágenes del portapapeles cuya cabecera dice más de lo que traen (el largo de fila contado sin desbordar 32 bits) y los trozos de archivos remotos que pasan de su tamaño; un ZIP de archivos remotos hasta 65 535 entradas y 4 GB (sus límites sin ZIP64); las tramas del flujo hasta 128 MB, con su longitud leída sin signo (una longitud de −5 dejaba el worker en un bucle sin fin); los trozos de audio de un formato que no puede reproducir y los mapas de bits o rectángulos sin tamaño se descartan, sin lanzar.

## Estructura de datos (`data/`)

```
users.json                 cuentas (hashes, claves de datos envueltas, semillas TOTP cifradas con la clave del servidor, passkeys,
                           navegadores conocidos)
settings.json              ajustes del administrador
connections/<uid>.json     conexiones de cada usuario; con un id que empieza por "m", lo que el usuario guarda de una
                           conexión del administrador (su contraseña, certificado y opciones al conectar)
managed_connections.json   conexiones del administrador, cada una con sus usuarios (ids, o "*": todos)
hosts/<uid>.json           certificados de los equipos a los que cada usuario llegó con conexiones manuales (estas nunca se
                           guardan: van en la sesión web, con ids que empiezan por "o", y solo para quien puede crear conexiones)
oidc.json                  la configuración y las claves del proveedor de OpenID Connect (guardadas una hora)
secret.php                 clave del servidor (semillas TOTP, el HMAC de la cadena de auditoría, las cookies de los navegadores
                           de confianza), tras <?php exit; ?>
audit-key.php              clave RSA de las exportaciones firmadas de la auditoría, tras <?php exit; ?>
.htaccess, web.config,     niegan el acceso web (Apache/LiteSpeed/OpenLiteSpeed e IIS;
index.html                 se reescriben si faltan)
setup-code.php             código de un solo uso de la instalación (se borra al crear el administrador)
web-check.txt              el navegador intenta leerlo para detectar una carpeta expuesta
ratelimit.json             intentos fallidos
auditlimit.json            peticiones rechazadas de quien no ha entrado, contadas por hora
*.json.lock                bloqueo de cada almacén JSON
audit/AAAA-MM-DD.jsonl     auditoría, un fichero por día (.last: hash de la última línea; .lock)
sessions/                  sesiones PHP
run/                       sesiones RDP en curso (registro, sockets, colas, register.lock)
tmp/<sid>/                 subidas del portapapeles y trabajos de impresión de una sesión (se borran al terminar)
tmp/upload-<uid>.lock      las subidas, movimientos, borrados y archivos del portapapeles del usuario, uno a la vez
trace/<sid>.log            trazas de diagnóstico (se borran a los 7 días)
recordings/<sid>.rec       grabaciones de sesiones, cifradas (<sid>.json: quién, conexión, horas, tamaño); se borran pasados
                           los días de los ajustes
files/<uid>/               carpeta compartida de cada usuario
files/<uid>.quota          bytes contados en la cuota del usuario
```
