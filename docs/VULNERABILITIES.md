# Known vulnerabilities of RDP clients, checked

MuDeskClient implements the Remote Desktop Protocol itself (the gateway in PHP, the pictures, sound and files in the browser), so the faults found over the years in other RDP clients could be in it too. In November 2026 every one published by official sources was looked for in its code, one by one: the vulnerabilities of RDP clients that INCIBE-CERT, CISA, CERT-UA, Microsoft and the NVD list, the research behind them (Check Point's *Reverse RDP*, CyberArk's), and all of FreeRDP's security advisories (348, from 2020 to November 2026: FreeRDP is the most used open-source RDP client, and its advisories cover every part of the protocol).

Each one is here with what it was and how MuDeskClient stands: **not applicable** (code MuDeskClient does not have: a server, a proxy, a channel it never implements), **covered** (its code already prevents it: where), or **fixed in this review** (it was there, or something close to it: fixed for the version after 1.2.0, each fix with a test that fails without it). Memory corruption as such (buffer overflows, use after free) cannot happen in PHP and JavaScript; its equivalents here are reading past the data, allocations or loops without a limit, and names or paths that leave their folder, and those were looked for.

## A malicious server attacking the client

Connecting to a computer someone else controls (or to one impersonated by someone in between) lets it send whatever it likes: the vulnerabilities below were all of that kind.

| Vulnerability | What it was | MuDeskClient |
|---|---|---|
| CVE-2019-0887, CVE-2020-0655 (Microsoft's client, Check Point's *Reverse RDP*) | file names in the clipboard with `..\` (and `../`, which got past the first fix) wrote files anywhere on the client | covered: a remote copy's names stay inside the copy (`Cliprdr.php`); **fixed in this review**: also the look-alikes of `/ \ : .` that some unzippers turn into real ones, streams (`:`), device names and what Windows refuses (`Files::zipName`, `zip.js`) |
| CVE-2025-26645, CVE-2025-48817 (Microsoft's client, relative path traversal, CVSS 8.8) | a server reached files outside the folder it was given | covered: every path of the shared folder is checked by name (`Files::clean`) and once links are followed (`Files::confined`), and a folder of this computer goes only through the handle the user chose (`localdrive.js`); **fixed in this review**: a Windows junction that leads nowhere, deleting or renaming the folder itself, and names Explorer acts on (`desktop.ini`, `.url`, `.lnk`...) created in this computer's folder |
| CVE-2025-29966, CVE-2025-29967, CVE-2025-27487, CVE-2025-58718 (Microsoft's client: heap overflow, write out of bounds, use after free) | code execution on the client from a server's answers | not applicable as such (PHP and JavaScript); their equivalents (allocations, loops and reads driven by the server) reviewed in every decoder and channel: see FreeRDP below |
| CVE-2018-8791 to CVE-2018-8800, CVE-2018-20174 to CVE-2018-20182 (rdesktop 1.8.3, Check Point) | 21 faults in bitmaps, device redirection, sound, clipboard, CredSSP and the planes of a picture | covered: every reading of the server's data is bounded (`Reader`, `Der`), each length checked before it is used, the pictures' sizes limited (`gfx.js`, `Client::SIDE_MAX`) |
| CVE-2019-0708 (*BlueKeep*, the server) | a client asking for the channel `MS_T120` ran code on the server | not applicable to a client; MuDeskClient never asks for that channel (its channels are a fixed list, `rdp.php`) |

## The connection's security

| Vulnerability | What it was | MuDeskClient |
|---|---|---|
| CVE-2005-1794 (Standard RDP Security: the key Microsoft signs its servers' keys with is public) | someone in between posing as the server | covered: the server's key is pinned as a certificate and confirmed the first time; **fixed in this review**: the encryption level, which nothing authenticates, goes into the pin (lowered to 1 by someone in between, what he sent in the clear was taken, even a redirection to his computer with the user's password), and a redirection sent in the clear is not followed (`RdpSecurity::pin`, `Client.php`) |
| Taking TLS away (someone answering for the computer that it only speaks the old security) | the password encrypted to the attacker's key | **fixed in this review**: refused for a computer seen with TLS within a year (before, asked as a changed certificate); one changed on purpose: its certificate forgotten in the connection (`Client::notDowngraded`, `Transport::hadTls`) |
| Taking NLA away, or TLS 1.2 | the password in the session instead of NLA; a weaker TLS | covered: the protocols the server says it was asked for are compared with those asked (`Client::mcsConnect`), TLS 1.0 only to a computer never seen with 1.2 (`tls.json`), *NLA only* for computers that have it |
| CVE-2018-0886 (CredSSP without the 2018 update) | someone in between taken for the computer used the session's key against it | covered: refused, as Windows does, unless `credssp_unpatched` (`CredSsp.php`) |
| NTLM relayed to another service | the user's answer used elsewhere | covered: NTLMv2 only, with MIC; **fixed in this review**: the channel bindings and the computer's name always sent (before, only when the server sent a timestamp) (`Ntlm.php`) |
| Kerberos messages replayed or out of order (RFC 4121) | a sealed message of the server taken twice or late | **fixed in this review**: NLA asks for replay and sequence detection and checks each sealed message's number (Windows numbers them 0 when not asked); tried on Windows Server 2022 with AES and RC4 (`Kerberos.php`) |
| TLS 1.0 without secure renegotiation (Windows 7 and Server 2008 R2 as first released) | OpenSSL 3 refuses such a server, and PHP sends empty records that its TLS refuses: they could not be reached | **fixed in this review**: TLS 1.0 made by MuDeskClient itself for them (ECDHE offered first, never renegotiating, records split 1/n-1 against BEAST once NLA is done; `LegacyTls.php`); tried on Windows Server 2008 R2 |

## Malicious .rdp files

In October 2024 CERT-UA and CISA warned of thousands of emails with .rdp files that connected to the attacker's computer with the victim's drives, clipboard and devices shared; Microsoft answered in April 2026 (CVE-2026-26151): a file it cannot verify shows its destination and every sharing it asks for, all off. **Fixed in this review**: importing a file never turns on the clipboard, the shared folder, the printer, the microphone or the camera; what it asked for and its gateway are said in the import notes, to be turned on by hand where the computer is trusted (`rdpfile.js`); an administrator's import is nobody's until the users are chosen, and the certificate box "valid for every user" comes unticked (`app.js`). The first connection to a computer stops for its certificate before anything is sent.

## Weaknesses of the remote computer itself

CVE-2022-21893 and CVE-2022-24533 (CyberArk): on a computer several people use at once, without the updates of January and April 2022, another user signed in there could take over what a session redirects (clipboard, drives). No client can fix that: keep the remote computers updated, and turn the redirections off for those you do not keep updated or do not trust ([SECURITY](../SECURITY.md)).

## FreeRDP's 348 security advisories

Every advisory FreeRDP published (GitHub, from 2020 to November 2026), read and looked for in MuDeskClient's equivalent code:

| Status in MuDeskClient | Advisories |
|---|---|
| Not applicable (FreeRDP's server, proxy or shadow server; channels MuDeskClient never implements: USB, smart cards, serial and parallel ports, video redirection) | 195 |
| Covered (its code already prevents it) | 144 |
| Covered within a limit (see below) | 1 |
| Fixed in this review (the same fault, or a close one, was there) | 8 |

Found by following FreeRDP's advisories and fixed in this review: a clipboard format list read to its end when one format repeats, and a file list without a limit (each up to 10 s of the gateway's CPU); the H.264 codec taken from a server where it was never offered (the pictures stopped); messages with up to millions of rectangles (H.264, RemoteFX) and glyph caches beyond those offered (the browser's tab frozen or out of memory); ZGFX messages shorter than they said; a negative length of a drawing order; the RD Gateway's WebSocket pings piling up their answers.

Within a limit: a server can make the page keep graphics surfaces of up to four times its desktop (with the largest desktop accepted, 8192 x 8192, about 1 GB): bounded, and the browser may refuse them; it never reaches another session's data. Tying them to the size asked for would break the resizes and several screens. Also bounded, with no data at risk: pixel-by-pixel drawing (ROP), 20 desktops a second.
