# Changelog

## 1.0.0 — 2026-11-20

First stable version. It gathers everything below since 0.1.0. Before it was released, three external audits, their second passes and a full review of our own (with the most weight on speed: the best picture with the smoothest motion) were checked against the code: what was real is fixed with a test that fails without the fix (checked by putting the old code back), what was not is said in [SECURITY](SECURITY.md) or left as it was, with the reason. The microphone came with it.

### Microphone
- **This computer's microphone on the remote one**: one more box of the connection and of the connect dialog, **off by default**. Windows shows it in the session as *Remote Audio* and opens it only while a program there records (a call, a dictation): the browser then asks once for the microphone and records until Windows closes it. Read and written in `.rdp` files (`audiocapturemode`). The remote Windows must allow audio recording redirection (Windows 10/11 and current Windows Server allow it unless a policy forbids it; Windows Server also needs its Windows Audio service): how to check it or turn it on, in [HOSTING](docs/HOSTING.md#remote-computers). Browsers only give the microphone to pages opened with `https://`; a refusal, no microphone or an `http://` page is said once on the page and the session goes on without it.
- In the connect dialog, an **ⓘ** beside the microphone explains that the browser asks for permission and how to allow audio recording on the remote Windows: the policy editor step by step (`gpedit.msc`, an MMC console), the registry command (`reg add "HKLM\SOFTWARE\Policies\Microsoft\Windows NT\Terminal Services" /v fDisableAudioCapture /t REG_DWORD /d 0 /f`) and, on Windows Server, the command that starts its Windows Audio service. Another **ⓘ** beside *Use all my screens* says what each browser asks: Chrome and Edge, the permission to manage windows on all the displays; Firefox and Safari, pop-ups allowed (this browser's first).
- Protocol (MS-RDPEAI, `src/Rdp/Audin.php`): the `AUDIO_INPUT` dynamic channel, `INFO_AUDIOCAPTURE` in the Client Info, only with the box ticked. The gateway answers Windows itself and at once (it waits 5 s at most for each answer, less than the browser may take to be allowed the microphone): the version, the formats (16-bit PCM only, sent as it is recorded), the open and later format changes. The audio goes in packets of the size Windows asks for, between 10 ms and a second, with at most a second waiting. Dynamic channel messages longer than one 1600-byte channel chunk (1598 bytes with a channel id under 256) now go as Data First + Data PDUs.
- In the browser (`mic.js`, `mic-worklet.js`): an audio worklet mixes the microphone to one channel, resamples it to the rate Windows asks for (with a low-pass filter first when the rate goes down) and turns it into 16-bit PCM; pieces of 100 ms go on the input's request slots, joined while one waits (at most a second, the oldest dropped).
- Measured on Windows 11 Pro: it asks for 44.1 kHz stereo in packets of 10 ms (176 KB/s upwards, only while a program records); in 30 s the page sent 29.0 s of audio and Windows got 29.3 s; its microphone test gave 99 % with Edge's simulated microphone ([PERFORMANCE](docs/PERFORMANCE.md#microphone)).
- Found by the new fuzz target (`tests/fuzz.php --target=mic`) before release: a server asking for 1 frame a packet made two messages for every 2 bytes (88,200 a second); a Format Change before the Open left no packet size and the browser's audio looped for ever.

### Speed: picture and input
- **Frames no longer wait for the gateway's decompression.** With bulk compression (Windows 7/2008 R2, xrdp, RemoteApp), the gateway decompressed every update before sending it on, only to keep its history in step (the browser decompresses them): each frame of a batch, and a key pressed meanwhile, waited 15 ms (MPPC) to 150 ms (NCRUSH). They are now sent first, the browser's input is read, and the history catches up after (`Client::catchUp`); a compressed slow-path PDU catches it up first, so it reads the same.
- **Frame acknowledgements while the mouse moves.** They were sent only when no mouse move waited: with a mouse kept moving and every request slot busy they waited up to 0.8 s (with 200 ms to the gateway), and Windows paces its frames by them, so the screen stalled while dragging. Mouse moves and acknowledgements now take 3 of the 4 request slots at most and take turns; a key or a click always has the fourth (it waited up to 120 ms behind moves).
- **Input on Windows servers** (XAMPP, IIS): the session's messages go through a TCP port of this computer only, with a secret of the session, instead of a queue file read every 20 ms (each key, mouse move and acknowledgement waited up to 20 ms).
- Only the last of the browser's coalesced mouse moves is placed (each one read the screen's position for nothing).
- **MPPC decompression** (Windows 7/2008 R2 and other servers that use it): its 64 KB history is kept as what was written since the last restart and what came before, instead of one string copied twice for each block: 15.5 to 9 µs for a 20-byte block, the same output.
- The list of common passwords (435 KB) is read once per process; the data files written on every failed sign-in or refused request (`ratelimit.json`, `auditlimit.json`) are written compact.
- **Scrolling and copies within the screen**: a canvas drawn onto itself makes the browser copy all of it first (6.7 ms for 64 × 16 pixels of 1920 × 1080). Every line a console scrolls (ScrBlt) and every graphics-pipeline copy within a surface now goes through a scratch canvas (12 µs): 600 console scrolls in an 800 × 600 window on a 1080p screen took 5.5–6.3 s of drawing, now 1.2–1.3 s.
- **RemoteFX progressive**: the areas its tiles wrote are put on the page as they are (they are opaque), instead of blending each update through a new canvas: the page's own thread spent 6.6–7.2 s on an animation that now takes it 2.0–2.6 s. Its decoding in the worker is 9–18 % faster (Golomb-Rice decoding without closures, only the non-zero coefficients dequantized, colour conversion in integers), with the very same pixels.

### Security and robustness
- **Shared folder: links never followed.** A symbolic link, or a Windows junction (which PHP's `is_link()` does not see), put into a user's folder by something else (a restored backup, a program on the server; MuDeskClient makes none) led out of it: over the web, from the remote drive, and deleting the folder that held it, its ZIP or the quota went into it (on Windows, deleting such a folder deleted what the junction led to). Every path must now stay inside the user's folder once links are followed (`Files::confined`), and walks of a folder never go into a link (`Files::isLink`).
- **Input of a session on Linux.** With Unix sockets (the default on Linux), a large message (a paste of some 200 KB or more) arriving in pieces while other requests came whole was mixed with them, and the session's input stopped for good. Each request's message is now kept apart until all of it has arrived.
- **Input token**: the session's file in `data/run/` keeps its SHA-256, not the token (a copy of the data folder gave the keyboard of a running session). A session started before the update keeps working.
- **Request size**: a JSON body is read up to 4 MB and decoded once (413 `too_large`): an 8 MB list sent to `api.php` before signing in was decoded twice and took 150 MB.
- **`rdp.php`**: a list where a text or a number goes is refused (`invalid_input`); it became the password "Array", with a PHP warning.
- **Administrators**: the last enabled administrator and unique user names are checked under the users' lock (two administrators demoting each other, or creating the same name, at once both did it). A disabled administrator can now be changed and deleted while a single one is enabled (it was refused as "last administrator").
- **User editor**: *Administrator rights* is a box, unticked for a new user (it was a *Role* list); there can be several administrators.
- **Data files**: a damaged or empty one stops with an error naming it (it was an anonymous JSON error, and an empty `users.json` looked like a first run); the failed sign-ins (`ratelimit.json`) start again, the damaged file kept aside. A store is deleted under its lock.
- **Passwords**: the rule counts characters, not bytes (three equal emojis, 12 bytes with 4 different ones, were accepted); 72 bytes at most as before.
- **TOTP**: the step is taken under the users' lock (two sign-ins with the same code at once both passed), and a code already used is no longer counted as a failure (a few of them, with a phone's clock ahead, locked the user's own address for 15 minutes).
- **A data key that the right password cannot open** (a damaged users file) is now audited (`saved_passwords_lost`) and logged; it was replaced in silence.
- **Targets**: a `*.domain` rule trusts the DNS of every name under it, so it no longer reaches this computer, link-local or cloud metadata addresses (an exact name still reaches what it resolves to).
- **Session ids** that are paths are never written or removed (`Sessions::send`, `cleanup`).
- **Connections**: a remote user changed from "0123" to "123" (or "007" to "7") kept the saved password and the pinned certificate (the fields of the target were compared loosely, and numeric texts were equal); compared strictly now.
- **Several screens**: hiding this window (minimized, another tab) stopped the server drawing while the other screen's window was still in view; it stops only when no window of the session is seen.
- **Reconnection**: requests of the connection before, still in flight, were counted as the new one's (the count went below 0, then 8 requests at once); and the lock keys (Caps Lock…) are synced again after it. After the first retry each wait gets up to half as long again at random: after the gateway restarted, every page tried again at the same moments and most found it busy.
- **User names in any alphabet** (NLA): NTLM puts the user name in upper case as Windows does, and only Latin and Cyrillic letters were: a name with lower-case Greek (or Armenian, Vietnamese, fullwidth...) letters was refused. The gateway now uses Windows' own table, taken from Windows 11 (973 letters), with the letters Windows leaves as they are (the final sigma, Georgian) left too; a test checks all 65,536 code units against it.
- **Audit search**: the text was looked for in the raw JSON line, so `event` or `true` found every line (the field names, the outcome) and a piece of a hash found its line, while quotes, a backslash, `reason=unknown_user` or `JOSÉ` for `josé` found nothing. It is now looked for in what a line shows (user, IP, event, browser and each detail as `key=value`), in upper or lower case of any alphabet. To keep it as fast, the lines are now counted in blocks (that pass took 40 % of a search) and a plain text is told on the raw line: on a day of 110,000 lines, no text 111 ms instead of 130, a user 137 instead of 158, a name 149 instead of 156, an event 184 instead of 199, a reason 166 instead of 162 (the same, within the noise); a one-letter text found on every line takes 329 ms instead of 229, since each line found is now checked.
- **Text sent to Windows** (user names, passwords, file names): a cut or invalid UTF-8 sequence took the bytes after it and became another character ("a\xC3" was "aÀ"); each bad sequence is now U+FFFD.
- **Connections of the administrator**: a user taken out of one kept their password and certificate for it, and got them back when given it again; they are forgotten now.
- **Touch**: a tap the browser cancels (a system gesture starting on the screen) was sent as a click.
- **Phone keyboard** hidden without leaving the field (Android's Back): the remote desktop stopped following the window's size.
- **Clipboard**: an image whose upload failed was never sent again (pasted again, the remote Ctrl+V pasted the old content).
- **Interface**: leaving a session's page by its address (Back, a link) left the remote session connected where nobody saw it; a double click on *Save* saved a new connection twice; a context menu closed with Escape left behind what closed the next one at its first press; with nothing to type in the connect dialog (the password saved), the focus was on the phone keyboard's ⓘ, so Enter opened its explanation instead of connecting (it is on Connect now).
- **Shared folder**: a list of a folder no longer walks the whole folder (7 to 17 s with 20,000 files, and under the quota counter's lock while a session ran): it shows the quota counter, and the folder is counted again when the file manager opens or is refreshed. A file replaced by a smaller version near the quota was refused. A folder removed during a walk, two first openings at once and a file that vanished during a list gave errors or warnings.
- **Administration**: saving a connection of the administrator read every user once per assigned user (38 s with 300 users) and rewrote every user's file; now one read, and only the files that hold it.
- **Sessions registry**: a session's file read while it was written was taken for a dead session and removed with its queue (its input got 404); written whole now (temporary file and rename), and only files not touched for a minute are cleaned up.
- **Passkeys**: a passkey updated by its place in the list (a passkey deleted meanwhile left a broken entry that made every later passkey sign-in of the user fail); found by its id now. Lists where its data has text (authData, the challenge, a key) gave PHP warnings.
- **PHP 8.5**: numbers past the int range in a request (`1e30`) gave "not representable as an int" warnings: read with `Http::int` everywhere.
- **Wide desktops**: with the graphics pipeline, a desktop of several monitors wider than 8192 px was drawn again only up to x 8192 after a layout change.
- **ZIP downloads**: a ZIP's list of names is used once and leaves the session (kept, 8 lists of 10,000 names weighed on every later request).
- **Audit**: refused requests of someone not signed in no longer rewrite the hourly counter once past the limit.
- **Error page after running out of memory**: sent by the shutdown function without calling `exit()` there, with a little memory to build it (PHP 8.1's built-in server stopped on that request at GitHub; it still does there, before any page is sent, and the test says so).
- **8-bit colour**: with a server capped at 8 bits, drawing-order colours are indexes of the palette (they were taken for red levels: every fill in the wrong colour). A palette update shorter than its header ended the session.
- **Shared drive (RDPDR)**: a read at or past the end answers nothing without seeking there (Linux refused positions past 2^63 − 1, and the test failed there), and a write ending past 2^63 is refused (it ended the session with a TypeError; on Linux, a position the system refuses wrote where the file was).
- **Audio**: only formats the page can play are taken (1 or 2 channels, 8–192 kHz, IMA ADPCM blocks of whole groups); the page drops a chunk of any other instead of throwing on each one.
- **NCRUSH**: literals past the 64 KB history are refused, as the browser refuses them.
- **Browser**: an impossible stream frame length (−5) made the worker loop for ever; lengths are read unsigned and limited to 128 MB, and the request is cancelled. A ZIP of remote files is refused past 65,535 entries or 4 GB (its counters wrapped into a broken file). A clipboard image whose row length overflowed 32 bits passed the size check. Bitmaps and graphics rectangles of no size draw nothing (they threw). The page works with the browser's storage blocked (it did not start).
- **Texts**: every error the gateway answers has its text in both languages (an upload whose file changed meanwhile showed "Error: offset"); "Cannot reach the remote computer" now names the firewalls to check, and so does `tools/check.php`.

### RemoteApp: a program of the remote computer on its own
- A connection can name a **program (RemoteApp)**: its path on the remote computer (`C:\Windows\System32\notepad.exe`) or the name it was published with (`Excel`), with arguments. The session then shows only that program's windows, each one where it is, over the page, without the remote desktop; the tab title follows its active window. Its windows are moved, resized and closed with their own title bars (drawn by the server), and the new **Windows** panel of the toolbar lists them, to bring one to the front (also a minimized one), minimize, maximize or close it.
- The published name is typed and shown without the `||` that Windows expects before it: the gateway adds them (`Connections::program`), but not to a path or a file name (`notepad.exe`). Shown in the editor, they looked like a mistake, and a name without them is refused as not allowed.
- Until the program's first window comes, a spinner in the middle of the page and the taskbar say it is opening (before, the page stayed empty and looked stuck); after 15 s, that it is taking longer than usual. Once its window came, the page no longer says it is opening when it closes: 3 s after its last window the session ends saying "The program was closed".
- Which windows count as the program: tool windows (a program starting showed a strip 4 px high and a hint window) and, until its first titled window, untitled ones (a splash screen) are not "the program is here": they ended the spinner, and the program's closing was then taken from them. The taskbar and the Windows panel list a window owned by one that is not shown here: a program's main window owned by a hidden window of its own (sent as 0xFFFFFFFE) was left out; a titled window of no size is not listed. Both seen in a real trace.
- A program that takes long to open is no longer cut off: the server ends a session that has no program some 12 s after it synced (error info 0x0B), also while the program is still starting. When that happens before the program's first window, the page connects again by itself, quietly (no "Disconnected", the spinner stays): its windows come back, or it is asked for again. 90 s after it was first asked for without a window, the session ends saying the program did not open, with **Reconnect**. For a few versions, an **Open** button came after 10 s, and "Disconnected" right after it: that button is gone.
- A **taskbar** at the bottom of the page has a button for each of the program's windows (the active one marked, a minimized one dimmed): a click brings a window to the front, also a minimized one, or minimizes the active one. Before, minimizing the only window left an empty page, and the way back was the Windows panel.
- Protocol (MS-RDPERP), on the gateway (`src/Rdp/Rail.php`):
  - The client asks for it (`INFO_RAIL`, Remote Programs and Window List capability sets, the `rail` static channel) only for a connection with a program. A server that does not offer it ends the session saying so (`app_unsupported`).
  - After the server's handshake: the client's handshake, its status and its system parameters, with the work area = the browser window less the taskbar (40 px; it follows the window, so maximized windows fill it and leave the taskbar in view).
  - The program is asked for (Client Execute) once the server has sent its windows: the browser reads the desktop order "arc completed" and tells the gateway, since the server only takes it then. Without that report it is asked for after 5 s, and once more if the server was not yet watching the desktop.
  - A program the server refuses ends the session with the reason in the page: not allowed (not in its list of allowed programs; the message says to check the published name or the path), not found, failed, session locked.
  - Reconnected after the connection dropped, the server is told (`AUTORECONNECT`) and the program is started again only if its windows did not come back with the desktop (the browser says how many are open when it reports it). Without that report it is left as it was. Connected again with **Reconnect**: with the browser's report, no second program if its windows came back; without it, after the program closed it is asked for after 5 s, and after any other end it is left as it was.
  - The icon caches announced never exceed the server's.
- In the browser:
  - The windowing orders (alternate secondary drawing orders, `TS_ALTSEC_WINDOW`) are read with the drawing orders (`orders.js`).
  - The remote desktop is drawn off screen and only the visible region of each window shown is copied to the page. The server does not paint what is outside its windows, so what stays there is old.
  - When the browser window changes size, what the remote desktop had is kept and the server is then asked to draw it all again (Refresh Rect, 0.4 s later). Before, the new size emptied it: the server moves its windows by copying from there, so after a resize they came back in mixed pieces.
  - Diagnostic mode records the server's first 120 window orders (titles only by their length), to look into how a program draws.
  - New browser message 14 (the browser's window commands, JSON); new gateway frame 12 (a window cloaked).
- Limits of this first version: drawn from bitmaps and drawing orders, without the graphics pipeline (each window of the pipeline comes on a surface of its own) or H.264; no icons in the Windows panel; the notification area of the program is not shown.
- The remote computer must allow it: Windows Server with Remote Desktop Services publishes RemoteApp programs; on Windows 10/11 Pro, programs can be allowed in its registry (see HOSTING).
- .rdp files of a RemoteApp are now imported as one (its program and arguments) and exported so (with the connection's name as the program's name).
- **On several screens** (*Use all my screens*, or *Full screen* on a computer with several): each window of the program goes to the window of the screen it is on, over that window's page. The session's screen is the remote primary monitor, even when it is not this computer's primary: the program opens there, beside its taskbar, and the work area sent (the taskbar left out) is that monitor's; the other monitors keep all of theirs. The program's windows come in the server's coordinates (its primary at 0,0, a screen at its left or above at negative ones) and are moved to the remote desktop's. Before, RemoteApp had one screen and did not offer more.
- **Closing the program ends the session**: when its last window closes (none shown or minimized for 3 s, so that a program may close its sign-in and open its main window; windows of no size, with nothing visible, hidden, cloaked or tool windows do not count: a program may keep some of those for a while as it closes, and they kept the session open for about 15 s), the browser disconnects and says "The program was closed", with **Reconnect**. Windows keeps the session (disconnected, as with Remote Desktop Connection), so the next connection to it is quick. Before, the page stayed connected and empty.
- **Reconnect** after the program closed is a new connection: the program is asked for again, unless its windows come back (it was still running). After any other end, Reconnect goes as a reconnection (the server is told) and the program is asked for only if its windows did not come back. It is asked for as soon as the server has sent its windows. Windows keeps some windows in every session, also before the program first opens: one of no size per screen and some hidden ones. They are not the program and are not counted (for a while they were taken for the program still closing: the page waited, and the server ended the session some 12 s later, error info 0x0B, as two traces of the user showed). Before, the button was taken for a reconnection after a dropped connection, the program was not asked for, and the page stayed empty.

### An update reaches the browser at once
- The page's script and style sheet are asked for with a fingerprint of the page's files in their address (`?v=<version>-<fingerprint>`, from the names, sizes and dates of its scripts and styles: `Http::build`), so after an update the browser loads the new ones although the version number has not changed. Before, the address carried only the version number, and a browser could keep using the old files after an update until it reloaded them.
- A page that was open while MuDesk was updated says so at the bottom and offers to reload, the next time it asks for the state: when signing in again in it (also after its web session expired). ### Security audit
A full review, before this version, of the gateway (the PHP side that talks to the remote computers) and of the page. Nearly every fix below has a test that fails without it: each was undone in a copy of the project and its test checked to fail there (41 checks).
- **Remote sessions end with the web session.** Signing out, or the session expiring or being closed by the gateway, now ends the remote sessions opened from it; before, they went on, with nobody signed in, until their own idle limit. A password change ends the remote sessions of your other sign-ins (they say so), not those of the window where you changed it. Signing out in one tab also ends the other tabs of that browser, and each says so. Every 15 s a remote session also checks that its account still exists and is enabled.
- **The password asked again** (to add a passkey or an authenticator app, change the password or remove a second factor): five wrong ones close the session. Before, whoever had the session open could guess it without limit.
- **Sign-in answers take the same time**: every answer (password, TOTP, passkey) takes 1 s so that it says nothing about the user name or the password. In PHP's web server on Windows `usleep()` sometimes woke early, and some answers came after 0.78 s. The wait now goes on until the second is over, measured with `hrtime`: 60 sign-ins against PHP 8.5, none under 1.0 s (before, 4 of 45 in the same test).
- **Sign-in locks**: signing in no longer clears the failures counted against that address, so an account of one's own can no longer reset them between guesses at others.
- **Audit**:
  - Refused requests of someone not signed in are written at most 100 times an hour per address and 5,000 in all, then one `audit_limited` line. Before, each one wrote a line, so a day's file could grow until reading it stopped sign-ins.
  - The days are read a line at a time (backwards in 1 MB blocks). With a day of 60 MB: 3.7 MB of memory instead of 128 MB; search and *Verify integrity* as fast as before (0.3 s and 1 s); the notice after signing in, 0.002 s instead of 0.1 s.
  - *Verify integrity* lists the first 1,000 problems and counts them all.
- **HTTPS behind a proxy on the same machine**: requests from 127.0.0.1 skipped the HTTPS check, so plain HTTP was accepted behind such a proxy. A proxy listed in `trusted_proxies` is no longer taken as local: its `X-Forwarded-Proto` decides (see HOSTING).
- **RDP targets** with "Allow all": IPv4 inside IPv6 is checked as IPv4 also in its NAT64 (`64:ff9b::/96`) and `::a.b.c.d` forms, and the other cloud metadata addresses (100.100.100.200, fd00:ec2::254) are refused too.
- **What a hostile or broken RDP server can make the gateway hold or do**:
  - A channel message is at most 64 MB, with the length its first chunk announced (each chunk could announce 4 GB). Dynamic channel messages too, with at most 8 being joined at a time.
  - The XCRUSH history starts again only when it is full: a server resetting it at every block made each one copy 2 MB (a core busy with 2 KB/s).
  - The socket is read 4 MB at a time (the main loop comes back for the rest), and a write that makes no progress ends after 30 s: a server reading a byte now and then held the PHP worker.
  - A desktop over 32766 a side or 8192 × 8192 pixels ends the connection, and so does a protocol the server picks that was not offered (RDSTLS, NLA extended).
  - The remote clipboard is kept up to 16 MB to put it back after typing: 64 MB held three times passed a 128 MB memory limit.
  - The shared drive: at most 1,024 open handles (64 open files at a time), 20,000 new files and folders and 2,000 audit lines a session (then one line saying so); masks with more than 4 `*` match nothing (their pattern backtracked on every name); a rename to the same file under another case no longer gives its size back to the quota (that made the quota endless).
  - Windows device names (CON, NUL, COM1, LPT¹, CONIN$… with any extension) are refused in the shared folder: such a file could not be read back or removed.
  - Messages waiting for a session are kept up to 16 MB, diagnostic traces up to 256 MB in all, and passwords never appear in PHP stack traces (`zend.exception_ignore_args`, `#[\SensitiveParameter]`).
- **What a server can make the page hold**: ZGFX uses one buffer of the size a message declares (up to 64 MB; 65,535 empty segments took 4 GB). The graphics pipeline keeps its surfaces within 4 times the output, its bitmap cache within 100 MB with each slot inside its surface, and ClearCodec glyphs only as the codec allows them. The drawing-order bitmap caches keep only the cells offered (600, 600 and 1,024 entries of 256, 1,024 and 4,096 pixels). A desktop over 32766 a side or 8192 × 8192 pixels is not taken. A clipboard image whose header claims more than it brings, and a remote file chunk past its announced size, are refused.
- **Requests**:
  - Values of the address are taken as text only: `p[]=x` gave a TypeError, an error 500.
  - `files.php`, `rdp.php` and `api.php` (except `state`) refuse a request without a session cookie before a session file is made.
  - The ZIP of several items is asked for with its names in the request body (hundreds of names did not fit in an address; IIS takes 2 KB) and downloaded with the id it got.
  - Thumbnails are revalidated each time (`Last-Modified`, 304) instead of kept, and signing out clears the browser's cache of the site (`Clear-Site-Data`).
  - Deleting waits for an upload chunk still being written. A ZIP stops being walked past 65,535 entries or 64 folders deep; dates before 1980 or after 2107 are clamped to what ZIP can say.
- **Page**:
  - Items dragged between windows of the application carry a key of this browser, so another web page cannot make a drop move files. A drag left over (its item drawn again before it ended) is never taken for a new one.
  - Signing out clears what the account left in the page: uploads still queued (they would land in the next account's folder) and the explorer's state.
  - Windows and notices show inside full screen. A malformed folder address shows the top folder.
- **Explorer bugs found on the way**:
  - The keyboard stays in the list or the tree after changing folder (going up selects the folder you came from) and after a menu closes; before, it fell to the page and the keys did nothing.
  - Typing a name with a space jumps to it.
  - Two quick clicks on **New folder** make one folder.
  - Cancelling an upload during its first request removes what reached the gateway.
  - No error notices beside the *Session expired* window.
- **Several screens**: a window of another screen opened while connecting now gets its monitor once connected (its screen stayed black), and the same layout is not asked for twice.
- Tested: `tests/run.php` (180 checks then) and `tests/fuzz.php --strict` with PHP 8.1, 8.2, 8.3, 8.4 and 8.5, with no warning, notice or deprecation; every `tests/*_unit.mjs` and `tests/fuzz.mjs --strict`. Not covered by a test: the sign-in answers waking early (it depends on the system; the end-to-end test of equal answer times caught it now and then), the fallback socket name (data folders with long paths), the delete waiting for an upload chunk, the 30 s write limit, ClearCodec glyphs, `Clear-Site-Data`, windows inside full screen and the page cleared on sign-out.

### Error pages

  - PHP not supported or without OpenSSL;
  - HTTPS required;
  - IP not allowed;
  - internal error, out of memory included.

- The interface's own requests get `{"error": key}` and show the same reason with "Try again"; before, it showed a bare "Error" or failed with a script error.
- The error log names the data folder that could not be created.
- No measurable cost. On Apache with XAMPP's PHP 8.2, the page took 4.4–5.0 ms before and 4.6–5.6 ms after, and the state request 7.2–9.0 ms before and 6.9–8.6 ms after; both ranges are within the noise between runs. The calls added to each request take under 0.5 µs.
- HOSTING explains how to give the *Modify* permission on Windows (XAMPP, IIS).

### Second review (external audit report, pending fixes, random-data tests)

- Sign-in: each remembered browser has its own attempt count and lock; once locked, the normal locks apply. The 20 used most recently are kept and each new one is audited (`device_add`). A TOTP code already used, such as the one that enabled it, is refused with "wait for the next code". To require 2FA the administrator must have it first (`totp_required_self` otherwise); users without it sign in and only see their profile until they add TOTP or a passkey. The page is served in the browser's language before the interface loads.
- Targets: with "Allow all", the server itself (127.0.0.0/8, ::1), link-local addresses (169.254.0.0/16, with cloud metadata, and fe80::/10) and 0.0.0.0/8 or :: are never reached, nor their ::ffff:… forms; list them to reach them. Administration warns while it is set. Names are still resolved by the system resolver, with its time-out: one of its own would break the `hosts` file, search domains and Windows name resolution, and the session limit below bounds how many processes can wait (see HOSTING).
- API and shared folder: 400 `invalid_input` when a field carries a list or object, 404 `not_found` for what does not exist; file and folder names over 255 bytes are refused (400 `invalid_path`).
- Audit: the export is streamed row by row (about 20 MB of memory instead of about 71 MB). The JSON export is signed with a server RSA 3072 key (PKCS#1 v1.5, SHA-256), in a ZIP with `audit.json` and `audit.json.sig`; each row is the line as stored. The hash is computed while streaming, with no copy: 0.21–0.23 s against 0.32–0.36 s for the unsigned export before, same memory (19–20 MB). The key (`data/audit-key.php`) is made once (≈2 s) on the first JSON export or when its panel is opened; Administration → Audit shows the public key and the `openssl dgst -sha256 -verify` command. The CSV is not signed. "Verify integrity" checks up to the moment it starts; what is written meanwhile is left for the next check.
- Points of the report that were not real: the drive rename format is the one in MS-RDPEFS (renaming works on Windows 11 Pro); the input token is checked first; a negative offset and a connection saved without a host already gave 400; `*.domain` targets already worked and a name that does not resolve is refused as a target not allowed; the interface already followed the browser's language; a password change already forgot the remembered browsers; requiring 2FA could not lock everyone out.
- Profile: each user sees their open remote sessions and can end them, and their trusted browsers (added, last used, browser, IP), to forget one by one or all but the current one; removals are audited (`device_forget`, `session_kill` by the owner). At sign-in, the last sign-in (date and IP) and the failed attempts with the user since then ("one failed attempt" / "N failed attempts") are shown, read from the audit log (up to 90 days) within the fixed second of the sign-in (worst case 73 ms, usually 5 ms).
- Installable app on phones and computers: `manifest.webmanifest`, icons 192/512/maskable and `apple-touch-icon`, no service worker. `public/.htaccess` and `public/web.config` set the type of `.webmanifest` (Nginx: see HOSTING).
- Gateway: new setting "RDP sessions at once (all users)" (`max_sessions_total`, 20 by default, 0 = no limit): at the limit the gateway answers "busy" (503) without connecting, the session window says the server is busy and the audit log records `rdp_denied` with reason `busy`. Both limits are checked and the session registered under one lock. Each handshake step (TCP, TLS, X.224, NLA, MCS) waits at most 8 s (was 20 s); activation keeps 30 s. If the browser closes while connecting, the PHP process is freed within 1–2 s. A server that goes silent during NLA is reported as not answering, not as a wrong password (only a dropped connection means wrong credentials).
- Shared folder: one quota per user for the drive of all their sessions, the file manager and clipboard files (counter `data/files/<uid>.quota`), recounted when the file manager is opened with no session running. Opening the drive with 3000 files: 205–238 ms → 0.2–1.4 ms; free-space queries 213–233 ms → 0.1–0.4 ms.
- Phone keyboard: two pastes in a row no longer repeat the previous text. Windows confirms a clipboard announcement before applying it and did not apply a list equal to the one it had; the clipboard is now put back after every paste (nothing copied: an empty text) and each list carries a format of its own that alternates. Measured on Windows 11 Pro: 21 of 21 in the Run box, 30 of 30 words in Notepad.
- Keyboard: with a Chinese, Japanese or Korean IME on a computer the text is sent once, when confirmed; dead keys (´ + a) are not doubled; phones and tablets without a mouse are unchanged.
- Drawing orders: MemBlt and PatBlt with any ROP; PATINVERT XORs the brush colour or pattern. Mem3Blt is not negotiated: a MemBlt whose ROP uses a brush takes GDI's default white brush. FastGlyph with a fixed pitch no longer also draws glyph 0.
- RemoteFX progressive: sparse rectangles give a box each (two corners: 33 KB instead of 8.3 MB; worker 0.93 → 0.51 ms; main thread in Chrome 17.8 → 6.7 ms); the usual case is unchanged.
- Found with `tests/fuzz.php` (gateway): shared drive: reading past the end returns nothing, and an offset of 2^63 or more is an error (before: a warning on Windows or data from another position). Clipboard: malformed browser file lists are ignored without errors; a remote file of 2^63 bytes or more no longer keeps the download asking for chunks without end. Dynamic channels: capabilities shorter than 4 bytes no longer end the session in diagnostic mode.
- Found with `tests/fuzz.mjs` (browser decoders, hardened against corrupt or hostile data): bitmaps no larger than the desktop (rounded up to 64-pixel tiles) and of a valid depth; surfaces and graphics output up to 32766 px a side (the RDP maximum); each rectangle within its surface and each ClearCodec subcodec within its rectangle (as FreeRDP); quantizer indexes checked in RemoteFX and progressive; NSCodec plane end; SPS at the end of an H.264 unit.
- Tests: `tests/fuzz.php` and `tests/fuzz.mjs` send random and mutated data (fixed seed; `--seed`, `--iterations`, `--target`, `--case`, `--strict`; known failures are shown as pending). They found 9 real bugs (4 in PHP, 5 in JavaScript), all fixed: no known failures left. New checks in `tests/orders_unit.mjs`, `tests/gfx_unit.mjs`, `tests/rdpgfx_unit.mjs`, `tests/session_unit.mjs` and `tests/ui_unit.mjs`; `tests/render.mjs` applies the ROPs and patterns too.
- Tested on Windows with the official builds of PHP 8.1.34, 8.2.35, 8.3.33, 8.4.27 and 8.5.12: `php -l`, `tests/run.php`, `tests/fuzz.php --strict`, `tests/auth_e2e.php` (75 checks then, 79 now) and a live connection to Windows 11 Pro with the graphics pipeline and with compressed bitmaps; no warning, notice or deprecation.
- CI: PHP 8.1, 8.2, 8.3, 8.4 and 8.5 on Linux and Windows, where any warning, notice or deprecation fails the run; JavaScript with the current and the previous Node.js LTS; every `*_unit.mjs` and both fuzz tests with `--strict`.
- `tools/check.php`: six tests (new: data folder reachable from the web, and PHP processes at once, which gives the highest `max_sessions_total`); warns about PHP outside 8.1–8.5, `display_errors` on and `memory_limit` below 128M.

### Code review (security and robustness)
A full review of the gateway and the browser code, area by area; every fix has a test that fails without it.
- Security: the shared folder and the file manager refuse `.htaccess`, `web.config` and `.user.ini` (they could make the web server run uploaded code); the shared folder is refused when only the printer is on; the sign-in lock can no longer be bypassed with an expired second step, huge user names are cut, a locked IP is answered at once; adding a passkey or TOTP asks for the current password and is refused while a password change is pending; an administrator's password reset stops passkeys from opening the account without a password; the client IP behind trusted proxies is the right-most untrusted one; the session input token is no longer listed to administrators and travels in the `X-MuDesk-Token` header instead of the URL; disabling, deleting or resetting a user closes their RDP sessions; passwords are limited to 72 bytes (bcrypt) and a typo past them no longer resets the account; the file quota holds with chunked or parallel uploads and clipboard uploads; audit verification detects edited first lines and removed last lines; CSV exports cannot start a formula; WebAuthn counters follow the specification; errors no longer show server paths.
- RDP: NLA with non-ASCII user names (josé, Begoña); licences with X.509 certificates; MPPC, fast-path, channel and CredSSP data from the server are bounded (no memory or CPU blow-up); static channel messages are joined once (8 MB from 16 s to 15 ms); input sent during a reactivation is kept (no stuck Ctrl or Shift); the activation wait is limited as a whole; a fatal error still cleans the session up; the graphics pipeline refreshes the size set through Display Control; the printer capability is announced (MuDeskPDF needs it).
- Clipboard and drive: a late answer is no longer filed under the next remote list (clipboard text reached the audit log); no format list before Monitor Ready; the drive quota is charged and given back correctly (also when unlimited, with huge offsets and end-of-file changes); print jobs of a session are limited together; remote file names cannot leave the download; reading the remote clipboard stops at 64 MB; format lists are read in linear time.
- Browser: the web session stays alive while the remote desktop is in use, and an expired one is reported as such; keys typed during a slow paste wait their turn; touch long press or a second finger no longer leave the left button down; chorded mouse buttons; sticky modifiers of the key panel are released; Cmd+V on a Mac; the bitmap cache of drawing orders is kept; reconnection retries when the old session still counts; "save password" saves the corrected one; ZIP with files that shrank; QR for long names; iOS zoom; module caching after an update; accessibility (alerts, Escape closes dialogs).
- Graphics: a large H.264 key frame or a surface deleted while decoding no longer stop the pipeline; four endless loops on corrupt data (planar, NSCodec, SPS, RemoteFX) and several memory blow-ups (ZGFX, ClearCodec, progressive tiles, glyphs, pointers) are refused; a faulty PDU or drawing order no longer drops the rest of the message or the session; ZGFX is 6 to 60 times faster; 16 bpp pointers keep their white; progressive upgrades without reduce-extrapolate.

### Performance
- Graphics mode per connection: **Automatic** (new default), graphics pipeline and H.264, or bitmaps only. In automatic, the Windows version sent in the NTLM challenge during NLA decides: Windows 8.1 / Server 2012 R2 or later gets the graphics pipeline at 32 bpp (PHP 0.4–2 % CPU instead of 6–52 % with compressed bitmaps), xrdp, TLS-only and older servers keep bitmaps. The old "H.264 graphics" setting becomes "graphics pipeline" when it was on and "automatic" otherwise. The audit (`rdp_start`) records the server version and whether the pipeline was used.
- Drawing orders (`drawing_orders`) on by default: validated with Windows 11 (identical picture; no leftovers when the server repaints the whole screen after moving windows and scrolling text, at 16 and 32 bpp). Dragging a window: 150 → 60 KB/s and PHP CPU 6.5 → 2.7 %.
- Benchmark per codec and colour depth against Windows 11, PHP and browser apart: `docs/PERFORMANCE.md` / `docs/es/RENDIMIENTO.md`.
- RemoteFX progressive decoding 5.6 times faster (79 → 14 ms for a full-screen frame): the inverse wavelet transform indexes the arrays directly instead of calling closures per coefficient, and halves in integers. Same output, bit for bit.
- Graphics pipeline: opaque blocks (70 % of them) are written directly instead of being blended through a new canvas (2.6 times faster per block in Chrome).

### Sign-in security
- First run protected by a one-time setup code (`data/setup-code.php`).
- Passkeys (WebAuthn, plain PHP + OpenSSL): passwordless when the authenticator supports PRF (the passkey wraps the data key), otherwise as second step; TOTP and passkeys both satisfy "2FA required".
- Brute force: per-IP, per-user and global counters; known browsers (signed device cookie) stay allowed when a user name or the whole site is under attack.
