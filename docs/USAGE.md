## First start

The first visit asks for the one-time **setup code** (in `data/setup-code.php` on the server; it stops anyone else from claiming a fresh install; it lasts a day, then another one is written there) and creates the **administrator** account. Passwords need at least 12 characters and 72 bytes at most (72 plain letters; accented letters and symbols take more), at least 4 different characters, and must not be a common password nor contain the user name. The administrator creates the other users with a temporary password, which they must change at their first sign-in.

The language (Spanish or English) is changed with the selector in the header, at the top right; it is saved in each user's profile. Before signing in it is picked on the sign-in screen. In *Profile*, **Automatic** follows the browser's language. The pages end with a link to the project's site.

## Connections

A connection moved to another computer (another host, port, user, domain, security or gateway) forgets its saved password and its certificates (the computer's, its gateway's and its broker's servers'). Each user keeps their own connections (*Connections → New connection*), if the administrator allows it (*Settings → Users can create connections, import .rdp files and make manual connections*, off by default: usually the administrator creates them and gives them to each user). Without it, the list has neither *New connection*, *Import .rdp* nor *Manual connection*; connections a user already had stay usable, their options adjustable and they can be deleted, but they cannot be pointed at another computer (host, port, user, domain, security, the gateway, the load balance info, the Hyper-V machine and Wake-on-LAN stay as they are). Those marked **From the administrator** were made by the administrator for you: you connect with them and keep your own password and options for them, but cannot change or delete them. A redirection the administrator turned off in them (sound, microphone and camera, clipboard, shared folder, printer) you can leave off but not turn on (its box unticked and greyed: *The administrator has turned it off for this connection*); without *Users can create connections*, the same with your own connections: what each has is the most it can have.

**Manual connection**, for an occasional one: the same form as a new connection, without its name, group or password, and **Connect** instead of Save. The session opens in a new tab and the password is asked for when connecting; nothing is saved in your connections (not even the options of the connect dialog), and the connection is forgotten when your web session ends (signing out, or when it expires). The computer must be an allowed target, as for any connection, and its certificate is pinned for you as a saved connection's is: the next manual connection to that computer warns if it changed. In the audit log its lines say `occasional`.

**Import .rdp** creates connections from files of Remote Desktop Connection: one file opens the form filled in to check and save; several are saved at once. What MuDesk does not take is said there (a RemoteApp file without its program: the whole desktop opens; a start program; the saved password, which only the Windows that saved it can read). A RemoteApp file with its program becomes a RemoteApp connection, and exporting keeps the program. A Remote Desktop Gateway (`gatewayhostname`, when the file uses it) and a connection broker's `loadbalanceinfo` are taken, and exported. What a file asks to share from this computer (the clipboard, drives, the printer, the microphone or the camera) is never turned on by importing it, as Windows does since April 2026 with files it cannot verify: the import's notes say what it asked for and through which gateway it connects, to turn it on in the options only where you trust that computer (a file sent by mail that connects to someone else's computer is a known way to take your drives and clipboard). An administrator's imported connection is nobody's until its users are chosen. Exporting writes the microphone and camera box to both `audiocapturemode` and `camerastoredirect`. Imported connections get the Spanish keyboard layout, as new ones: check it. The download button of each connection exports it as an **.rdp file** for Remote Desktop Connection (without its password).

In the form, *Keyboard layout* and the fields after it in this table (all but the RemoteApp ones) are in the folded section *Advanced options*. The form shows its fields in columns where they fit (one on a phone): the password beside the user and the domain, the folded sections side by side, and the advanced options' lists and boxes in columns, so most of it shows without scrolling. In it, as in every window of this kind, the content scrolls between the title and the buttons, which stay in sight.

**Connect** opens the session in a new tab, so several sessions can be open at once. When the server already has as many sessions as the administrator allows for all users together, the session window says the server is busy: try again later.

## Connect dialog

Before each session (unless *Remember these options and do not ask again* was chosen and the password is saved) you choose: remote audio, this computer's microphone and camera on the remote one, clipboard, phone keyboard through the clipboard, shared folder, MuDeskPDF printer, graphics (not for a RemoteApp, which says which program it opens), color quality and **use all my screens** (ticked; unticked, it is remembered with the other options; Chrome/Edge: only with several screens; Firefox and Safari: the other screen is looked for, ticked once one was found, since before that they cannot know whether there is one; not on phones and tablets; its **ⓘ** says what this browser asks first: the permission to manage windows on all the displays in Chrome and Edge, pop-ups allowed in Firefox and Safari) and **start in full screen** (ticked; unticked, it is remembered with the other options; its **ⓘ** says what each browser does and how to let every screen go to full screen without a click, with the commands for the page's address: see *Full screen on every screen*). The options come folded under **Options for this session**: unfold them to change them. Unfolded, they show in two columns where the window is wide enough, so **Connect** shows without scrolling; in a window too short for them, the dialog scrolls and **Connect** stays in sight. Connections without a saved password also ask for the credentials here, above the options, with **Save password (not recommended)**: it is stored only once the connection works. A wrong password asks for them again. Under *Advanced options*, at the end of the options, **Diagnostic mode** records a technical trace of that session for the administrator (see Administration). The X at its top right closes the window; if the browser does not let the page close it, it goes back to the connections (also the **Close** of the window that says the session was disconnected).

## RemoteApp: a program on its own

With **Program (RemoteApp)** filled in (its path on the remote computer, such as `C:\Windows\System32\notepad.exe`, or the name it was published with, such as `Excel`: MuDesk adds the `||` that Windows expects before it), the connection shows only that program: its windows, each one where it is, over the page, without the remote desktop. They are moved, resized and closed with their own title bars, and the tab title says which one is active.
- A taskbar at the bottom of the page has a button for each window: click one to bring it to the front (also when it is minimized), or click the active one to minimize it. Maximized windows leave it in view.
- The **Windows** button of the toolbar lists them too: click one to bring it to the front, or minimize, maximize or close it.
- The remote computer must allow the program: Windows Server with Remote Desktop Services publishes RemoteApp programs; on Windows 10/11 Pro it is allowed in its registry (see [HOSTING](HOSTING.md#remote-computers)). Otherwise the session says so ("does not allow this program as a RemoteApp"); it also says when the program is not found or could not be opened, when the remote session is locked, and when the computer does not offer RemoteApp at all (connect without a program).
- When the program is closed (its last window), the session ends about 3 s later and says so; **Reconnect** opens the program again. Windows keeps the session disconnected, as with Remote Desktop Connection, until its time limits log it off. If the program was still running there, **Reconnect** brings its windows back without opening a second one.
- Until the program's first window comes, a spinner in the middle of the page (and the taskbar) says it is opening: some programs take a while. After 15 s it says it is taking longer than usual. If the server ends the session meanwhile (it does after some 12 s without a program, also while one is starting), the page connects again by itself and keeps waiting; after 90 s without the program it says so, with **Reconnect**.
- On several screens (see *Several screens*), each window of the program shows on the screen where it is; the session's screen is the remote primary one, so the program opens there, beside its taskbar.
- This version uses bitmaps (not the graphics pipeline or H.264), and the remote desktop always follows the window (the *When the window is resized* option does not apply).

## Session toolbar

The toolbar hides itself at the top; move the mouse there or tap the small tab to show it. Drag it by its grip (at its left) or its title to move it to a side (or use the arrow keys on the grip); it stays there for the next sessions in this browser.

Next to the name, the **quality indicator** shows every second the frames per second on screen, the input latency to the gateway and the data received (for example `24 fps · 35 ms · 120 KB/s`). The dot is green below 100 ms, amber up to 250 ms and red above; with the toolbar hidden, the small tab takes that colour when it is not green.

| Button | Action |
|---|---|
| Full screen | Full screen with keyboard capture (Win, Alt+Tab… where the browser allows it). With several screens, it offers to use all of them (see *Several screens*) |
| Ctrl+Alt+Del, Windows key | Send these keys |
| On-screen keyboard | On phones and tablets, opens the device keyboard. With a mouse, opens and closes a keyboard of our own, used with the mouse (see *On-screen keyboard*) |
| Special keys | Esc, Tab, sticky Ctrl/Alt/Shift/Win, arrows, Home/End, PgUp/PgDn, Del, Backspace, Enter, F1–F12 |
| Mute | Remote audio on/off |
| Screenshot | **Full screen** (the whole remote desktop; with several screens, all of them; with RemoteApp, the program's windows on the session's screen) or **Select an area** (drag a frame over the remote picture; Esc or right click cancels). Only the remote picture, without the toolbar, the panels or the pointer, at its real size even when the window shows it smaller. Then: **Save** (PNG), **Copy** (to this device's clipboard) or **To the remote computer** (to its clipboard, to paste it there with Ctrl+V; with the shared clipboard on) |
| Clipboard | Text copied remotely appears here; type or paste text and send it to the remote clipboard. Below it, the **history** (like Win+V) |
| Files | Send files to the remote clipboard (then Ctrl+V in Explorer) and download files copied remotely (ZIP when there are several); with the shared folder, [A folder of this computer](#a-folder-of-this-computer) |
| Screens | Lists the screens: **Open** adds a screen's window and its remote monitor, **Close** removes them; in Firefox, **Look for other screens** |
| Windows | RemoteApp: the program's windows (see *RemoteApp*) |
| Share | Links for guests to watch the session, or use it too (see *Sharing a session*) |
| Record the session | Starts recording the session at once; pressed again (**Stop recording**), stops (see *Recorded sessions*) |
| Disconnect | Leaves the Windows session running (disconnected) |
| Hide toolbar | Tucks the toolbar away (it comes back with the pointer at the top, or the small tab) |

**Mute** is there when the session has remote audio, **Clipboard** when it has the shared clipboard, **Files** when it has the shared clipboard or the shared folder, **Screens** when it uses several screens (or, in Firefox and Safari on a computer, to look for them), **Windows** with RemoteApp, **Share** in every session but RemoteApp, **Record the session** for administrators, and for the other users when the administrator allows it (not with RemoteApp).

**Microphone.** With **This computer's microphone and camera on the remote one** ticked, the remote computer hears this computer's microphone: Windows shows it there as *Remote Audio*. The microphone is only opened while a program of the remote computer records (a call, a dictation...); the first time, the browser asks whether the page may use it (allow it: the icon next to the address changes it later), and while it is open the browser shows its own recording sign, and the session too, at its top: *The remote computer is using your microphone* (with the camera, *…your camera*, or both). If the browser does not allow it, the page has no microphone, the page is not opened with `https://`, or the remote Windows forbids audio recording, the session goes on without it (the first three are said on the page; for the last one see [HOSTING](HOSTING.md#remote-computers)). The **ⓘ** beside the box in the connect dialog says all this, with how to allow audio recording on the remote Windows: step by step in the policy editor (`gpedit.msc`, an MMC console) or with a command for the registry, and the Windows Audio service on Windows Server.

**Camera.** The same box (**This computer's microphone and camera on the remote one**) brings this computer's camera, if it has one: in the session it is **MuDesk camera** (Windows 10 1803, Windows Server 2019 and later), for video calls and the Camera app. It is only on while a program there uses it, at the size the program asks for (640 × 480, 1280 × 720, 640 × 360 or 320 × 240; the picture is cut to those proportions in its middle); the first time the browser asks for permission, as for the microphone, and shows its own sign while it is on. It works the same in Chrome, Edge and Firefox, also while the page is in another tab. Windows allows it as it comes; if the camera does not appear, the policy *Do not allow video capture redirection* is enabled on the remote Windows (the **ⓘ** gives the command for the registry), or a Remote Desktop Gateway's policy forbids Plug and Play devices (then the camera is not offered, as with Windows' own client). Each picture goes as a JPEG: about 8 KB at 640 × 480 for the simulated cameras of the tests (some 20 a second, 150–185 KB/s); a real camera's are larger, an estimated 30–50 KB, about 0.5–1.5 MB/s upwards while a program uses it. On a slower connection fewer pictures arrive, never later ones.

## Sharing a session

**Share** on the toolbar makes links to the open session for someone without an account (a colleague who helps, a trainer, support):

- Choose what the guest can do: **View only** (the default) or **View and control** (their keyboard, mouse and touch reach the remote computer as yours do: both of you use it at once). **Create link** makes it and copies it; send it however you like. Several links can be open at once (up to 10, each with its own mode).
- Whoever opens the link sees the remote desktop in their browser, with a mark where your mouse is, and a line at the top saying whose session it is. They see the picture only: not your clipboard, sound, microphone or printed documents.
- When a guest joins, the connection is made again for a moment (Windows keeps the session; the picture stops for a second or two) so that everyone starts from the same picture.
- While anyone watches, **Guests watching: N** stays in sight in a corner of the session. **Revoke** ends a link and its guests stop seeing the session at once; every link ends with the session (closing it, disconnecting, or the web session ending).
- A guest given control uses the desktop as you do, also while you are not looking: what it reaches too (the shared folder, the printer, programs). Give control only to whom you would let sit at your computer, and revoke the link when it is no longer needed. Its typing is limited (it cannot queue minutes of keystrokes), and keys it held are released when it leaves.
- Guests joining one after another make the connection again at most once every 10 seconds (the next one waits that long).
- A link lasts as long as the session, or less: **15 minutes**, **1 hour** or **4 hours**, chosen before it is made (its end shows in the list); past it, its guests stop seeing the session.
- A guest given control who does not use it for the minutes the administrator sets (*Settings → Minutes unused after which a guest loses control*, 15 by default, 0 = never) loses it and keeps watching, told why; control again takes a new link with control.
- Up to 5 guests at once per session. Each guest takes a PHP process of the server while watching (see [HOSTING](HOSTING.md#capacity)). Not available for RemoteApp, nor when the server uses the queue file (`'ipc' => 'file'`).
- The audit log keeps each link made (`share_create`, with its minutes), revoked (`share_revoke`) and expired (`share_expire`), each control lost for not being used (`share_control_end`), and each guest joining and leaving (`share_join`, `share_leave`, with the guest's IP and how long they watched).
- Treat a link like a key: anyone who has it can watch (or use) the session while it lasts. The link's secret goes after `#` in the address, so it is not sent in requests' addresses nor kept in web server logs; the server keeps only its SHA-256.

## Recorded sessions

A session is recorded in two ways:

- **Every session of a connection:** an administrator ticks **Record the sessions of this connection** (in the connection's advanced options; in *Administration → Connections*, for the administrator's connections and for each user's own; a user cannot turn it on or off). A computer recorded through one connection is recorded through any other connection of the same user to it (the same port, by the same name, another name or its address): a connection of their own does not avoid it. The server records it from the session's own stream, from its first picture: the user's browser cannot leave anything out.
- **From one moment to another:** **Record the session** on the session's toolbar (a circle) starts recording it at once and, pressed again (a square, **Stop recording**), stops. Administrators always have it; the other users only when the administrator allows it (*Settings → Users can record their own sessions*). An administrator also starts and stops the recording of any running session in *Administration → Active sessions* (**Record the session**, **Stop recording**), that of a connection always recorded too. A recording an administrator started, or that of a connection always recorded, is stopped only by an administrator (the user's button is hidden then). It is made in the session's browser, of what it shows: the remote desktop (all its screens) with the mouse pointer, the remote computer's sound and the microphone the remote computer hears; the browser sends it to the server as it goes, a piece each second, as a video file (WebM with VP9 or VP8 and Opus; MP4 in Safari). The session goes on as it was: nothing stops or connects again. Its sound needs the page to have been used since it opened (a click or a key), as browsers ask before playing sound; else the picture alone is recorded. It needs MediaRecorder (Chrome, Edge and Firefox, Safari 14.1 or later; a browser that cannot record says so, and the session goes on unrecorded). Not for a RemoteApp session (its connection can be recorded).

What is kept, and for how long:

- Whoever connects is told before anything is shown when the connection is always recorded: it is marked **Recorded** in the list and the connect dialog says so. While a session is recorded, **● Recording** stays in a corner of it (also when the recording started in the session); guests of a shared session see it too, and *Active sessions* marks it **Recorded**.
- The picture and the sound are kept: what the screen shows, where the mouse is, what the remote computer plays (when the connection has its remote audio) and what this computer's microphone sends it (when the connection has the microphone and a program there records). Not the keyboard, the clipboard or printed documents. It is encrypted on the server with a key of its own (AES-256-GCM, in pieces bound to their recording and place: a changed piece is refused).
- Recordings are kept on the server (`data/recordings/`) until they are deleted by hand: by default *Settings → Days recordings are kept* is 0; with a number of days, older ones go by themselves. At most 2 GB each (`record_max_mb` in `config.php`; past it the rest of the session is not kept, and the recording says so). Watching or downloading one leaves it where it was.
- Room they take: a recording of a connection always recorded, some tens of MB an hour for an office desktop; much more with video, and the microphone, kept as Windows asks for it (16-bit PCM, about 176 KB/s), adds some 635 MB an hour while a program there records. One started in the session (a video already), 10 to 30 KB a second for an office desktop (35 to 110 MB an hour, measured at 1280 × 844); with something moving all the time, up to about 300 MB an hour at 1280 × 844 and 600 MB at 1920 × 1080.
- Screens added or removed while it records: the video keeps the size the desktop had when it started; a desktop that grew (a second screen) is drawn smaller to fit, one that shrank stays at its size with black around it. On a remote computer that changes its screens by connecting again (one without Display Control: Windows 8 and Server 2012 or earlier), a recording started in the session ends there, kept up to that moment: start it again.
- If the recording of a connection always recorded cannot start (the data folder cannot be written to), the session does not connect. One started in the session that cannot be written, that the browser cannot make, or whose pieces cannot reach the server (the network gone for more than about 10 s, or an upload slower than the video: more than 32 MB waiting), stops, kept whole up to that moment, and the session goes on (the page says so). One that grows faster than a video can (a page changed on purpose) is stopped too.
- Each start and stop is audited (`recording_start`, `recording_stop`: who, as administrator or as the session's user, and the recording's id).

**Watching one**: administrators and auditors see every recording in *Administration → Recordings*, the newest first (when, whose session, which connection, who started it, its length and size), with **Watch the recording** and **Download the video**; or they open *Administration → Audit log* and click the line marked **Recorded** (`rdp_start` for a connection always recorded, `recording_start` for one started in a session), then **Watch the recording**. Closing the player goes back where it was opened from. A recording of a connection always recorded plays in the page with its sound at 1× (muted at other speeds and while it jumps), pause, speed (1×–8×) and a bar to jump to any moment (a jump plays the recording again up to there, quickly). One started in the session is read whole from the server and plays in the browser's own player (pause, position, speed, full screen). Each viewing is audited (`recording_view`).

**Deleting one**: an administrator deletes any recording from *Administration → Recordings* (**Delete**, after saying yes; not while it is being recorded; audited as `recording_delete`, with whose it was); an auditor only watches them. One the server left unfinished (its process stopped by the hosting, with no session running it any more) shows no length and can be deleted.

**Its video**: a recording started in the session already is one: **Download the video** saves it as it is, after a window says its size. Of a connection always recorded, the player's download button makes a video of the whole recording in this browser and saves it: a WebM file (VP9, or VP8 where the browser has no VP9 encoder; its sound in Opus, the remote computer's and the microphone's together), the mouse pointer drawn in, the desktop at its largest size in the recording, at most 15 pictures a second. It is made as fast as the browser can (a 17-second recording in about 4 s), while the recording can still be watched; *Cancel* stops it. It needs WebCodecs: Chrome and Edge 94, Firefox 130, Safari 26 or later (the button is not there in other browsers). Each video made is audited as a viewing.

Before it is made, a window says how much room the video may take, by how long the recording lasts and its size: **up to** what the encoder writes with something moving all the time (a video played in the session), the room to have free, and **about** what it takes with an office desktop, mostly still (measured: 13 KB a second at 928 × 917). Per hour:

| Desktop | Up to | Office desktop |
|---|---|---|
| 1280 × 720 | 550 MB | 55 MB |
| 1920 × 1080 | 1.2 GB | 120 MB |
| 3840 × 2160 | 4.9 GB | 480 MB |

The sound adds 43 MB an hour (Opus at 96 kbit/s).

**Your own recordings**: **Recordings**, in the menu at the top of every user, administrators too, lists the recordings the user started in their own sessions (the date, the connection, its length and size; while *Users can record their own sessions* is off, a notice tells a user who is not an administrator that they cannot record): watch one (as above), download its video, or delete it, after saying yes (not while it is being recorded; audited as `recording_delete`). Only those: the recording of a connection always recorded, or one an administrator started, is for administrators and auditors, and a user asking for it is answered that it does not exist. An administrator finds there the ones they started in their own sessions, and every recording in *Administration → Recordings*.

## Clipboard

- **Text and images**: Ctrl+V in the session sends the local clipboard first; what is copied remotely is copied locally when the browser allows it (always visible in the Clipboard panel).
- **Formatted text**: text copied in Word, Outlook or a browser keeps bold, colours, tables and links both ways (it also goes as HTML, the Windows "HTML Format"). Each application pastes the format it supports: Notepad and WordPad, just the text. The Clipboard panel always sends plain text.
- **Files**: drag them onto the remote screen and drop them where you want them pasted: on the desktop, in an open Explorer folder, in a mail being written… They are uploaded, put on the remote clipboard and pasted with a click on that point and Ctrl+V. The gateway says when the application asks for them: "N file(s) pasted". If it does not within 10 s, they stay on the remote clipboard to be pasted by hand with Ctrl+V.
  - On the desktop, Windows puts them in the first free slot (not exactly where they were dropped).
  - The click is a real click: dropping them on a button presses it.
  - The Files panel only puts them on the remote clipboard (Ctrl+V wherever you want): choose them or drop them on its dashed zone. It lists the files sent last and their state: being sent, on the remote clipboard, pasted, or no longer there once something else was copied. Folders cannot go through the clipboard (use the shared folder). Files copied remotely are offered as a download.
- **History** (Clipboard panel), like Win+V:
  - It keeps the last 25 texts and images that went through the shared clipboard, either way, newest first, with where they came from ("From the remote computer" or "From this device") and the time. Copying the same again moves it up.
  - **Paste** (text only) pastes it into the active application of the remote computer: the gateway puts it on the remote clipboard, presses Ctrl+V and leaves the clipboard as it was, as with the phone keyboard (see [MOBILE-KEYBOARD](MOBILE-KEYBOARD.md)).
  - **Copy** makes it the clipboard on both sides, to paste it with Ctrl+V wherever you want.
  - It lives only in that window's memory (never sent to the gateway nor stored) and is cleared when the window closes; items can be removed one by one or all at once. Texts up to 1 MB and images up to 4 MB.

## Shared folder

*Shared folder* in the web interface manages a personal folder on the web server; in the session it is a drive that Windows Explorer lists under "Redirected drives and folders" as **Shared folder on MuDesk** (in the language of the page; Windows adds its own "on"). The administrator sets the quota; the bar at the top shows how much is used.

It works like a file explorer:

- **Folder tree** on the left (a folder is read when it is opened), the folder's contents on the right in **Details** (name, modified, size; click a heading to sort) or **Icons** (images with a thumbnail), a path bar, **Parent folder** and a search box for the folder. On a phone the tree opens with the **Folders** button.
- **Upload**: **Upload files**, **Upload folder**, or drag files and folders from the computer onto the list (the folder shown) or onto any folder of the list, the tree or the path bar. Dragged folders keep their structure, empty folders included (the **Upload folder** button cannot send empty ones: browsers do not give them). When something with the same name is already there it asks: **Replace** (folders are merged, files overwritten), **Skip** or **Cancel**. The status bar shows the progress, with an X to cancel; the upload carries on while you move to another folder, and leaving the page asks first.
- **Organise**: drag items onto a folder (list, tree or path bar) to move them; holding them over a closed folder of the tree opens it. **New folder** is created and named at once; **Rename** (F2) edits the name in place; **Delete** (Del) asks first, folders with everything in them.
- **Select**: click, Ctrl+click, Shift+click, the boxes, a frame drawn with the mouse on an empty part of the list, Ctrl+A. Keys: arrows, Home/End, Enter opens, Backspace or Alt+↑ goes up, typing jumps to the name. Right click opens a menu.
- **Download**: one file as it is; several items or a folder in one ZIP, written by the server as it is sent (no copy on the server; up to 4 GB and 65,535 items). In Chrome and Edge, items dragged onto the computer's desktop are downloaded there. A double click opens a folder, downloads a file, or shows an image in a new tab.
- The folders of the tree have their own actions: right click (Open, New folder inside, Download as ZIP, Rename, Delete), F2 renames in place, Del deletes after asking, and they can be dragged onto another folder. When the folder you are in is renamed or moved the page goes with it; when it is deleted, the page goes to its parent.
- On a phone or tablet a tap opens; the boxes select (then a tap adds to the selection).

## A folder of this computer

With the shared folder's option, the session's **Files** panel has **A folder of this computer**: **Choose folder…** asks the browser for a folder of the computer you are on, and while the session lasts it is one more drive there, by its name (letters outside plain ASCII, such as accented ones, are left out of it) (**<name> on MuDesk** in Windows Explorer, `\\tsclient\<name>` for programs, as `net use` lists it). Its files go straight between the browser and the session: nothing is kept on the web server. **Stop sharing** takes the drive away; a session connected again shares it again.

- **Chrome and Edge**: read and write; the browser asks once whether the page may change the folder's files. What a program writes is saved when it closes the file (or before something reads it: the browser reads only what is saved), and meanwhile Windows sees the file at its size as written. A program that reads and writes the same large file by turns (a database) is slow there: each read saves the file first, and the next write copies it.
- **Firefox** (and browsers without File System Access): read only, as an upload of a folder gives its files: programs there can open and copy them, not change, add or delete them (the drive says it is read only). Folders with no files in them are not seen.
- The files read, written, created, emptied, deleted and renamed are in the audit log (`local_file`, `local_delete`, `local_rename`, and `local_folder_shared` / `local_folder_unshared`, also when the session ends with files still open), with the folder's name, never their contents. Without the shared folder's option the panel does not offer it; if a Remote Desktop Gateway's policy forbids drives, the folder is not shared and the page says so.
- Each file read goes through the gateway in pieces of up to 1 MB; a folder's listing goes with its first name in one message (up to 3 MB; a larger one name by name) and the gateway gives Windows the rest (155 files in about 1 s). The drive's size and free space are not known to the browser: it shows 1 TB (none free when read only).

## MuDeskPDF printer

Printing to **MuDeskPDF** in the remote session sends the document to the browser as PDF: a notice offers **Print** (browser print dialog, any local printer) or **Download**. Browsers cannot see local printers directly, which is why printing goes through PDF. Documents that are not PDF (PostScript, XPS) can only be downloaded.

## Several screens

> In **Chrome and Edge** (and other Chromium-based browsers) the *Window Management* API lists the screens. **Firefox and Safari do not have it**: the other screen **is looked for** by opening a window next to the current one (see *Firefox and Safari*, below); the connect dialog says so. **Full screen** always covers the screen the window is on.

Chrome and Edge (Window Management API): tick **Use all my screens**, allow the permission, and each screen becomes a separate monitor of the remote session (not one stretched desktop). In the same click, the other screen's window opens; with **Start in full screen** (ticked by default), every screen goes to full screen (see *Full screen on every screen*).
- **A screen is part of the remote desktop only while its window is open.** On connecting, the remote computer has this window's monitor and that of each window already open; opening another screen's window adds its monitor, and closing it removes it, and Windows moves its programs to the screens left. So no program opens on a screen nobody sees. The change is made without reconnecting (Display Control; servers without it reconnect). Until the server takes the new monitor, its window shows black and sends no mouse input.
- The other screens' windows close with the session's window: when the session ends, when its tab is closed or reloaded, or when it shows something else.
- **Full screen** also opens the other screen's window when it is closed (or open them from the **Screens** panel); in each new window press its **Full screen** button. That window has a bar at the top with the look of the session's toolbar (it comes back with the pointer at the top edge): the **Full screen** button, with its same icon (**Exit full screen** in full screen), and **Close this screen** (an X). Chromium allows one thing per click (full screen or a new window), except a window opened right after asking for full screen on a given screen: that is why it is asked that way. Once connected, the **Screens** panel opens by itself while a screen's window is closed.
- If the session was connected without that option and the computer has several screens, **Full screen** offers **Use all of them** (the session reconnects with a remote monitor on each screen) or **Only this one**.
- With **When the window is resized: Change the remote resolution** (the default), each remote monitor takes the size of its window and follows it: going full screen, resizing the window… with no black margins and no reconnection (Display Control; servers without it reconnect with the new size). The monitors stay side by side (or one above the other), as the screens. With the other modes, each window shows its monitor whole and in proportion.
- Dragging from one screen to the other (a window, an icon) works: while the button is held, the remote point comes from the pointer's position on the screen and the window under it.
- With a **RemoteApp** connection, each screen's window shows the page with the program's windows that are on that screen. The taskbar stays in the session's window, whose screen is the remote primary one.

### Firefox and Safari

Without the API, the page cannot ask for the list of screens, but it can know which screen each of its windows is on. So it looks for the other one:
1. Tick **Use all my screens** when connecting (or press **Screens** → **Look for other screens** in the toolbar, once connected).
2. A window opens right at the corner of the next screen: to the right; or where the other screen was found the time before; or, when the session window is not on the main screen, towards the main one. If there is a screen there, the window lands on it and tells where it is and its size; Firefox puts it back on the current screen when there is none.
3. Found, the session connects (or reconnects) with a remote monitor on each screen, placed as on the desktop, and that window fills the other screen and shows it (its remote monitor takes that window's size as soon as the session connects); with **Start in full screen**, each window goes to full screen as said below. Closing that window takes its monitor out of the remote desktop; it comes back with **Screens** → **Open**.
4. If it is not found (for example, the other screen is to the left of the main one), that window says so: take it to the other screen and press **Use this screen**. This browser remembers it and next time looks there directly (and **Full screen** offers to use them all).

Pop-ups must be allowed for the site: browsers let a page open one window per click, which is why one place is tried each time. Two screens are used. Tested in Firefox 160 with two 1920×1080 screens; also in Edge 157, and in Chrome after its permission prompt. Safari has never been tested (no Apple device).

### Full screen on every screen

**Start in full screen** (connect dialog, ticked by default) puts the session's window in full screen with the click on **Connect** and, with **Use all my screens**, the other screens' windows too. Browsers allow full screen only from a click in that same window, so as they come:
- **Chrome and Edge**: the session's window goes to full screen with Connect; each other screen's window opens and goes to full screen with its first press (that press is not sent to the remote computer; on a touch screen, it goes to full screen when the finger is lifted).
- **Firefox**: the click on Connect opens the other screen's window (full screen is asked for after it: the click lets one new window open, and asking for full screen first takes the click, so Firefox blocked the window); the first press in each window (the session's too) puts it in full screen. Firefox gives full screen only to the window in front: refused to a window that is not, it is asked for again when that window comes in front.
- **Brave**: its fingerprinting protection hides the real screens, so only one screen is used; the session's window goes to full screen with Connect.
- A connection opened without the dialog (a saved password, and *Remember these options and do not ask again*) has no click: its window goes to full screen with its first press. It uses this screen only, as no window can open without a click: **Full screen** then offers the others (**Use all of them**).
- Once you press in a window in full screen, or leave full screen in it yourself (Esc, or its **Full screen** button), its presses go to the remote computer. A window taken out of full screen while another one was in front (Firefox, as it comes, when a window opens) goes back with its first press.

For every screen in full screen with the click on Connect alone (or, without the dialog, as the session opens), the browser has to allow full screen without a click for the MuDeskClient address. That is set on each computer, by its administrator (the **ⓘ** next to *Start in full screen* shows these steps, with the commands for the page's address):
- **Chrome and Edge**: the policy *AutomaticFullscreenAllowedForUrls* ("Allow automatic full screen on specified sites"; Edge 132 and later) with the address, for example `https://mudesk.example.com`. On Windows, by group policy or in the registry: under `HKLM\SOFTWARE\Policies\Microsoft\Edge\AutomaticFullscreenAllowedForUrls` (Chrome: `Google\Chrome` instead of `Microsoft\Edge`), a string value named `1` with the address.
- **Firefox**: in `about:config`, `full-screen-api.allow-trusted-requests-only`, `full-screen-api.exit-on.windowOpen` and `full-screen-api.exit-on.windowRaise` set to `false` (for every site; in a company, Firefox's AutoConfig can set them).

Measured with two 1920×1080 screens: Edge 158 and Firefox 160 (its pop-up blocker on) as they come and with that permission or those settings (every screen in full screen with Connect), Chrome 158 (this screen with Connect; with that permission, both with Connect) and Brave 158. In Chrome as it comes, the press in the other screen's window puts it in full screen (checked by hand; in an automated session with no window in front of the desktop, Chrome refused it). The Chrome and Edge permission was given through the browser's developer protocol, as the policy gives it: the policy itself has not been tried. Safari has not been tested.

## On-screen keyboard

On a computer with a mouse, the **On-screen keyboard** button opens a full keyboard over the session (Esc, F1–F12, Del, digits, letters and punctuation, Tab, Caps Lock, Shift, Ctrl, Win, Alt, AltGr, Space, Backspace, Enter, arrows; the right Alt is AltGr with the Spanish layout). It works with any server, xrdp included.
- Each key is sent as the physical key: the keyboard layout of the remote session gives its character, as with a real keyboard (dead keys such as ´ and AltGr included).
- Shift, Ctrl, Alt, AltGr and Win stay pressed until the next key (Ctrl + C, Win + E, Shift + 4 = $…), are shown pressed and a line over the keyboard says so. To send one alone, press it again: Windows acts when it is released (Win alone opens Start).
- The labels follow the layout of the connection: Spanish or English (US). With other layouts, the browser's own when it gives them (Chrome, Edge), else the English ones.
- It moves anywhere in the window by dragging it with the mouse from its four-arrow grip or its edge (keys do not move it); it never leaves the window and, opened again, it is where it was left. **X** closes it.

## Phones and tablets

| Gesture | Action |
|---|---|
| Tap | Left click |
| Long press | Right click |
| Drag | Drag with the left button |
| Two fingers up/down | Scroll |
| Pinch | Zoom the picture; drag with two fingers to move around |
| Tap a text box | The device keyboard opens |

With the connection option **Multitouch: fingers reach Windows as touch** (off by default; Windows 8 or later, which opens its touch channel), the fingers no longer move the mouse: each one reaches Windows as a touch (up to 10 at once), and Windows makes its own gestures (tap, press and hold, pan and pinch in programs that take them, as on a touch screen). Pinching then no longer zooms the page's view. Until Windows says it is ready, and if it suspends touch input, the table above applies.

With the "Phone keyboard through the clipboard" option (in the connection settings; on "Automatic" it is ticked by itself on phones and tablets, and it can be unticked in the connect dialog), text the phone keyboard sends in one go (autocorrection, swipe typing, dictation) is pasted through the remote clipboard, because Windows 11 Notepad, Terminal and Explorer garble letters that arrive close together. The clipboard is then left as it was (an image copied in Windows included) and the text does not show in the clipboard history (Win+V). Single letters go as before. In programs where Ctrl+V is not paste (PuTTY, vim), set the option to "Never". The ⓘ icon next to the option explains the problem, the tests that found it and the sources. More in [Phone keyboards and Windows 11](MOBILE-KEYBOARD.md).

The keyboard opens when, after the tap, Windows shows the text cursor (the I-beam). It also shows over text that cannot be edited (web pages, read-only documents); close it with the device's button. If it does not open, use the **On-screen keyboard** button on the bar.

## Installing as an app

On phones and computers, browsers that allow it can install MuDeskClient as an app (for example *Install app* in the browser menu, or *Add to Home Screen* on iPhone and iPad, not tested: no Apple device). It opens in its own window with its icon. It is the same web application: there is no service worker and nothing is kept for offline use.

## After an update

When MuDesk is updated on the server, the page loads the new files the next time it is opened. A page that was already open says so at the bottom (**Reload**, or X to close the notice) the next time it asks the server for its state: when you sign in or out, when its session expires, or after changing the language, the password or a second factor. Reloading disconnects a remote session open in it.

## Session expired

The web session closes after the idle time the administrator sets (30 minutes by default) and, in any case, after 12 hours. When it does, a **Session expired** window says why (no activity, the 12 hours, a password change, the account disabled…). **OK** takes you to the sign-in screen and, once signed in again, back where you were.
- The page notices on its own, without waiting for a click: when the session should end, it asks the gateway. That question does not count as activity, so it does not keep an idle session open. If you are using it in another tab, the session stays open and nothing is shown.
- Using a remote session in that window counts as activity and keeps the web session open. If it ends anyway (no input for the idle time, or the 12 hours), the remote session ends with it and the window says so at once.
- Signing out, or the session ending, also ends the remote sessions opened from it. Signing out in one tab ends the other tabs of the same browser too, and each says so.
- Changing your password ends the remote sessions of your other sign-ins; the window where you changed it goes on.
- When your password is asked again (to add a passkey or an authenticator app, change the password or remove a second factor), five wrong ones close the session.

## Profile

- **Passkeys**: each one is "Passwordless" (you sign in with it alone, with **Sign in with a passkey**) or "Second step" (you sign in with your password, then confirm with it). The kind depends on the device and browser: passwordless only if they can keep with the passkey the key that encrypts your remote passwords (the PRF extension); MuDesk says so when you add it, and the list shows it.
- **Password, language, two-step verification (TOTP or passkeys).** A TOTP code works once: a code already used, such as the one that turned 2FA on, is refused and the message asks you to wait for the next one.
- **Your open remote sessions**: the sessions of your user that are running; **End** closes one.
- **Trusted browsers**: the browsers you have signed in from, with when each was added and last used, the browser and the IP. From them you can sign in even while your user is locked by failed attempts of others. **Forget** removes one and **Forget the others** all but this one; their cookies stop working. Removals go to the audit log.
- After signing in, if there were failed attempts with your user since your last sign-in, a notice shows them (how many, the last one's date and IP), read from the audit log (up to 90 days). If they were not you, change your password and check your trusted browsers. Once closed, the notice stays closed.

When the administrator requires 2FA and you do not have it yet, you sign in and only see your profile until you add TOTP or a passkey.

With a company account: signed in with OpenID Connect, the profile has no password, two-step verification or passkeys of its own (the provider's sign-in has them); with a Windows account, the password is changed in Windows.

## Linking your company account (OpenID Connect)

When the administrator has set up signing in with a company account, the sign-in screen has a **Sign in with …** button (with the provider's name: Microsoft, Google…). A user who already had a MuDeskClient user name and password links it to their company account once, from their profile; then either one signs them in. MuDeskClient never links them by the name alone (up to 1.2.0 the first sign-in through the provider with a user's name took that user, without its password or second step). Until it is linked, **Sign in with …** answers *You already have a MuDeskClient user of that name, but it is not linked to your company account: sign in with your password and link it in your profile.*

Step by step:

1. On the sign-in screen, sign in with your MuDeskClient **user name and password** (and your second step, if you have one), not with **Sign in with …**.
2. Open **Profile** in the menu at the top.
3. In the **Company account** card, click **Link with …** (the provider's name). If the card is not there, see below.
4. The browser goes to the provider's sign-in page: sign in there with **your own** company account (and its second step), and accept if it asks whether MuDeskClient may know who you are.
5. You are brought back to your profile with *User linked to your company account.*; the card now says *Your user is linked to your company account: you can sign in with it.*
6. From then on, **Sign in with …** opens that same user, also if your name or e-mail at the provider changes later. Your password and your passkeys keep working as before.

Good to know:

- One company account is linked to one MuDeskClient user, and one user to one company account. Check that you sign in at the provider with your own account: once made, the link stays until an administrator undoes it (see below); then you link the right one again from step 1.
- Signed in through the provider, its sign-in and its second step are the ones that count: MuDeskClient does not ask for its own. That session cannot open the RDP passwords you saved (they are encrypted with your MuDeskClient password), so each one is typed when connecting; signed in with your password, they are there as always.
- An error at the provider (cancelled there, an e-mail domain not allowed, a sign-in that expired) brings you back to your profile, where it is said; start again from step 3.

If the **Company account** card is not in your profile:

- the sign-in screen has no **Sign in with …**: signing in with a company account is not set up;
- you signed in with **Sign in with …** in this session: sign out and sign in with your password;
- your user is an administrator (administrators keep their own password and second step, and are never linked) or a Windows account (it signs in with the domain's password);
- it is linked already: the card says so.

If it says *It could not be linked: that company account is another user's, or this user cannot be linked.*, that company account is already linked to another MuDeskClient user (for example one made by its first sign-in through the provider): ask the administrator.

For administrators: users made by the provider (**Create the user**), and those linked by signing in through it before this version, are linked already; nothing to do. To undo a link (a user who linked a company account that is not theirs), open *Administration → Users*, **Edit** that user and click **Unlink company account**, then **Yes**: the user can no longer sign in with that account, their open sessions end (remote ones too), and they link the right one again from their profile. A user the provider made cannot be unlinked (it has no other sign-in). Tell the others who will sign in with the provider to link it as above before they first use **Sign in with …**. The audit log records each link (`oidc_link`; refused, with `other_account` or `not_linkable`), each one undone (`oidc_unlink`) and each sign-in refused because the account is not linked (`login_fail`, `not_linked`).

## Administration

- **Users**: create, enable/disable, delete, **Administrator rights** (a box, unticked for a new user; there can be several administrators, never none: the last enabled one cannot be disabled, demoted or deleted), **Auditor (read only)** (a box: the user also sees *Administration* with only the **Audit log**, **Active sessions**, **Recordings** and **Status**, without changing anything, ending sessions or recording them; with administrator rights ticked, they are an administrator), concurrent sessions, **Sign-in hours** (the days of the week and a span of time, such as Monday to Friday from 08:00 to 18:00, in the time zone of *Settings*; a span whose end is earlier than its start goes past midnight. Outside them the user cannot sign in or open remote desktops, while those already open go on; `outside_hours` in the audit log. Not for administrators), reset password (saved remote passwords are lost, and passkeys then only sign in as a second step after the password), remove 2FA, **Unlink company account** (a local user who linked one from their profile: see [Linking your company account](#linking-your-company-account-openid-connect)). Disabling or deleting a user, resetting their password or unlinking their company account ends their sessions, remote ones included.
- **Connections**: the administrator's connections, each one for the users ticked or for **all users** (also those created later), who cannot change or delete them; without a Windows user name, each user types theirs when connecting, and each one keeps their own password for it. In the Windows user, `{username}` becomes the MuDeskClient user name of whoever connects (for example `DOMAIN\{username}`): one connection serves every user whose Windows account has the same name. Below, every user's own connections, which the administrator can change or delete (their saved password can only be forgotten; it is also forgotten when the computer, port, user, domain, security or gateway changes). **Import .rdp** works here too: one file (or a new connection) opens with **All users** ticked; several files are saved for nobody yet ("Nobody sees them yet"), to edit and choose their users. **Import CSV** adds many at once from a spreadsheet saved as CSV (comma, semicolon or tab separated): the first row names the columns, `host` at least, and each other row is a connection. Columns: `name`, `group`, `host`, `port`, `user`, `domain`, `users` (MuDeskClient user names separated by spaces, `*` for all users; empty, nobody yet), `security` (`auto`, `nla`, `tls`), `gfx` (`auto`, `on`, `off`), `bpp`, `app`, `app_args`, `gw` (a Remote Desktop Gateway: its name, and `:port` when it is not 443), `lb` (a connection broker's load balance info), and the options `audio`, `mic`, `clipboard`, `drive`, `printer` (`1`/`0`, `yes`/`no`); an empty cell takes the editor's default. For example:

  ```
  name;group;host;user;users;mic
  Reception;Office;192.0.2.21;DOMAIN\{username};*;no
  Accounts;Office;192.0.2.34;;laura david;yes
  ```

  Every valid row is added; the result says how many, and each refused row by its number in the spreadsheet with the reason, users that do not exist and columns not used (`admin_conns_import` in the audit log). At most 2000 rows per file.
- **Settings**: client IP and RDP target allow-lists, sign-in lock-out, web and remote idle time-outs, sessions per user, **RDP sessions at once (all users)** (20 by default, 0 = no limit; each session holds a PHP process, so keep it below what the server has: see [HOSTING](HOSTING.md#capacity)), reconnection attempts when the connection is lost (10 by default, 0 = none; waits of about 1, 2, 3, 5, 8 and then 10 s: after the first, up to half as long again at random), 2FA required, the **time zone of the sign-in hours** (an IANA name such as `Europe/Madrid`; empty, the server's own), audit retention, shared-folder quota (one per user for the drive of all their sessions, the file manager, clipboard files and what is printed while the session lasts), **Users can create connections, import .rdp files and make manual connections** (off by default; administrators always can), **Users can record their own sessions** (off by default; administrators always can: see *Recorded sessions*), **Minutes unused after which a guest loses control** (15 by default, 0 = never: see *Sharing a session*), **Allow Kerberos with RC4 (Windows Server 2003 domains)** (off by default, with its risk said next to it: someone on the network between this server and the domain controller could pose as it and get something to try passwords against thousands of times faster than with AES; not needed for Windows XP, reached with Standard RDP Security, without Kerberos; without it those accounts sign in with NTLM) and **Allow saving the password of RDP connections** (on by default). Turning it off, once confirmed, erases the saved RDP passwords of every user (`rdp_passwords_erased` in the audit log, with how many); the connection form loses its password field and the connect dialog its "Save password" box: it is asked for when connecting.
- **Signing in with a company account** (in *Settings*):
  - **OpenID Connect** (Microsoft Entra ID, Google, Keycloak, Authentik…): register MuDeskClient with the provider as a web application (authorization code flow) with the **redirect address** shown there (`…/oidc.php`), and fill in the **issuer** (for example `https://login.microsoftonline.com/TENANT-ID/v2.0` or `https://accounts.google.com`), the **client id** and **secret**, and the name on the button. The sign-in screen gets **Sign in with…**. The MuDeskClient user is the account's e-mail (only one the provider marks as verified: Microsoft Entra ID does not, so use `preferred_username` there, the user principal name) or its `preferred_username`; the user made by its first sign-in is bound to that provider account (its `sub`), so a name or e-mail given later to another account does not sign it in; a user who already had a MuDeskClient password links it in *Profile → Company account* (**Link with…**, signed in with that password and the second step: never by its name alone; see [Linking your company account](#linking-your-company-account-openid-connect)), and until then the provider's sign-in with that name is refused (*You already have a MuDeskClient user of that name…*); an administrator, or a Windows account, is never linked (they keep their own sign-in); it must exist unless **Create the user** is ticked (it is then made as a plain user); the e-mail domains can be limited. Such a session cannot use saved RDP passwords (there is no password to open them: each one is typed when connecting), and the provider's own second step counts. The server must reach the provider over HTTPS and check its certificate (on Windows, PHP needs `openssl.cafile`).
  - **Windows account (Active Directory)**: the computer that checks the passwords (any RDP computer of the domain that accepts NLA and that the MuDeskClient server reaches), its port and the domain's NetBIOS name (or `.` for that computer's own accounts). On the normal sign-in screen, a user without a MuDeskClient password types their Windows name and password: they are checked the way Remote Desktop checks them before a session (NLA), without opening one and without the password going further. Their saved RDP passwords are encrypted with the Windows password: when it changes in Windows, they are forgotten (said in the audit log). Its password is changed in Windows. **The computer's certificate is pinned** when it is saved (shown under it): only that computer checks the passwords, since another one posing as it would accept any password. When Windows renews that certificate, Windows accounts cannot sign in (the users are told the accounts cannot be checked now, and the audit log says `ad_cert`) until *Pin the computer's certificate again when saving* is ticked and the settings saved. A computer that does not answer is not counted as a failed sign-in. The domain is required (or `.`). A passkey alone does not sign in a Windows account: the password first, so that an account disabled in the domain cannot go on signing in. Tested against a Windows Server 2022 domain ([TESTING](TESTING.md)).
  - Users made this way are marked *Windows* or *OIDC* in the list; their password is not reset in MuDeskClient.
  - With the allowed remote computers on **Allow all**, the server itself (127.0.0.0/8, ::1), link-local addresses (169.254.0.0/16, where clouds keep their metadata, and fe80::/10), the other cloud metadata addresses (100.100.100.200, fd00:ec2::254) and 0.0.0.0/8 or :: are never reached, nor their ::ffff:…, ::a.b.c.d or 64:ff9b:: forms; to reach them, use **Only the list** and list them. Administration shows a warning while "Allow all" is set.
  - To require 2FA for every user, the administrator must have it first; otherwise the setting is refused.
- **Diagnostics**: traces of the sessions started in diagnostic mode (or of every session with *Settings → Diagnostic mode in every session*): TLS/NLA negotiation, server data and capabilities, licensing, channels and their messages, audio formats (and the microphone's: offered, taken and opened), the camera (version, messages and pictures counted), clipboard formats, device redirection, graphics pipeline (versions, commands and codecs counted in the browser), message counts and sizes every 10 s, errors of the gateway and of the browser, end reason and server error code. Never screen, keys, clipboard or file contents, passwords or keys. Download or delete them; they are removed after 7 days (8 MB at most per session). Downloads and deletions go to the audit log. From the command line: `TRACE=1 php tests/rdp_probe.php …`. Useful to send when something fails with a server.
- **Active sessions**: who is connected where, and which are recorded; start or stop the recording of one, and end one (administrators only).
- **Status** (administrators and auditors): now, the active sessions against their limit, guests watching, sessions being recorded, the PHP processes they take, the memory of the largest session against PHP's `memory_limit`, the disk left and what recordings take, failed sign-ins, sessions ended by an error, certificates that did not match and access refused yesterday and today, the last housekeeping and the server (versions, time limit, load); and the last 30 days: sessions a day and most at once (with the limit drawn), the computers used most (hours), each chart with its table. **Refresh** reads it again.
- **Backup** (administrators): under *Make a backup*, **Download the backup** downloads the users, settings, connections, certificates, the audit and the keys of the data (`secret.php`, `audit-key.php`), and the users' folders and recordings when ticked, encrypted with a password you choose (10 characters at least; without it nobody can open it: keep it apart). A file the web server cannot read is said at once (the server's error log names it). Under *Restore a backup*, **Restore** sends the file in pieces, checks it whole with its password and only then puts it in place: the users, settings, connections, certificates and the audit become those of the backup, and the users' folders and recordings only when it carries them (else they stay as they are); every session ends, yours too, and you sign in again with the backup's users. A backup of a newer version (1.3 on a 1.2, say; not just a newer fix) is refused. If it cannot be put in place, the data goes back as it was (the sessions ended stay ended); what could not go back is never removed (it is kept in the data folder, in a `restore-kept` folder the server's error log names). Meanwhile the gateway answers *Restoring a backup*.
- **Recordings**: every recording, the newest first, to watch or download as a video (administrators and auditors; see *Recorded sessions*).
- **Audit log**: everything that happens, one line per event with date (ms), user, IP, browser and outcome (succeeded/failed with the reason). Never passwords or contents.
  - Sign-in: each attempt with method (password, TOTP, passkey) and failure reason (`unknown_user`, `bad_password`, `disabled`, `bad_code`, `locked_ip`/`locked_user`/`locked_global`…), setup, logout, sessions closed (idle, maximum time, other browser, password changed, user disabled or deleted), CSRF and IP refusals, refused requests.
  - Profile and administration: password, language, 2FA and passkeys, trusted browsers added (`device_add`) and forgotten (`device_forget`); users, settings and connections with old → new values (saved passwords only as "changed"); session termination (by an administrator or by its owner); audit searches, exports and verifications.
  - Remote sessions: options used (screen size and monitors, colours, audio, microphone, clipboard, drive, printer, H.264, compression), certificate trusted or changed, the Remote Desktop Gateway and the routing token used (with the gateway's transport, `websocket`, `http` or `rpc`, how the user signed in to it and what its policy forbade), its consent message accepted or not (`gateway_consent`: `why` when it was not, `declined`, `closed` (the page left), `ended` (the session ended meanwhile) or `timeout`; `again` when the same terms were accepted earlier in that session), NLA made with Kerberos, the encryption of Standard RDP Security (`rdp_security` in `rdp_start`: 40-bit, 56-bit, 128-bit or FIPS), a broker's redirections (`rdp_redirect`, with the address reached and `late` when it came after the sign-in), start, resizes, end with reason, duration and bytes; refusals (`rdp_denied`, for example `busy` when the server is full).
  - Clipboard (each copy, both directions: type and size, file names and sizes), shared drive (each file read or written with bytes, created folders, renames, deletions; plain browsing is not logged), web file manager (uploads, downloads and ZIPs with the names, folders, moves and renames as `file_move`, deletions; thumbnails not logged), print jobs and their downloads.
  - Search by dates, user, event (prefix: `login` finds every sign-in event), IP, free text and outcome; the text is looked for in what a line shows (user, IP, event, browser and each detail as `key=value`, such as `reason=unknown_user`), in upper or lower case of any alphabet, never in the field names, the date or the chain's hashes; summary per event (click to filter); details of a line; export of the filtered results to CSV or JSON (up to 20 000 rows).
  - **Signed export**: the JSON export comes in a ZIP with `audit.json` and `audit.json.sig`, a signature made with the server's RSA key; each row is the line as stored. The CSV is not signed. To check a file, open *Checking the signed exports* (below the export buttons), save the public key as `mudesk-audit-key.pem`, unzip the export and run `openssl dgst -sha256 -verify mudesk-audit-key.pem -signature audit.json.sig audit.json`: it answers "Verified OK", or fails if the file was changed. The key is made the first time (about 2 s) and kept in `data/audit-key.php`.
  - Kept 90 days by default; *Settings → Days of audit log to keep* (0 = no limit). The purge is itself recorded.
  - **Verify integrity**: every line is signed and chained to the previous one (HMAC with the server key). Nothing is hidden: changed or inserted lines and missing lines are listed and marked in red. It checks up to the moment it starts; lines written meanwhile are left for the next check. Someone with the server key (`data/secret.php`) could rewrite the whole chain, so keep a copy of the logs elsewhere if you need stronger proof.
