# Architecture

[Español](es/ARQUITECTURA.md)

## Goals and constraints

- Remote desktop (RDP) in the browser with **nothing installed on the remote computers**.
- Browser side: HTML, CSS and JavaScript only (ES modules, no libraries).
- Server side: **plain PHP 8.1 – 8.5**, only the bundled `openssl` and `session` extensions, no Composer dependencies, no database (JSON files).
- Must run on **shared hosting**: no daemons, no listening ports, no WebSocket.

## Overview

```
Browser                                     Web server (PHP)                          Remote computer
┌──────────────────────────┐   HTTPS   ┌──────────────────────────────┐   TCP/TLS  ┌───────────────┐
│ app.js (UI)              │◀────────▶│ api.php   users, connections │            │               │
│ session.js (input, view) │           │ files.php shared folder      │            │  Windows /    │
│ stream-worker.js ────────┼──────────▶│ rdp.php?a=stream  ───────────┼──────────▶│  RDP server   │
│   gfx.js / orders.js     │◀── frames ┤   (one long request = 1 RDP │◀──────────┤  3389         │
│ audio.js, mic.js, clip…  │           │    session, src/Rdp/*)       │            │               │
│        input ────────────┼──────────▶│ rdp.php?a=send (short, IPC) │            └───────────────┘
└──────────────────────────┘           └──────────────────────────────┘
```

`index.php` asks for `app.js` and `app.css` with `?v=<version>-<fingerprint>`: `Http::build` hashes the names, sizes and dates of the scripts and styles in `public/assets`, so an update changes the address even when the version number does not. The same fingerprint goes in `data-build` of `<html>` and in the `state` answer (`build`): a page older than the gateway says so and offers to reload when it asks for the state (at start and on signing in; not on every request, since the fingerprint costs about 0.8 ms).

### Why one long HTTP request per session

A normal PHP request ends after the response and the RDP connection must stay open for the whole session. Shared hosting does not allow background processes or WebSockets, so each session is **one HTTP request that does not end**: `rdp.php?a=stream` opens the RDP connection and streams binary frames to the browser (`fetch` + `ReadableStream`). If the hosting cuts the request, the browser reconnects automatically and the Windows session is still there.

Frame format (server → browser): `[u8 type][u32 length][payload]`

| Type | Content |
|---|---|
| 0 | padding (makes some proxies start forwarding) |
| 1 | RDP update: `u8 fast-path code` + data (bitmaps, palette, pointers, drawing orders) |
| 2 | desktop size: `u16 width, u16 height, u8 bpp` |
| 3 | status JSON (`token`, `connected`, `end`, `errorInfo`…) |
| 4 | clipboard sub-protocol (`Cliprdr`) |
| 5 | display control available (dynamic resolution) |
| 6 | keep-alive |
| 7 | audio sub-protocol (`Rdpsnd`) |
| 8 | print job JSON (`Rdpdr`, MuDeskPDF) |
| 9 | graphics pipeline message (RDPGFX, decoded in the browser) |
| 10 | bulk compression on: fast-path update as received: `u8 code, u8 fragmentation, u8 compression flags` + data |
| 11 | bulk compression on: slow-path data PDU as received: `u8 compression flags, u8 pduType2` + data |
| 12 | RemoteApp: JSON about the program's windows that does not come with the drawing orders (a window cloaked or shown again) |
| 13 | microphone: `u8 1, u32 rate, u8 channels` (a program of the remote computer records: send 16-bit PCM like this) or `u8 0` (stop and let go of the microphone) |

Messages from the browser (`rdp.php?a=send`, after a `u32` sequence number: `u8 type` + data):

| Type | Content |
|---|---|
| 1 | input events (keyboard, mouse, Unicode) |
| 2 | resize: `u16 width, u16 height` |
| 3 | page visible or hidden |
| 4 | clipboard sub-protocol (`Cliprdr`) |
| 5 | quit |
| 6 | refresh: the server draws everything again |
| 7 | typed text: characters with their pauses |
| 8 | several characters at once (UTF-8): pasted with "Phone keyboard through the clipboard", else typed |
| 9 | reserved (ending a session from the gateway): refused from the browser |
| 10 | graphics pipeline frame acknowledgement |
| 11 | diagnostic note of the browser (diagnostic mode) |
| 12 | a text of the clipboard history (UTF-8), always pasted (with the clipboard on) |
| 13 | several monitors, each the size of its window (JSON) |
| 14 | RemoteApp command (JSON, see below) |
| 15 | microphone audio: 16-bit PCM in the format of frame 13 (about 100 ms each; while one waits to be sent the next is joined to it, at most a second, the oldest dropped) |

Besides the stream and these messages, `rdp.php?a=clipfile` takes clipboard files and images in chunks (into `tmp/<sid>/`, counted in the quota) and `rdp.php?a=print` hands out a print job.

### Session admission and time limits

- Each session holds a PHP process while it lasts, so the number of sessions is limited per user and for all users together (`max_sessions_total`, 20 by default). Before any output, `rdp.php` counts the running sessions and registers the new one under one lock (`data/run/register.lock`), so two requests at the same time cannot both take the last place. A full gateway answers 503 `busy` at once, before opening a socket.
- Each handshake step (TCP, TLS, X.224, NLA, MCS) waits at most 8 s; the activation, 30 s. If the browser closes while connecting, the PHP process is freed within 1–2 s.
- The target name is resolved after the admission, so the global limit also bounds the processes waiting for a slow DNS server (see [HOSTING](HOSTING.md#host-names-dns)).

### Input path (browser → server)

Keyboard, mouse, clipboard and resize messages go through **short POST requests** to `rdp.php?a=send`:

- No PHP session is opened (no session-file lock, no user file read): they are authorised by a random **per-session token** delivered in the first status frame and sent in the `X-MuDesk-Token` header (not in the URL, so it stays out of the web server logs). The session's file in `data/run/` keeps only its SHA-256: a copy of the data folder gives nobody the keyboard of a running session.
- Every message carries a `u32` sequence number. The browser keeps **up to 4 requests in flight**; the stream process re-orders them (gaps older than 0.5 s are skipped).
- Mouse moves are coalesced while requests are in flight (only the last of the browser's coalesced events is placed). Mouse moves and graphics-pipeline frame acknowledgements take 3 of the 4 slots at most and take turns, so an acknowledgement never starves behind a moving mouse (Windows paces its frames by them) and a key or a click always has a slot.
- **Typed text** (on-screen keyboards, IME, autocorrection) keeps its order with the rest of the input in a queue in the gateway (`Client::input`):
  - A single character (message type 7) goes as Unicode and whatever comes behind waits 100 ms; the pause is applied in the gateway because HTTP requests arrive unevenly spaced.
  - Several characters at once (message type 8, UTF-8), with the "Phone keyboard through the clipboard" option, are **pasted** (`Client::pasteText`, `Cliprdr::typeText`; reasons and tests in [MOBILE-KEYBOARD](MOBILE-KEYBOARD.md)). Texts in a row are joined. When the last thing was copied in Windows, it is read first (all its formats, up to 16 MB) to put it back; with files or over 16 MB the text is typed. The gateway announces the text (with the formats that keep it out of the history and the cloud), waits for the answer to *that* announcement (Windows answers each list in order) and for the screen to change after the last input sent, presses Ctrl and V and holds them until the application asks for the text, hands it over, releases them and puts the clipboard back right after each paste (an empty text when nothing was copied). Windows confirms an announcement before applying it and did not apply a list equal to the one it had (two pastes in a row pasted the previous text again), so each announced list carries a format of its own that alternates: two lists in a row never match. Without the option the text is typed as Unicode.
  - A text of the clipboard history (message type 12, UTF-8, up to 1 MB) is always pasted this way, whatever the option (connections with the clipboard on).
  - Input waiting behind a paste goes out once the screen changes (the application has drawn the paste).
  - Limits only for when Windows does not answer: 2 s for the answer to the announcement and for the screen change, 10 s for the application to ask for the text; then it is typed as Unicode.
- RemoteApp (message type 14, JSON): the desktop synced (`ready`: the server's windows all sent, with how many are open; the program may be asked for), a window brought to the front (`activate`), minimized, maximized, restored or closed (`sys` with one of those four commands only).
- The short request hands the message to the long one through a **Unix socket** in `data/run/` (or in the system temp folder when that path reaches 100 characters); on Windows, which has no Unix sockets for PHP, through a **TCP port of this computer only** (127.0.0.1), each message starting with a secret of the session kept in its mode file (any local process can connect to such a port); without `stream_socket_server` or with `'ipc' => 'file'`, through a queue file polled every 20 ms (Windows used it before: each key, mouse move and frame acknowledgement waited up to 20 ms). Each request is one connection to the socket with one message, kept apart until all of it has arrived: added to one buffer as it came, a large message (a paste) arriving in pieces had the other requests' messages in between, and the session's input stopped for good.

### Screen path

- The stream is read and decoded in a **Web Worker** (`stream-worker.js`), so input never waits for drawing.
- Decoders (`gfx.js`): interleaved RLE (8/15/16/24 bpp), planar (32 bpp), uncompressed, palettes, pointers (colour, new, large). 15/16-bit pixels use lookup tables.
- Decoded rectangles are transferred to the main thread (`postMessage` with transferable buffers) and drawn with `putImageData`.
- Drawing orders (`orders.js`: DstBlt, PatBlt, OpaqueRect, ScrBlt, MemBlt) and the **bitmap cache** (revision 2, three cells of 600/600/1024 entries: secondary orders *cache bitmap v2* store decoded bitmaps, MemBlt draws them) are parsed in the worker and executed on the canvas; the cached bitmaps live on the main thread as small canvases. On by default (`drawing_orders`): validated pixel-identical against xrdp and Windows 11. MemBlt and PatBlt take any ROP: the plain copies (SRCCOPY, PATCOPY) are drawn by the canvas, the others pixel by pixel on the main thread (`drawRop` reads the rectangle, `rop3` computes each bit from brush, source and destination; PATINVERT XORs the brush colour or pattern). Mem3Blt is not negotiated (Windows sends bitmaps instead), so a MemBlt whose ROP uses a brush takes GDI's default white brush. **Text** (same setting): GlyphIndex, FastIndex and FastGlyph with the glyph cache (Cache Glyph revision 2, which servers send as order type 3 for glyph support level "encode"; ten caches) and the 256-entry fragment cache. The worker keeps glyph sizes and resolves positions (deltas, fixed pitch, fragments); the main thread turns each 1 bpp glyph into a `Path2D` of its pixel runs once and fills it in the text colour, clipped to the background rectangle (the opaque rectangle is filled first with the order's *foreground* field and the text uses the *background* field, as RDP defines them). Checked against hand-built orders (`tests/orders_unit.mjs`), pixel-exact in Chrome and Firefox (`tests/e2e_glyphs.mjs`), and with the real text orders of xrdp's own login window: the text is identical to the bitmap version at 16 and 32 bpp. PatBlt draws 8x8 pattern and hatched brushes (PATCOPY; a set bit takes the background colour, as in GDI). Order colours at 24/32 bpp are red, green, blue bytes. Brush and colour table caches are not negotiated and are skipped by length.
- **Bulk compression** (`bulk_compression`, on by default, `'rdp61'`): the client offers up to RDP 6.1 and the server picks a type no higher than that for each block: MPPC with a 64 KB history ("RDP 5", `Mppc.php`, used by xrdp), NCRUSH ("RDP 6.0", `Ncrush.php`: Huffman-coded literals, copy offsets with a 4-entry cache, 64 KB history; decoding tables built from the codes of MS-RDPEGDI) or XCRUSH ("RDP 6.1", `Xcrush.php`: an inner MPPC over a level that copies matches from a 2,000,000-byte history; Windows Vista SP1/Server 2008 and later). `Bulk.php` dispatches by the type of each block and creates each history when first used. Measured on the same 11.1 MB of xrdp screen updates compressed by FreeRDP's compressors: MPPC 3.05 MB and 0.53 s of gateway CPU, NCRUSH 4.85 MB and 0.93 s, XCRUSH 2.08 MB and 0.32 s; browser 0.09/0.18/0.06 s. XCRUSH needs about 4 MB more memory in the gateway and 2 MB in the browser. The gateway decompresses everything to keep the shared history and to read slow-path PDUs, but forwards updates **as received** (frames 10 and 11); the worker (`bulk.js`) keeps an identical history, decompresses, reassembles fast-path fragments and turns slow-path updates into the fast-path form. Both links carry compressed data. Virtual channels are opened without `CHANNEL_OPTION_COMPRESS_RDP`, so channel data is never compressed.
- **Graphics pipeline** ("Graphics" option, MS-RDPEGFX; never with RemoteApp, where each window would come on a surface of its own; AVC444 and AVC444v2 are shown from their 4:2:0 stream): in automatic mode `Client` turns it on (at 32 bpp) when the Windows version in the NTLM challenge is 6.3 or later. `Drdynvc` opens the `Microsoft::Windows::RDS::Graphics` channel, advertises capability sets 10.7 (no scaled mapping) and 8.1 with AVC420 only when the browser decodes H.264 (checked with `VideoDecoder.isConfigSupported`), and 8.0, and forwards every message untouched (frame type 9). The worker (`rdpgfx.js`) decompresses ZGFX, parses the PDUs and decodes: AVC420 with WebCodecs (the SPS is rewritten to declare BT.709 full range and no frame reordering, otherwise browsers assume limited range and may buffer frames), RemoteFX and RemoteFX progressive (`rfx.js`: RLGR1/3, dequantization, plain and reduce-extrapolate inverse DWT, upgrade passes; the tiles of a message go into one box around its rectangles, or, when the rectangles are sparse (the box would be over twice their area), into a box per rectangle (`#region`): two corners of the screen give 33 KB instead of 8.3 MB), ClearCodec (residual, bands with vBar caches, NSCodec/RLEX subcodecs; glyph cache kept with the surfaces), planar, uncompressed and alpha. Operations keep their order: those after an H.264 frame wait for the decoder. The main thread (`gfxsurfaces.js`) keeps one canvas per surface plus the surface cache, and copies mapped surfaces to the desktop canvas. Each end of frame is acknowledged (message type 10; only the latest pending one is sent), which gives the server its flow control. Requires 32 bpp (forced). Early capability flag (`earlyCapabilityFlags`) `RNS_UD_CS_SUPPORT_DYNVC_GFX_PROTOCOL` is set in the core data.
- Several screens: the remote desktop is drawn on an offscreen surface; each window (one per screen) copies its monitor region on the next animation frame. A screen is a remote monitor only while its window is open (`RdpSession.setMonitors`, `#wanted`, `#checkMonitors`): the new layout goes as browser message type 13 (JSON `[[x,y,w,h,primary],…]`, checked by `Drdynvc::monitors`) in one Display Control layout, as a plain resize when one is left, or by reconnecting without Display Control; until the server takes it, that window is black and sends no input. Full screen asks `requestFullscreen({ screen })` and opens the other windows in the same click (`fullAndOthers`).
- Screenshot: `RdpSession.areaOf` maps the frame drawn over the canvas to desktop pixels; `capture` makes the PNG at full size, without toolbar or pointer.
- **Limits against corrupt or hostile data** (found with `tests/fuzz.mjs`), so that sizes taken from the data cannot make the browser allocate without bound:
  - Bitmaps (updates and cached ones) no larger than the desktop rounded up to whole 64x64 tiles, and of a valid depth: the gateway sends the desktop size (frame 2) before any update, so the limit is known in time.
  - Surfaces and the graphics output up to 32766 px a side, the RDP maximum: the desktop size is not a limit there, because a single surface may span all the monitors.
  - Each rectangle within its surface and each ClearCodec subcodec within its rectangle (as FreeRDP does); quantizer indexes checked in RemoteFX and progressive; the end of each NSCodec plane and an SPS in the last bytes of an H.264 unit are handled.
  - Still possible: a hostile server can make the browser hold surfaces of up to 4 times the output (at most 8192 × 8192), about 1 GB at worst; beyond that the browser fails with a logged error.

## RDP implementation (`src/Rdp/`)

| Class | Responsibility |
|---|---|
| `Transport` | TCP + TLS (any version, self-signed accepted), `TCP_NODELAY`, framing (TPKT, fast-path, DER) |
| `Client` | X.224 negotiation, MCS/GCC (core, security, network, monitor blocks), Client Info, licensing, Demand/Confirm Active, finalization, fast-path input/output, static virtual channels, reactivation; RemoteApp asked for (`INFO_RAIL`, capability sets 23 and 24; a server without it ends the session with `app_unsupported`) |
| `CredSsp` + `Ntlm` + `Rc4` + `Der` | NLA: CredSSP v6 with NTLMv2, MIC, session security, public-key binding check; `.\user` takes the server's NetBIOS name from the NTLM challenge; the user name in upper case with Windows' own table (taken from Windows 11: 973 letters of every alphabet it changes, and none of those it leaves) |
| `Licensing` | RDS licensing exchange (MS-RDPELE): RSA, platform challenge |
| `Drdynvc` | dynamic channels; Display Control (MS-RDPEDISP) for resolution changes; graphics pipeline channel (forwarded to the browser, frame acknowledgements back); the microphone's `AUDIO_INPUT` (only with the option); a message longer than one 1600-byte channel chunk (1598 bytes with a channel id under 256) sent as Data First + Data PDUs |
| `Cliprdr` | clipboard (MS-RDPECLIP): text, formatted text ("HTML Format": the browser converts between HTML and CF_HTML, the gateway only forwards the bytes), DIB images, files (FileGroupDescriptorW / FileContents) |
| `Rdpdr` | device redirection (MS-RDPEFS/RDPEPC): the shared folder drive ("Shared folder on MuDesk", in the language of the page) and the MuDeskPDF printer |
| `Rdpsnd` | audio output (MS-RDPEA): IMA ADPCM, A-law, μ-law, PCM |
| `Audin` | microphone (MS-RDPEAI, `AUDIO_INPUT` dynamic channel; `INFO_AUDIOCAPTURE` in the Client Info): Windows opens the channel when a program there records and closes it when none does. The gateway answers the negotiation itself, at once (Windows waits 5 s at most for each answer, less than the browser may take to be allowed the microphone): version 1 (version 2 only changes AAC), the formats it takes (16-bit PCM, 1 or 2 channels, 8–48 kHz: mono first, the highest rate first), the open (the initial format confirmed with a Format Change PDU, then success) and later format changes. The browser is told the format (frame 13) and sends PCM (message 15); the gateway sends it in packets of the size Windows asked for (FramesPerPacket, kept between 10 ms and a second), each after an Incoming Data PDU, with at most a second waiting. A malformed message is left out without ending the session |
| `Rail` | RemoteApp (MS-RDPERP): the `rail` channel (handshake, client status, system parameters with the work area = the browser window less a 40 px taskbar (with several screens, the page's monitor, made the primary one); Client Execute once the browser reports the desktop synced (`ready`, with how many windows are open) or, without that report, 5 s after the handshake (not when reconnecting after a dropped connection), and once more 2 s later if the server was not yet watching the desktop (RAIL_EXEC_E_HOOK_NOT_LOADED); connected again (`again`: client status with AUTORECONNECT; `resume`: from a page where it was open), only if none came back; the server's refusals, the browser's window commands); the windowing orders are read in the browser (`orders.js`), which copies only the windows' visible regions to the page, says it is opening (after 15 s, that it is slow; after 90 s, that the program did not open), connects again quietly when the server ends the session before the program appeared (error info 0x0B), and ends the session when the program's last window has been closed for 3 s (windows of no size, with nothing visible, hidden, cloaked or tool windows do not count); with several screens each window's canvas gets the program's windows on its monitor, moved from the server's coordinates (primary at 0,0) to the desktop's |
| `Mppc` | bulk decompression (MPPC, 64 KB history) |
| `Bulk`, `Ncrush`, `Xcrush` | bulk compression level offered (`bulk_compression`) and NCRUSH / XCRUSH decompression (RDP 6.0 / 6.1) |
| `Trace` | diagnostic trace of a session in `data/trace/<sid>.log`: never contents; 8 MB per session, 256 MB in all, removed after 7 days |

Bitmaps are **not decoded in PHP**: the gateway only parses headers and forwards updates, which keeps CPU and memory low (measured: 0.19 s CPU and 4 MB to relay 34 MB of screen updates).

## Security model

- **Sign-in**:
  - First run: the administrator account can only be created with the one-time code of `data/setup-code.php` (behind `<?php exit; ?>`), so nobody can claim a freshly uploaded copy.
  - Passwords: bcrypt cost 12 (≈0.27 s), at least 12 characters, not one of the ≈30 000 common passwords of that length (`src/common-passwords.txt`), not containing the user name.
  - Brute force: failures counted per IP, per user name, per known browser and globally (all IPs). A locked IP is refused. A locked user name, or more global failures than `login_global_max` (a distributed attack), only lets in browsers where that user already signed in (signed *device cookie*, revoked when the password changes), so an attacker cannot lock the owner out. Each known browser has its own attempt count and lock; once it is locked the usual locks apply, so a stolen device cookie gives no more attempts than the per-user lock. The 20 browsers used most recently are kept (in the user's record); each new one is audited (`device_add`) and the user can forget them from the profile.
  - Every sign-in answer (password, TOTP, passkey) takes 1 s (waited until the second is over by `hrtime`: `usleep()` may wake early), except a locked IP's, answered at once (it says nothing about users), and wrong user, wrong password, disabled account and lock give the same message: no user enumeration by timing or text. Within that second the last sign-in and the failures since then are read from the audit log for the sign-in notice (at most 90 days back; worst case 73 ms, usually 5 ms).
  - Second factor (optional, or required by the administrator, who must have it first): TOTP (RFC 6238; each code is accepted once, also the one that turned it on) or a passkey. A user without one, once it is required, only reaches the profile until they add it.
  - **Passkeys** (WebAuthn, `WebAuthn.php` + `Cbor.php`, plain PHP + OpenSSL): ES256/RS256, user verification required, one-time challenges, origin and RP id checked, signature counter checked. With the PRF extension the passkey's secret (HKDF) wraps the data key, so it can replace the password; without PRF it is only a second step. Phishing-resistant: a passkey only works on its own site.
- Sessions: new id at sign-in, idle and absolute (12 h) limits (the request that closes an expired session answers `{"error":"auth","reason":…}`, also when it would fail the CSRF check, since the token went with the session; `session.left` tells how long is left without counting as activity; `state` returns `session: {idle, max}`, so the page asks `session.left` only when the session should end and then shows *Session expired* with the reason), bound to the browser (user agent: a stolen cookie fails in another browser and closes the session; the languages are not used because Web Workers may send different ones), and every other session of a user closes when the password changes (session version). The remote sessions opened from a web session end with it (signed out, expired or closed by the gateway: `Sessions::killWeb`, each registered with the sign-in's id `wid`); a password change ends those of the user's other sign-ins (`Sessions::killUser` keeping this `wid`), and the page says *signed out*; signing out in one tab tells the others of that browser (`BroadcastChannel`), which end theirs. A remote session checks every 15 s that its account still exists and is enabled. The password asked again inside a session (passkey or authenticator app added, password changed, second factor removed: `Auth::confirmPassword`) closes it after 5 wrong ones (`reason: reauth`); it does not touch the sign-in locks, which an attack on the user name could hold.
- Temporary passwords set by the administrator must be changed at the first sign-in.
- Remote passwords: AES-256-GCM with a per-user data key. The data key is wrapped with a key derived from the user's password (PBKDF2-SHA256 computed by OpenSSL, 400 000 iterations; a key wrapped with fewer, as up to 1.0.0, is wrapped again at the next sign-in with the password). During a session the data key is kept encrypted in the PHP session with a random key stored only in an HttpOnly cookie, so neither the session file nor the cookie alone reveals it. An administrator password reset makes saved remote passwords unreadable (they are removed).
- Web: CSRF token on every state-changing request, `SameSite=Strict` cookies, strict Content-Security-Policy (`'self'`, plus `data:`/`blob:` images and `blob:` frames), HSTS, HTTPS enforced, client IP allow-list. The API answers 400 `invalid_input` when a field carries a list or object instead of text or a number (`rdp.php` too), and 404 `not_found` for what does not exist. A JSON body is read up to 4 MB and decoded once (413 `too_large` past it: PHP's `post_max_size` does not limit it, and an 8 MB list decoded twice before signing in took 150 MB). PHP's messages never reach the browser, even with `display_errors` on: they go to the server error log, and the visitor gets a page of ours (`ErrorPage.php`), without paths or traces; stack traces carry no arguments (`zend.exception_ignore_args`, passwords marked `#[\SensitiveParameter]`). Values of the address are read as text only (a list such as `p[]=x` is ignored). `files.php`, `rdp.php` and `api.php` (except `state`) refuse a request without a session cookie before a session file is made. Requests from 127.0.0.1 skip the HTTPS check unless that address is a trusted proxy, whose `X-Forwarded-Proto` then decides. Signing out sends `Clear-Site-Data: "cache"`. Items dragged between windows of the application carry a key of that browser (`localStorage`): another page cannot make a drop move files.
- RDP: target allow-list (IPs, CIDR, host names, `*.domain`), DNS resolved once and the checked address is the one used; a name that does not resolve is refused as a target not allowed. Names go through the system resolver (not one of its own, which would break the `hosts` file, search domains and Windows name resolution). With "Allow all", every address of the name is checked and the gateway never connects to itself (127.0.0.0/8, ::1), to link-local addresses (169.254.0.0/16, with the cloud metadata, and fe80::/10) or to 0.0.0.0/8 and ::, also as IPv4 inside IPv6 (::ffff:…, ::a.b.c.d, NAT64 64:ff9b::/96), nor to the other cloud metadata addresses (100.100.100.200, fd00:ec2::254); they can only be reached by listing them, and Administration warns while "Allow all" is set. In the list, an exact name reaches whatever it resolves to; a `*.domain` rule trusts the DNS of every name under it, so those addresses are refused through it too. Server certificate pinned on first use (TOFU) with a warning when it changes; NLA public-key binding verified; a protocol the server picks that was not offered (RDSTLS, NLA extended) ends the connection.
- Shared folder: one quota per user for the drive of all their sessions, the web file manager and clipboard files. The counter (`files/<uid>.quota`) is changed under its own lock by every way of writing, so together they stay within the quota; it is counted again from the folder when the file manager is opened or refreshed with no session of the user running, walked outside the counter's lock; any other list of a folder shows the counter, without walking the folder (that took 7 to 17 s with 20,000 files) (opening the drive with 3000 files went from 205–238 ms to 0.2–1.4 ms). Names over 255 bytes and Windows device names (CON, NUL, COM1, LPT¹, CONIN$… with any extension) are refused (400 `invalid_path`).
- File manager (`files.php`): every path goes through `Files::clean` (no `..`, no configuration file names) and must stay inside the user's folder once links are followed (`Files::confined`, also for the remote drive): nothing of MuDeskClient makes a link, but one put there by something else (a restored backup, a program on the server; a symbolic link, or a Windows junction, which `is_link()` misses) is never followed, and walks of a folder (deleting it, its ZIP, the quota) never go into one (`Files::isLink`). Moves and renames stay inside the user's folder, never over something and never a folder into itself. The tree reads only the open folders (walking every folder took 2.4 s with 1,000 folders and 20,000 files on Windows; the open ones, 64 ms). Actions: `list` (with the quota), `tree` (up to 200 open folders), `move`, `mkdir`, `mkdirs` (up to 1000), `upload`, `delete`, `download` (`view=1`: thumbnails), `zip` (`check=1` first, with the names in the body, up to 10,000, CSRF checked; the answer's id downloads it, `z=`, kept in the session). `delete` waits for an upload chunk still being written. Several items or a folder download as a ZIP written while it is sent (`ZipStream`: stored, each file's CRC read just before it, so the length is known first and there are no data descriptors; no temporary copy; up to 4 GB and 65,535 entries and 64 folders deep, else `too_big`, asked first by the page). Thumbnails are served only for bitmap types, inline with `Content-Security-Policy: default-src 'none'; sandbox` (never SVG or HTML), revalidated each time (`Cache-Control: private, no-cache`, `Last-Modified`, 304).
- Data: `data/` outside the web root, or inside it denied by `.htaccess`/`web.config` (rewritten if missing) with a browser check that warns the administrator if it can be read; server key in an exiting PHP file; files written atomically with locks. A damaged or empty data file stops with an error naming it (an empty `users.json` is never taken for a first run); only the failed sign-ins (`ratelimit.json`) start again, the damaged file kept aside. The last enabled administrator and unique user names are checked under the users' lock, and a TOTP step is taken under it (two sign-ins with the same code at once both passed).
- Audit: one JSON line per event in a file per day; each line carries the HMAC (server key) of its content and the previous line's, so edits, insertions and removals are detected by *Verify integrity* (purged days are expected at the start). The check ends where the log was when it started (days, size of the newest file and its last line, taken under the writers' lock), so lines written meanwhile are left for the next one. Contents and passwords are never logged. The export (up to 20 000 rows) is streamed row by row, each row as stored (about 20 MB of memory instead of about 71 MB). The JSON export is signed with an RSA 3072 server key (`data/audit-key.php`, made once on the first JSON export or when its panel is opened): the SHA-256 is computed piece by piece while the file goes out, with no copy, and signed at the end with PKCS#1 v1.5, which `openssl dgst -sha256 -verify` checks. RSA allows signing a hash computed that way; measured: 0.21–0.23 s for 20 000 rows (0.32–0.36 s for the unsigned export before), 19–20 MB. Writing costs about 0.13 ms per event (lock + append). Refused requests of someone not signed in are written at most 100 times an hour per address and 5,000 in all (`Audit::anonymous`, then one `audit_limited` line). Days are read a line at a time, backwards in 1 MB blocks (a day of 60 MB: 3.7 MB of memory instead of 128 MB); *Verify integrity* lists the first 1,000 problems and counts them all. Search reads the days in range newest first and decodes only the rows shown (measured with 2 000 events/day: 90 days in about 0.1 s, a year in about 0.4 s, 4 MB of memory; verifying a year, 3.4 s).
- **Connections of the administrator** (`Connections::saveManaged`): given to users who cannot change or delete them. The administrator never sets or reads a user's password (encrypted with the user's key); when the target of a connection changes (host, port, user, domain, security), the passwords users saved for it and its pinned certificate are dropped, also for a user's own connection changed by the administrator, so that a password typed for one server never reaches another.
- **Limits on what a hostile or broken RDP server can make the gateway or the page hold**:
  - Gateway: a channel message up to 64 MB with the length its first chunk announced; dynamic channel messages up to 64 MB, 8 being joined at a time; XCRUSH history reset only when full; the socket read 4 MB at a time and a write not finished within 30 s (or 15 s without being writable) ending the connection; a desktop up to 32766 a side and 8192 × 8192 pixels; the remote clipboard kept up to 16 MB; print jobs up to 200 MB a session; the drive: 1,024 open handles (64 open files), 20,000 new entries and 2,000 audit lines a session, masks with more than 4 `*` match nothing; drive reads and writes at offsets of 2^63 or more, or ending past it, refused; NCRUSH literals past its 64 KB history refused (as the page refuses them); audio formats only those the page plays (1 or 2 channels, 8–192 kHz, IMA ADPCM blocks of whole groups); messages waiting for a session up to 16 MB; diagnostic traces up to 256 MB in all; the microphone only as 16-bit PCM of 1 or 2 channels at 8–48 kHz, in packets of 10 ms to a second whatever the server asks (one frame a packet made two messages for every 2 bytes), with at most a second of audio waiting, a Format Change before the Open left out (it had no packet size: an endless loop).
  - Page: ZGFX one buffer of the declared size (up to 64 MB); the graphics pipeline's surfaces within 4 times the output, its bitmap cache within 100 MB with each slot inside its surface, ClearCodec glyphs as the codec allows them; drawing-order bitmap caches within the cells offered (600, 600 and 1,024 entries of 256, 1,024 and 4,096 pixels); a desktop over 32766 a side or 8192 × 8192 pixels not taken; clipboard images whose header claims more than they bring (row lengths counted without 32-bit overflow) and remote file chunks past their size refused; a ZIP of remote files up to 65,535 entries and 4 GB (its limits without ZIP64); stream frames up to 128 MB, their length read unsigned (a length of −5 made the worker loop for ever); audio chunks of a format it cannot play and bitmaps or rectangles of no size dropped, never thrown.

## Data layout (`data/`)

```
users.json                 accounts (hashes, wrapped data keys, TOTP seeds encrypted with the server key, passkeys,
                           known browsers)

connections/<uid>.json     connections of each user; under an id starting with "m", what the user keeps of a connection of
                           the administrator (their password, certificate and connect options)

secret.php                 server key (TOTP seeds, the audit chain's HMAC, trusted-browser cookies), behind
                           <?php exit; ?>
audit-key.php              RSA key of the signed audit exports, behind <?php exit; ?>
.htaccess, web.config,     deny web access (Apache/LiteSpeed/OpenLiteSpeed and IIS;
index.html                 written again if missing)
setup-code.php             one-time code for the first run (deleted once the administrator exists)
web-check.txt              the browser tries to read it to detect an exposed folder
ratelimit.json             failed logins
auditlimit.json            refused requests of visitors not signed in, counted per hour
*.json.lock                lock of each JSON store
audit/YYYY-MM-DD.jsonl     audit log, one file per day (.last: hash of the last line; .lock)
sessions/                  PHP sessions
run/                       running RDP sessions (registry, sockets, queues, register.lock)
tmp/<sid>/                 clipboard uploads and print jobs of a session (removed at the end)
tmp/upload-<uid>.lock      one upload of the user's shared folder at a time
trace/<sid>.log            diagnostic traces (removed after 7 days)
files/<uid>/               shared folder of each user
files/<uid>.quota          bytes counted against the user's quota
```
